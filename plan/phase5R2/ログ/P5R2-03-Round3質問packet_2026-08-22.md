## 3. Round 3質問

### Q-R3-01：終了時刻の境界例

#### 背景

Q-R2-01=Aで、指定終了時刻と有効終了時刻を表示し、確認してから実行する方針は回答された。しかし、UTC基準、指定終了時刻が時間足境界外の場合、開始より前になる場合、実質ゼロ期間になる場合の扱いが未確定である。

#### 今回決める範囲

入力検証、切下げ、確認画面、API入力、Run保存、Preflightの停止条件を決める。

#### 推奨案：A

UTCを基準に、境界外の終了時刻は直前の完成済みバーまで切り下げる。指定値と有効値、切下げ理由を表示して確認を求める。開始時刻以前または有効バー0件になる場合は実行を拒否し、入力修正へ戻す。

推奨理由は、利用者の意図しない空計算・期間変更を防ぎ、表示・API・Run保存を同じ規則にできるためである。

#### 選択肢

- A（推奨）：UTC基準で切下げ、指定値と有効値を保存し、開始前・ゼロ期間は拒否する。
- B：ゼロ期間でも確認後に実行する。空の結果や意味のないRunを作る可能性がある。
- C：境界外の終了時刻を入力エラーにする。仕様は単純だが、現在の切下げ方針を変更する。

回答：Q-R3-01 = A / B / C

### Q-R3-02：補間可能な欠損の上限

#### 背景

Q-R2-02=Bにより、限定的な欠損1mを補間し、警告付きで使用可能にする方向が回答された。「限定的」が曖昧なままだと、少しの欠損と長時間の欠損を同じようにBacktestへ通す危険がある。

#### 今回決める範囲

連続欠損数、対象期間内の欠損位置、始端・終端欠損、警告表示、usable昇格の入口を決める。補間式そのものはQ-R3-03で決める。

#### 推奨案：A

各対象上位足の内部にある連続1分欠損だけを補間可能とし、始端・終端の欠損は拒否する。補間件数と対象バーを警告表示・保存する。

推奨理由は、補間範囲を最小にし、将来側の値を使わない条件を作りやすいためである。

#### 選択肢

- A（推奨）：内部欠損のみ、連続1分まで。始端・終端欠損は拒否する。
- B：内部欠損のみ、連続3分まで。利用可能範囲は広がるが、推測値の割合が増える。
- C：期間全体に対する欠損率で判定する。長い連続欠損を見逃す可能性があるため、追加の連続上限が必要になる。

回答：Q-R3-02 = A / B / C

### Q-R3-03：補間方式・provenance・usable状態

#### 背景

欠損を補間して使用可能にする場合、どの値を作るか、後続の実測値を参照してよいか、利用者にどう警告するかを決める必要がある。方法を決めないと、同じDataから別のBacktest結果が生成される。

#### 今回決める範囲

OHLCVの補間方法、未来側データの参照禁止、補間を含むDataSetの状態、保存するprovenanceを決める。

#### 推奨案：A

直前の実測closeを使って、補間バーのopen/high/low/closeを直前close、volumeを0とする。後続の実測値は使わない。DataSetは通常USABLEと区別できるUSABLE_WITH_WARNING状態とし、補間件数、元DataSet ID、補間規則の版、対象timestampを保存する。

推奨理由は、未来側の値によるlook-aheadを防ぎ、補間DataであることをBacktest結果から追跡できるためである。

#### 選択肢

- A（推奨）：過去側のcloseだけで固定値バーを作り、USABLE_WITH_WARNINGとしてprovenanceを必須保存する。
- B：前後の実測値を使う線形補間を許可し、USABLE_WITH_WARNINGとする。自然な値になりやすいが、未来側参照の規則が必要になる。
- C：補間したDataSetは常にPARTIAL / unusableとする。安全だが、Q-R2-02=Bの使用可能方針を取り消す。

回答：Q-R3-03 = A / B / C

### Q-R3-04：DataSetのusable昇格条件

#### 背景

Q-R2-04=Aで、DownloadJobとDataSetを分離し、品質確認前のDataSetは使用不可とする方向が回答された。Jobが完了したことと、DataSetがBacktestに使えることを同じ意味にしないため、品質検査の合格条件が必要である。

#### 今回決める範囲

JobのSUCCEEDEDとDataSetのUSABLEの関係、欠損・重複・時系列順・期間充足・provenance検査、品質不合格時の再試行単位を決める。

#### 推奨案：A

DownloadJobがSUCCEEDEDでも、品質検査に失敗したDataSetはUNUSABLEに留める。欠損規則、重複、時系列順、要求期間、provenanceを検査し、再生成・修復は新Jobと新DataSetにする。

推奨理由は、取得処理が完走した事実と、Backtestに使える品質を分離できるためである。

#### 選択肢

- A（推奨）：必須品質検査をすべて通過したDataSetだけをUSABLEにする。失敗時はUNUSABLEとし、新Jobで再試行する。
- B：品質警告だけでUSABLEにする。警告の見落としで不完全Dataが使われる可能性がある。
- C：品質不合格ならJob自体をFAILEDに戻し、DataSetを作らない。状態は厳格だが、取得完了と品質失敗の履歴を分けにくい。

回答：Q-R3-04 = A / B / C

### Q-R3-05：重複Dataの選択とversion固定

#### 背景

Q-R2-05=Cで、同じ条件のData重複を許可し、利用者が選択する方向が回答された。複数DataSetを許可するなら、どれを使ったかをRunに固定しないと、同じBacktestを再現できない。

#### 今回決める範囲

Data Catalogの表示項目、既定選択の有無、利用者の明示選択、DataSet ID/versionのRun保存を決める。

#### 推奨案：A

重複Dataをすべて一覧表示し、Provider、symbol、時間足、期間、取得時刻、version、品質状態、補間有無を表示する。既定値で自動選択せず、利用者が選択したDataSet ID/versionをRunへ不変保存する。

推奨理由は、暗黙のData変更を防ぎ、利用者が選択した入力を後から再現できるためである。

#### 選択肢

- A（推奨）：重複Dataをすべて表示し、必ず明示選択。RunへDataSet ID/versionを固定保存する。
- B：最新のUSABLE versionを初期選択し、利用者は変更できる。便利だが、初期選択理由を表示・保存する必要がある。
- C：「推奨version」だけを通常表示し、他のDataは詳細画面に隠す。誤選択は減るが、比較と監査が難しくなる。

回答：Q-R3-05 = A / B / C

### Q-R3-06：terminal Runの取消の意味

#### 背景

Q-R2-06=Cで、terminal状態のRunにも取消操作を許可する方向が回答された。完了済みRunは計算を止められないため、取消が状態変更・無効化・削除のどれなのかを明確にする必要がある。

#### 今回決める範囲

SUCCEEDED、FAILED、CANCELLED、RECOVERY_REQUIRED、LEGACY_RESULT_ONLYごとの取消可否、取消後の状態、結果・CSV・checkpoint・監査、削除との境界を決める。

#### 推奨案：A

terminal Runへの取消要求は受け付けるが、Run状態・結果・CSV・checkpointは変更しない冪等な監査イベントとして記録する。画面には「すでに完了しているため計算は取消できない」と表示し、結果を消す操作は削除として分離する。

推奨理由は、ユーザーが選択した「terminalにも取消操作を許可する」をUI上で受け止めつつ、過去結果の意味と再現性を壊さないためである。

#### 選択肢

- A（推奨）：terminal取消は状態を変えない受付・監査記録。結果とRunは不変、削除は別操作。
- B：SUCCEEDED/FAILEDをCANCELLEDへ再分類するが、結果は保持する。状態履歴が変わり、集計・再現性への影響が大きい。
- C：terminal取消で結果をTrashへ移し、削除要求として扱う。取消と削除が混ざり、誤操作からの復旧が複雑になる。

回答：Q-R3-06 = A / B / C

### Q-R3-07：cascade削除の対象と依存関係

#### 背景

Q-R2-07=Bで、利用者が明示的に選択した対象のcascade削除を許可する方向が回答された。しかし、他Runが参照する比較・Holdout・Sweep・CSV Jobまで選べると、別Runを壊す可能性がある。

#### 今回決める範囲

選択可能な対象、外部参照がある場合の拒否、Test Evidence・監査・tombstoneの保護、削除確認画面を決める。

#### 推奨案：A

対象Runが専有するresult、rows、CSV、checkpointだけを初期cascade対象とする。比較、Holdout、Sweep親子、別Runの参照、実行中CSV Jobがある場合は削除を拒否する。Test Evidence、監査記録、tombstoneは選択対象外とする。

推奨理由は、明示cascadeの方針を尊重しながら、別Run・監査・検証証拠の参照破壊を防げるためである。

#### 選択肢

- A（推奨）：対象Run専有の出力だけcascade可。外部参照があれば拒否。監査・Test Evidence・tombstoneは保護する。
- B：比較・Holdout・Sweep子なども依存一覧から明示選択すればcascade可。柔軟だが、依存グラフの完全表示と復旧が必要になる。
- C：Runから辿れる関連物をすべてcascadeする。便利だが、意図しない親子・別Runの破壊が起きる。

回答：Q-R3-07 = A / B / C

### Q-R3-08：cascadeの原子性・復旧・監査・手順書

#### 背景

明示cascadeを許可しても、途中で一つの対象だけ失敗したときに一部だけ削除されると、参照破壊と復旧不能が起きる。Q-R2-08=Aで監査と手順書反映の方針は回答されたため、cascadeの失敗・復旧も同じ記録へつなぐ必要がある。

#### 今回決める範囲

事前依存チェック、all-or-nothingか部分成功か、Trash移動、RECOVERY_REQUIRED、復旧、監査必須項目、手順書反映条件を決める。

#### 推奨案：A

事前に依存関係を全件確認し、対象を一つの削除操作としてTrashへ移す。途中失敗時は部分成功を完了扱いにせずRECOVERY_REQUIREDとし、復旧操作を可能にする。操作者、理由、対象ID、旧状態、新状態、依存件数、相関IDを監査し、検証済みの操作だけを01_バックテスト手順書へ反映する。

推奨理由は、部分破壊を防ぎ、失敗・復旧・手順書の三つを同じ証跡で追跡できるためである。

#### 選択肢

- A（推奨）：全対象の事前確認後に一括Trash移動。途中失敗はRECOVERY_REQUIRED、監査と復旧を必須にする。
- B：対象ごとの部分成功を許可する。処理は続きやすいが、削除済み・未削除の混在と復旧順序が複雑になる。
- C：Trashを使わず即時完全削除する。不可逆であり、DELETE-G1承認なしには採用できない。

回答：Q-R3-08 = A / B / C
