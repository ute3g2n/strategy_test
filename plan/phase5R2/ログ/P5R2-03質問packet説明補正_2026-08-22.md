## Q-R2-01：指定終了時刻と有効終了時刻の表示・確認

### 背景

ユーザーが 2026-01-01 10:07 まで、と指定しても、15m・30m・1hなどの足はその時刻でちょうど区切れないことがあります。現在の方向性は「最後に完成している時間足の境界まで切り下げる」ですが、利用者に指定時刻と実際に使う時刻をどう見せるかが未確定です。ここが曖昧だと、利用者は10:07まで計算されたと思っているのに、実際には10:00までしか使われない、という誤解が起きます。

### 今回決めてほしい範囲

終了時刻を境界まで切り下げる方針を維持したうえで、Single Backtest画面、確認ダイアログ、Run保存情報に、指定値と有効値をどう表示し、実行前に確認を求めるかを決めます。UTC表示、開始より前、期間がゼロになる場合は、選択後に詳細仕様として整理します。

### 推奨案：A

指定終了時刻と切り下げ後の有効終了時刻を両方表示し、「指定時刻に対応する完成済みバーまでで実行します」と理由を示した確認ダイアログを出します。利用者が確認してから実行し、Runには両方の時刻を保存します。

推奨理由は、計算範囲の短縮を黙って行わず、画面・実行記録・後日の結果確認で同じ事実を追跡できるからです。追加の確認操作は増えますが、Backtest結果の誤読を防ぐ効果が大きいです。

### 選択肢

- A（推奨）：指定終了時刻と有効終了時刻を両方表示し、差分理由を説明して、実行前に確認する。Runにも両方保存する。画面と保存項目は増えるが、誤解と再現性の問題を抑えられる。
- B：両方を表示するが、確認ダイアログは出さず、そのまま実行する。操作は簡単になるが、利用者が有効期間の短縮を見落とす可能性がある。
- C：時間足の境界でない終了時刻は入力エラーにする。意味は単純になるが、利用者が指定可能な時刻を選び直す必要があり、現在の「境界まで切り下げる」方向性を変更する。

### 影響する範囲

Single Backtest、Preflight、Backtest APIの入力・確認、Runメタデータ、結果サマリー、テスト、01_バックテスト手順書。

**回答：Q-R2-01 = A / B / C**

## Q-R2-02：Q-TF-05の欠損1mと補間

### 背景

上位足（15m、30m、1h、4h、1d）は1mデータから生成します。必要な1mが途中で欠けている場合、欠けたまま上位足を作ると、実際には存在しない値を含むBacktestになる可能性があります。さらに、Round 1の「5. C」と、既存記録の「欠損1mを含む上位足は補間する方向性」が一致していないため、ここは再確認が必要です。

### 今回決めてほしい範囲

欠損1mがあるときに、上位足を生成するか、補間したDataを使用可能とみなすかを決めます。AとCは似ていますが違います。Aは補間した上位足を生成しません。Cは調査・一覧表示のための補間表示を許す余地は残しますが、Backtestに使えるDataSetにはしません。

### 推奨案：C

補間値を調査・表示に使うことは許可しても、補間を含むDataSetは常に PARTIAL / unusable とし、Backtest実行には使えないようにします。

推奨理由は、調査上の見やすさを保ちながら、推測値が正式な過去DataとしてBacktest結果へ混ざることを防げるからです。補間を「使用可能」にするために必要な欠損量、始端・終端の扱い、警告、provenance、future参照禁止、再現性を先に細かく決める必要がなく、安全側で仕様を閉じられます。

### 選択肢

- A：補間は一切せず、必要な1mに欠損があれば上位足生成を失敗させる（PARTIAL_BAR_REJECTED）。最も厳格で再現性は高いが、少しの欠損でも対象期間全体を生成できない。
- B：連続欠損数などの上限を決め、範囲内だけ補間して警告付きで使用可能にする。Dataの利用範囲は広がるが、補間式・始端終端・警告・品質基準・再現性を追加で厳密に決める必要がある。
- C（推奨）：補間は調査表示に限定し、補間を含むDataSetは PARTIAL / unusable のままにする。Backtestは拒否するため、正式結果への混入を防げる。

### 影響する範囲

Data生成、DataSet品質状態、usable判定、provenance、欠損警告、Backtest Preflight、再現性、テスト、01_バックテスト手順書。

**回答：Q-R2-02 = A / B / C**

## Q-R2-03：「任意のsymbol」の入力境界

### 背景

Round 1では、任意の銘柄・任意の期間を扱う方向性が示されました。しかし「任意」が、画面に文字を自由入力できるという意味なのか、対応Providerの銘柄なら選べるという意味なのかは別です。境界を決めないと、存在しない銘柄、Providerが扱わない銘柄、別marketの記号を入力したときの動作が定まりません。

### 今回決めてほしい範囲

symbolの選び方と、Provider Catalogにないsymbolを受け付けるかを決めます。これは実Providerへの接続やData取得を許可する質問ではなく、画面入力・検証・後続のDATA-G1で確認する範囲の境界を決める質問です。

### 推奨案：A

画面ではProvider Catalogに登録済みで、対応済みと明示されたSpot symbolだけを選択可能にし、自由入力は許可しません。CatalogにはmarketとProviderを表示し、未対応symbolは選択できない状態にします。

推奨理由は、入力の意味をCatalogと結び付け、Provider境界外のsymbolや誤入力を早く拒否できるからです。「任意symbol」は「Catalogの中から利用者が任意に選べる」という意味に整理できます。

### 選択肢

- A（推奨）：対応済みProvider CatalogのSpot symbolだけを選択可能にし、自由入力不可とする。安全で説明しやすいが、Catalogへの登録が必要になる。
- B：Catalog選択に加えて、形式検証を通った自由入力も許可する。将来の拡張性はあるが、Provider未対応、market違い、表記揺れ、実取得可否のエラー処理が複雑になる。
- C：任意の文字列を受け付ける。入力は簡単だが、意味のないsymbolや外部境界外の値を後段まで通してしまうため、現時点では採用しない。

### 影響する範囲

銘柄Catalog、Single BacktestとData生成画面の入力、入力検証、エラー表示、監査、DATA-G1のProvider・symbol範囲。

**回答：Q-R2-03 = A / B / C**

## Q-R2-04：DownloadJobとDataSetの状態契約

### 背景

UIからヒストリカルDataを生成・ダウンロードすると、開始した処理そのものと、後からBacktestに使える完成Dataは別物です。処理が途中で失敗した場合や、同じ処理を再試行した場合を同じレコードで上書きすると、「失敗したのに使用可能に見える」「どの取得結果を使ったのか分からない」という問題が起きます。

### 今回決めてほしい範囲

ダウンロード処理の試行記録（DownloadJob）と、Catalogに載るDataSetを別ID・別状態で管理するかを決めます。ここで決めるのは状態モデルであり、実Providerへのdownloadを開始する承認ではありません。

### 推奨案：A

DownloadJobは QUEUED / RUNNING / SUCCEEDED / FAILED / CANCELLED などの処理状態を持ち、DataSetは PARTIAL / UNUSABLE / USABLE / DISABLED などの利用状態を別に持たせます。Jobが部分成功・失敗・取消になったDataはUSABLEへ昇格させず、再試行は新しいJobとして残します。

推奨理由は、「何を試したか」と「何をBacktestに使えるか」を分離でき、失敗や再試行の履歴を消さずに済むからです。品質検査を通過したDataだけを使用可能にするため、Backtestの入口も明確になります。

### 選択肢

- A（推奨）：DownloadJobとDataSetを別ID・別状態で管理し、PARTIAL / FAILED / CANCELLEDをUSABLEにしない。retryは新Jobとする。記録は増えるが、再現性と状態の安全性が高い。
- B：JobとDataSetを同じレコード・同じ状態で管理する。実装は単純になるが、取得試行と使用可否が混ざり、失敗・再試行・修正版の追跡が難しくなる。
- C：Jobが成功した時点で、品質確認なしにDataSetをUSABLEにする。画面上は早く使えるが、壊れた・欠損したDataをBacktestへ通す危険がある。

### 影響する範囲

Data生成画面、Download API、Job一覧、Data Catalog、永続化、品質検査、再試行、Backtest Preflight、監査、テスト。

**回答：Q-R2-04 = A / B / C**

## Q-R2-05：同じDataの再取得・修正版・重複

### 背景

同じProvider・symbol・時間足・期間のDataをもう一度取得する場合、完全に同じDataなのか、Provider側の修正版なのか、別の取得試行なのかを区別する必要があります。既存Dataを黙って上書きすると、過去に実行したBacktestがどのDataを使ったのか再現できなくなるおそれがあります。

### 今回決めてほしい範囲

同一source identityの扱い、修正版のversion管理、Data一覧への表示、既存Runとの参照関係を決めます。

### 推奨案：A

同一source identity（Provider、market、symbol、timeframe、期間など）が一致し、内容の更新がない場合は新規取得を重複登録せずskipします。Provider側の修正や再生成結果は新versionとして登録し、既存DataSetをin-place上書きしません。Runは実際に使ったDataSet versionを保持します。

推奨理由は、過去のBacktest結果を後から変えず、同じ条件の重複Dataを増やさず、修正版も履歴として扱えるからです。

### 選択肢

- A（推奨）：同一source identityはskip、修正版は新version、既存DataSetは上書きしない。Catalogとversion表示は必要になるが、再現性を守れる。
- B：同じ条件なら既存Dataをin-placeで上書きする。管理は簡単だが、過去Runの入力が変わったように見える。
- C：同じ条件でも重複Dataを許可し、利用者が一覧から選ぶ。柔軟だが、どれを選ぶべきか分かりにくく、誤選択・運用負担が増える。

### 影響する範囲

Data Catalog、version、重複判定、RunとDataSetの参照、再現性、復旧、Data一覧、01_バックテスト手順書、テスト。

**回答：Q-R2-05 = A / B / C**

## Q-R2-06：Run取消の状態・画面・競合

### 背景

今回の要求では、Backtest実行一覧・進捗・結果サマリー画面に、取消・削除の扱いを追加します。取消は、処理中に止める操作であり、完了後の結果を消す操作とは違います。画面ごとに別の判定を持つと、一覧では取消できるのに進捗ではできない、二重押下で二重処理になる、といった不整合が起きます。

### 今回決めてほしい範囲

どのRun状態で取消を許可するか、3画面で同じ表示・API判定にするか、二重操作や復旧中のRunをどう扱うかを決めます。

### 推奨案：A

QUEUED / RUNNING のRunだけを取消可能とし、実行一覧・進捗・結果サマリーの3画面で同じ可否判定と同じ取消APIを使います。二重押下や再送は同じ取消要求として扱い、terminal、RECOVERY_REQUIRED、LEGACY_RESULT_ONLY は理由付きで取消不可とします。

推奨理由は、取消を「まだ動いている処理を止める操作」に限定し、画面間の矛盾と状態破壊を防げるからです。完了済み結果の扱いはQ-R2-07の削除方針で分けて管理できます。

### 選択肢

- A（推奨）：QUEUED / RUNNINGだけ取消可。3画面共通判定、二重押下は冪等、terminal・RECOVERY_REQUIRED・LEGACY_RESULT_ONLYは理由付き不可。安全で一貫する。
- B：進捗画面だけ取消可とする。処理中の操作は分かりやすいが、実行一覧・結果サマリーとの操作差が生じる。
- C：terminal状態にも取消ボタンを表示し、取消可能にする。見た目は統一できるが、完了済み結果の状態を後から変えるため、監査・再現性・依存関係を壊しやすい。

### 影響する範囲

実行一覧、進捗、結果サマリー、Run状態遷移、取消API、二重操作、Sweep親子、復旧、監査、テスト、01_バックテスト手順書。

**回答：Q-R2-06 = A / B / C**

## Q-R2-07：Run削除の対象・依存・復旧

### 背景

結果サマリーから削除を許可する場合、画面上の結果だけでなく、result、rows、CSV、checkpoint、比較用選択、Holdout参照、Sweepの親子などが関係します。一部だけ消すと、残った参照が壊れたり、過去Runの説明ができなくなります。また、ユーザーが誤って削除した場合に戻せるかも決める必要があります。

### 今回決めてほしい範囲

削除要求できるRun状態、削除対象、依存中の拒否、Trash・tombstoneによる復旧、初期Scopeでcascadeを許可するかを決めます。実Data・実Runを実際に削除することは、別のDELETE-G1承認がない限り行いません。

### 推奨案：A

SUCCEEDED / FAILED / CANCELLED だけ削除要求できるようにし、mutableなresult、rows、CSV、checkpoint、比較選択などはTrashへ移します。Catalogにはtombstoneと監査記録を残します。Sweep親子、CSV Job、比較、Holdout参照など依存が残っている場合は削除を拒否し、初期Scopeではcascade削除を許可しません。LEGACY_RESULT_ONLYは閲覧専用とします。

推奨理由は、誤削除から戻せる余地を残し、参照を壊す連鎖削除を防ぎ、Runが存在したことと削除理由を監査できるからです。削除機能を追加しても、いきなり不可逆な完全削除にはしません。

### 選択肢

- A（推奨）：SUCCEEDED / FAILED / CANCELLEDのみ要求可。依存中は拒否。初期Scopeではcascade不可。mutableな結果はTrash、Catalogはtombstone、legacyは閲覧専用。安全で復旧しやすい。
- B：依存一覧を表示し、利用者が明示した対象だけcascade削除できる。柔軟だが、親子・比較・Holdout・CSVの関係を正しく選ぶ必要があり、実装・テスト・運用が大きくなる。
- C：result、Catalog、関連物を即時に完全削除する。単純だが、誤操作から戻せず、参照破壊と監査欠落の危険があるため採用しない。

### 影響する範囲

結果サマリー、Run Catalog、result・rows・CSV・checkpoint、compare、Holdout、Sweep、Trash、復旧、DELETE-G1、監査、テスト、01_バックテスト手順書。

**回答：Q-R2-07 = A / B / C**

## Q-R2-08：監査と01_バックテスト手順書の改訂範囲

### 背景

Download、DataSetの使用可能化、Run取消、Run削除は、成功した場合だけでなく、拒否・失敗・再試行・復旧が発生します。成功だけを記録すると、「誰が何をしようとして、なぜ拒否されたか」が分からなくなります。また、01_バックテスト手順書に未実装の操作を書くと、運用者が実際にはできない操作を行おうとして混乱します。

### 今回決めてほしい範囲

監査ログに何を残すか、手順書をどの時点・どの状態まで更新するかを決めます。手順書の修正そのものは、要件確定・実装・検証が終わった後の対象Stepで行います。

### 推奨案：A

Download開始・確認・取消・失敗・再試行、DataSetのusable昇格、Run取消、削除要求・拒否・成功・失敗をすべて監査します。操作者、理由、対象ID、旧状態、新状態、依存物件数を残します。01_バックテスト手順書には、実装・検証済みの操作だけを、成功・失敗・復旧・Trash・legacy閲覧専用を含めて反映します。

推奨理由は、障害や誤操作を追跡でき、手順書と実際の画面の差を防げるからです。未実装の機能を先に手順書へ書かないため、運用者に誤った期待を持たせません。

### 選択肢

- A（推奨）：成功・失敗・拒否・取消・再試行・復旧を監査し、実装・検証済みの操作だけを01_バックテスト手順書へ反映する。安全性と運用の一致を保てる。
- B：成功した取消・削除だけを監査し、手順書は別のタイミングで更新する。記録は簡単だが、失敗・拒否・再試行の原因追跡ができない。
- C：監査と手順書の範囲を実装後に決める。今は決めなくて済むが、API・保存項目・テスト・画面説明が後から揺れ、手順書修正漏れが起きやすい。

### 影響する範囲

監査永続化、Security、Run/Data操作、P5R2-UNK-DOC-001、doc/phase5R/07_運用手順/01_バックテスト手順書.html、画面キャプチャ、テスト追跡。

**回答：Q-R2-08 = A / B / C**
