# P5R2 UI ヒストリカルData期間日時入力 修正計画書

- 計画ID: `P5R2-UI-DT-001`
- 作成日: 2026-08-23
- 状態: `DRAFT`
- 対象: ヒストリカルDataの開始・終了期間を入力するUI

## 1. 目的

ヒストリカルDataの期間入力を、ISO文字列を直接入力する方式から、カレンダーと時刻選択を使って入力できる方式へ変更する。

この変更で変えるのは利用者向けの入力方法であり、次の既存契約は変えない。

- 期間はUTCで扱う。
- Backtestの期間境界は現在の半開区間 `[開始, 終了)` を維持する。
- Application APIへ渡す開始・終了値はISO-8601 UTC文字列を維持する。
- 15m / 30m / 1h / 4h / 1dの戦略時間足、1m sourceの役割、Data Catalogの品質判定は変更しない。
- 外部Provider、Secret、外部Data取得、DBスキーマ変更はこの修正の対象外とする。

## 2. 現状と問題

現在、次の画面に期間を直接文字列で入力する欄がある。

1. `ui/mock/src/P5R2WebProductScreen.tsx`
   - P5R2「Single Backtest条件」の開始・終了
   - P5R2「時間足生成」の生成開始・生成終了
2. `ui/mock/src/P5RBacktestScreen.tsx`
   - 現行P5R2画面から開ける旧P5R履歴表示の開始・終了
3. `ui/mock/src/App.tsx`
   - 汎用モックの単一Runにある期間欄

現在は、利用者が `2025-02-24T00:00:00Z` のような文字列形式、UTC、秒、末尾の `Z` を意識して入力する必要がある。入力ミスの発見が遅く、カレンダーから日付を選びたいという通常のUI操作にも対応していない。

## 3. 「全て」の対象範囲

この計画では、「全て」を「利用者が操作できる画面に残っている、ヒストリカルDataの開始・終了を指定する入力欄すべて」と解釈する。

### 3.1 対象に含めるもの

- P5R2のBacktest開始日時・終了日時
- P5R2の時間足生成開始日時・終了日時
- 旧P5R画面が現行UIから開ける場合のBacktest開始日時・終了日時
- 汎用モックに残る履歴期間入力欄

旧画面を対象に含めるのは、現行UIから到達可能であり、旧画面だけ文字列入力を残すと「全て」という要件に反するためである。旧画面の時間足やAPIの業務仕様は変更せず、入力方法だけを変更する。

### 3.2 対象に含めないもの

- Data Catalogや結果サマリーに表示するだけの期間文字列
- 不足Dataダイアログに表示する要求期間
- `Entry期間`、`Entry lookback`、`Exit lookback`、ATR係数などの数値パラメータ
- 実行日時、Job日時、取引日時など、利用者が期間を指定する入力欄ではない表示項目
- 戦略時間足の選択肢、1m source、30mの扱い

## 4. 推奨するUI方式

### 4.1 推奨案: ブラウザ標準の日時選択欄

新しい外部ライブラリを追加せず、共通の `UtcDateTimePicker` 相当のUI部品を作り、各画面の開始・終了欄から再利用する。

実体はブラウザ標準の `input type="datetime-local"` とし、カレンダーと時刻選択をブラウザ／端末の標準UIで提供する。

- 開始欄と終了欄をそれぞれ1つの日時欄にする。
- 表示ラベルは「開始日時（UTC）」「終了日時（UTC）」とする。
- `step="60"` とし、分単位で選択する。
- UI値は `YYYY-MM-DDTHH:mm` とする。
- API送信値は `YYYY-MM-DDTHH:mm:00Z` とする。
- キーボード入力はアクセシビリティ上の代替手段として残すが、主な入力方法はカレンダー／時刻ピッカーとする。
- 外部datepickerパッケージは追加しない。

### 4.2 UTCの扱い

`datetime-local`自体にはタイムゾーン情報がないため、ブラウザのローカル時刻へ勝手に変換してはならない。UI上の値をUTCの日時トークンとして扱い、シリアライズ時に明示的に `Z` を付ける。

実装では、`new Date(inputValue)` のようなブラウザのローカルタイムゾーン解釈に依存しない。次の変換を共通関数に閉じ込める。

```text
ISO UTC文字列  -> datetime-local表示値（YYYY-MM-DDTHH:mm）
datetime-local値 -> ISO UTC文字列（YYYY-MM-DDTHH:mm:00Z）
```

既存の期間境界の意味、UTC検証、Data範囲検証は変更しない。

### 4.3 秒の扱い

現行のP5R2サンプル期間は分単位かつ秒が `00` であるため、推奨初期仕様は分単位、秒は `00` 固定とする。既存値に `:00` 以外の秒が存在することが調査で判明した場合は、秒を黙って丸めず、実装を止めて次のいずれかを決める。

- 秒選択を追加して秒まで保持する。
- 対象ドメインが分境界だけであることを確認し、入力を分単位に制限する。

この計画では、秒を黙って切り捨てる実装を禁止する。

## 5. 画面ごとの動作仕様

### 5.1 P5R2 Backtest条件

- 現在の開始・終了文字列欄を共通日時選択欄へ置き換える。
- 初期値の表すUTC時刻は現状と同じにする。
- 日時が未入力、形式不正、開始が終了以上の場合は、Preflight／Run APIを呼ばず、入力欄の近くに理由を表示する。
- Data Catalogの範囲外であることの判定は、既存のPreflightを正本とする。
- Preflightへ渡す `start`、`end` は、従来と同じISO UTC文字列にする。
- 不足Dataダイアログへ表示する要求期間は、変換後の同じUTC値を使う。

### 5.2 P5R2 時間足生成

- 現在の生成開始・生成終了文字列欄を共通日時選択欄へ置き換える。
- 1m sourceがある場合、現在のsource coverage全体を初期値にする既存仕様を維持する。
- sourceがない場合は、現在どおり期間を空欄にし、生成要求を送信しない。
- source coverageを超える期間、逆順、同一時刻、未入力は、生成Job APIを呼ばずに停止する。
- 生成要求の `requested_range.start/end` は従来どおりISO UTC文字列にする。
- 銘柄、複数時間足、Job状態、外部I/O禁止の境界は変更しない。

### 5.3 旧P5R画面と汎用モック

- 現行UIから到達可能な旧P5R画面の開始・終了欄も同じ共通部品へ置き換える。
- 旧P5Rの1m、既存API、Preflight、履歴の意味は変更しない。
- `App.tsx`の汎用モックにある単一の「期間」文字列欄は、開始日時・終了日時の2欄へ置き換える。
- 期間を指定する入力欄を残したまま、文字列1欄だけを日時選択化する中途半端な状態にしない。

## 6. 入力検証とエラー仕様

共通部品または共通ユーティリティで、画面ごとに違う判定を作らない。

最低限、次を検証する。

1. 開始日時と終了日時が両方そろっている。
2. カレンダー上存在する日付である。
3. UTCとしてシリアライズできる。
4. 開始日時が終了日時より前である。
5. 既存の期間境界（半開区間）と矛盾しない。
6. 生成時はsource coverage内である。
7. APIへ渡す値に、ローカルタイムゾーン由来のずれがない。

エラー時の原則は次のとおりとする。

- エラー理由を開始・終了のどちらに問題があるか分かる形で表示する。
- エラー中はPreflight、Run作成、生成Job作成を実行しない。
- 自動的に日時を補正、丸め、入れ替え、source範囲へ切り詰めない。
- APIから返る既存の `DATA_INSUFFICIENT` などのエラー表示は変更しない。

## 8. 実行ステップと実行プロンプト

### Step 1: 入力欄の全件棚卸しと契約固定

目的は、ユーザーが操作できる全画面から、ヒストリカル期間入力を漏れなく特定し、対象外の数値期間と区別すること。

実行プロンプト:

```text

対象は、P5R2WebProductScreen.tsx、P5RBacktestScreen.tsx、App.tsx、関連するAPI型、テスト、P5R2 UI設計書、バックテスト手順書です。

Entry期間、lookback、ATR係数などの数値パラメータ、表示専用の期間文字列は対象外として明記してください。

「全て」の対象に漏れがないこと、旧画面を入力方法だけ変更するか、秒を保持する必要があるかを判断してください。
秒が00以外の値を扱う契約、ローカル時刻への暗黙変換、未確認の期間入力欄が見つかった場合は、実装へ進まず停止理由を報告してください。
```

## 10. 受入条件

以下をすべて満たした場合に修正完了とする。

1. 利用者が操作できる全ヒストリカル期間入力で、カレンダーと時刻を選択できる。
2. ヒストリカル期間を直接入力する生のtext欄が対象画面に残っていない。
3. UI操作後のAPI値は従来どおりISO-8601 UTC文字列で、ローカル時刻へのずれがない。
4. P5R2のsource coverage全期間の初期値と、空source時の停止動作が変わらない。
5. 開始・終了の不備でPreflight、Run、生成Jobが誤って実行されない。
6. 半開区間、Data Catalog、時間足、1m source、30m、外部I/O境界が変わらない。
7. デスクトップ、モバイル、キーボード、axe、既存unit/component/E2Eが確認できる。
8. P5R2 UI設計書とバックテスト手順書の入力説明が実装と一致する。

## 11. 停止条件

次のいずれかに該当した場合、画面ごとの場当たり修正を続けず、実装を止めてこの計画を見直す。

- 秒を00にできない既存データやAPI契約が確認された。
- `datetime-local`をUTCとして扱うための変換境界が既存APIと一致しない。
- 現行UIから到達できる別のヒストリカル期間入力が見つかった。
- 期間境界が半開区間ではない画面が見つかった。
- Backend変更、DB migration、外部Provider接続が必要になる。
- 既存のP5R2時間足選択や1m／30mの仕様を変更しないと実装できない。

## 13. 推奨判断

この計画では、次の判断を推奨する。

- 日時UIは外部ライブラリではなく、標準 `datetime-local` を共通部品化する。
- APIとバックエンドのUTC ISO文字列契約は維持する。
- 分単位、秒 `00` 固定で開始し、秒の非00は黙って丸めない。
- 「全て」は現行P5R2画面だけでなく、現行UIから到達可能な旧画面・汎用モックも含める。
- 期間の業務意味、時間足、Data品質、外部I/O境界は変更しない。

この推奨判断で問題がなければ、Step 1から順番に実行する。秒精度または旧画面の対象範囲を変更したい場合だけ、実装開始前にこの計画書を修正する。
