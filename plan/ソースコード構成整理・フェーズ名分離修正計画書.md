# ソースコード構成整理・フェーズ名分離修正計画書

作成日: 2026-08-23  
対象: 現行AutoTradeアプリの実行ソース、UI、起動設定、関連テスト  
目的: 現行プロダクトの実装からフェーズ名と`mock`という誤った配置名を取り除き、今後も同じ状態に戻らない構成にする。

## 1. 依頼内容

次の状態を実現する。

1. 現行プロダクトのソースコード内に、開発フェーズを表す`P5R`、`P5R2`、`phase5r`などの内部実装名を残さない。
2. 実Application APIへ接続するUIを`ui/mock`から、実アプリであることが分かる`ui/app`へ移す。
3. UI起動、API起動、Vite、Vitest、Playwright、品質確認設定の参照先を新しい配置へ揃える。
4. そのほかの現行実行ソースに、フェーズ名・履歴用の仮称・旧ディレクトリ名が残っていないかを再点検し、同じ種類の不整合を可能な範囲で同時に直す。
5. 変更後に、旧配置・旧内部名へ戻ることを自動検知できるテストを残す。

## 2. 棚卸し結果

### 2.1 現行プロダクト側で修正する対象

| 分類 | 現在の問題 | 修正方針 |
|---|---|---|
| UI配置 | `ui/mock`配下に実Application APIへ接続するReact UI、設定、テストがある | ディレクトリ全体を`ui/app`へ移し、package名・HTML title・READMEも実アプリ向けにする |
| UI内部名 | `P5R2WebProductScreen`、`P5RBacktestScreen`、`p5r2Api`、`p5r2-*`のCSS・test id・内部変数がある | `BacktestProductScreen`、`LegacyBacktestScreen`、`backtestProductApi`、`backtest-product-*`等へ改名する |
| UI表示 | 「P5R2 Web Product」「P5R旧履歴」など、運用者にフェーズ名を見せている | 「Backtest Web画面」「旧Backtest履歴」など、機能名に置き換える |
| API境界 | `/api/p5r2`、`p5r2_preflight`、`P5R-APPLICATION-API-V1`など、現行APIの実装名にフェーズ名がある | ローカルの現行UI・サーバー・テストを同時更新し、`/api/backtest-product`、`backtest_product_preflight`、`BACKTEST-PRODUCT-APPLICATION-API-V1`等へ移す |
| API起動ソース | `scripts/phase5r`に現行のローカルAPIサーバーがある | `scripts/application_server`へ移し、`backtest_api_server.py`等のファイル名も役割名へ整理する |
| ストレージ境界 | `storage_paths.py`が特定フェーズ名を禁止判定に直接埋め込んでいる | 許可されたアプリ領域を列挙する構造へ変え、フェーズ名を判定ロジックから除く |
| 起動・品質設定 | `start_autotrade.ps1`、`stop_autotrade.ps1`、quality gate、Playwright設定などが旧UI/APIパスを参照している | 参照先を一括更新し、旧パスが残っていないことを検査する |

### 2.2 残す対象と理由

次は現行プロダクトの内部実装名ではなく、過去の実行結果・承認・証跡・互換性を識別する固定情報であるため、今回の改名対象から除外する。

- `doc/phase*`、`plan/phase*`、`tests/evidence/phase*`の履歴・証跡パス。
- `RUN-P5R2-*`、`P5R2-19`など、既に取得済みの証跡を一意に指すRun ID、承認ID、手順書の証拠リンク。
- 過去仕様との互換性を持つ永続データのschema/version値。変更する場合は別途マイグレーション計画が必要である。
- Phase 1〜5の凍結済みテストや旧品質ゲートの識別子。現行アプリの実行経路を参照する箇所だけは新パスへ修正する。

上記は「フェーズ名を実装へ新たに持ち込む」こととは別の、既存記録を壊さないための固定識別子である。除外理由を明示したうえで、現行実装と履歴を混同しない。

## 3. 目標構成

```text
ui/
└─ app/
   ├─ src/                  # 現行Reactアプリ
   ├─ tests/                # 現行UIのPlaywrightテスト
   ├─ package.json          # name: autotrade-ui
   └─ playwright*.config.ts

scripts/
└─ application_server/
   ├─ application_api_server.py
   └─ web_product_fixture_server.py
```

現行UIと現行APIの機能は変えない。今回の主目的は、配置・命名・参照の是正である。API URLを変更するため、同一リポジトリ内のクライアント、サーバー、テストを同じ変更単位で更新する。

## 4. 実行ステップと、そのまま実行できるプロンプト

以下のプロンプトを上から順番に1つずつ実行する。各ステップの終了条件を満たしたら、対象ファイルだけを確認してコミット・プッシュする。既存の未コミット変更は混ぜない。

### Step 1: RED構造ガードを先に追加する

```text
この計画のStep 1を実行してください。

目的は、現行プロダクトのソース配置と命名を固定するためのREDテストを、実装変更より先に追加することです。TDDの順序を守ってください。

1. 既存の未コミット変更を変更・削除しない。
2. `tests/architecture/test_current_source_layout_contract.py`を追加する。
3. テストは、次を検査する。
   - `ui/app`が現行UIのルートであること。
   - `ui/mock`が現行UIのルートとして存在しないこと。
   - `scripts/application_server`が現行ローカルAPI起動ソースのルートであること。
   - 現行実行ソース（`src/autotrade/application`、`ui/app/src`、`scripts/application_server`、`scripts/start_autotrade.ps1`、`scripts/stop_autotrade.ps1`）に、`p5r`、`p5r2`、`phase5r`、`ui/mock`がファイル名・ディレクトリ名・内容として残っていないこと。
   - UI packageのnameが`autotrade-ui`であること。
   - UIのAPIクライアントとHTTPサーバーが`/api/backtest-product`という機能名の境界を使用すること。
4. 既存の履歴・証跡ディレクトリ、固定Run ID、既存の品質ゲート定義はこのテストの検査対象から除外する。
5. 新規テストだけを実行し、想定どおりREDになることを確認する。まだ本体ソースは直さない。
6. `git diff --check`と`git status --short`を確認し、新規テストだけをコミット・プッシュする。

報告には、REDになった検査項目、変更ファイル、コミット、プッシュ先を記載してください。
```

### Step 2: UIと現行API起動ソースを機能名の配置へ移す

```text
この計画のStep 2を実行してください。Step 1のREDテストが存在することを確認してから進めてください。

1. `ui/mock`を`ui/app`へ、`scripts/phase5r`を`scripts/application_server`へ、リポジトリ内で追跡可能な改名として移す。移動先が既に存在する場合は上書きせず停止する。
2. 現行API起動ファイルを、役割が分かる中立名へ改名する。
   - `backtest_api_server.py` → `application_api_server.py`
   - `p5r2_web_product_api_server.py` → `web_product_fixture_server.py`
3. UIの`package.json`と`package-lock.json`のpackage名を`autotrade-ui`へ変更し、`index.html`のtitle、UI READMEの説明も実アプリ向けに直す。
4. `start_autotrade.ps1`、`stop_autotrade.ps1`、UIのVite/Vitest/Playwright設定、現行のテスト起動設定を新しいパスへ更新する。
5. 既存のPlaywrightの証跡出力先、固定Run ID、履歴・証跡パスは変更しない。
6. Step 1の新規構造ガードを実行する。この時点で、配置・旧パス検査が通り、内部識別子検査だけが残る状態にする。
7. UIの`npm run build`を実行し、パス移動だけで壊れていないことを確認する。
8. `git diff --check`を確認し、Step 2の移動・設定変更だけをコミット・プッシュする。

報告には、移動したルート、更新した起動設定、build結果、コミット、プッシュ先を記載してください。
```

### Step 3: Python側の現行Application APIからフェーズ名を除く

```text
この計画のStep 3を実行してください。Step 2の移動後のパスを正本にしてください。

1. `src/autotrade/application`の現行Web Product経路を対象に、`p5r2`、`p5r`、`phase5r`を内部実装名・関数名・コメント・docstring・現行API契約名として使用している箇所を洗い出す。
2. 次のように機能名へ改名する。
   - `p5r2_preflight` → `backtest_product_preflight`
   - `_p5r2_generation_job_view` → `_generation_job_view`
   - `/api/p5r2/...` → `/api/backtest-product/...`
   - `P5R-APPLICATION-API-V1` → `BACKTEST-PRODUCT-APPLICATION-API-V1`
   - `P5R-*`の現行Run provenance/version文字列 → `BACKTEST-PRODUCT-*`
   - P5R2を説明するコメント・docstring → Backtest Productまたは時間足生成などの機能説明
3. `storage_paths.py`の禁止判定は、特定フェーズ文字列を含むかどうかではなく、アプリが許可する相対トップレベル領域（historical、backtest、logsなど）を検査する方式へ変更する。E:配下限定、reparse point拒否、親 traversal拒否は維持する。
4. Pythonテスト、現行UIサーバー、直接呼び出し側の参照を同じ変更単位で更新する。取得済み証跡ファイルの中身は書き換えない。
5. `p5r2`、`p5r`、`phase5r`を対象にした現行Pythonソースの検索結果が0件になることを確認する。固定IDや`tests/evidence`への参照は除外し、除外理由を確認する。
6. 関連pytest、`python -m compileall src scripts/application_server`、`git diff --check`を実行する。
7. Step 1の構造ガードを実行し、Python側の検査がGREENになることを確認してコミット・プッシュする。

報告には、API境界の変更、ストレージ境界を同等以上に保った根拠、テスト結果、コミット、プッシュ先を記載してください。
```

### Step 4: React UIの内部名・表示名・テスト識別子を機能名へ揃える

```text
この計画のStep 4を実行してください。Step 3で確定した`/api/backtest-product`境界を使ってください。

1. UI実装のファイル名、export名、import、型名、内部変数、CSS class、data-testid、aria label、画面表示から、実装上不要なP5R/P5R2名を除く。
2. 次の中立名へ整理する。
   - `P5R2WebProductScreen.tsx` → `BacktestProductScreen.tsx`
   - `P5RBacktestScreen.tsx` → `LegacyBacktestScreen.tsx`
   - `p5r2Api.ts` → `backtestProductApi.ts`
   - `P5R2WebProductScreen` → `BacktestProductScreen`
   - `P5RBacktestScreen` → `LegacyBacktestScreen`
   - `p5r2-*` → `backtest-product-*`
   - `p5r-*` → `legacy-backtest-*`
3. 「P5R2 Web Product」「P5R旧履歴」などの運用者向け表示を、機能名（Backtest Web画面、旧Backtest履歴など）へ置き換える。
4. UI単体テストとPlaywrightテストのimport、selector、テスト名を更新する。既存の証跡出力先と固定Run IDを指す文字列は、証跡の参照を壊さないため必要な箇所だけ残す。
5. UI packageの`npm run lint`、`npm run test`、`npm run build`を実行する。
6. PlaywrightはローカルAPIを使う既存の範囲から、少なくとも現行Backtest画面のsmokeを実行する。外部Data取得、ログイン、Secret、費用発生を伴う操作は実行しない。
7. Step 1の構造ガードを再実行し、UI側もGREENにする。`ui/app/src`の現行実装検索でフェーズ名が0件であることを確認する。
8. `git diff --check`を確認し、Step 4のUI変更だけをコミット・プッシュする。

報告には、改名一覧、表示文言の変更、unit/build/Playwright結果、コミット、プッシュ先を記載してください。
```

### Step 5: 全現行実行経路の残存参照を監査し、最終修正する

```text
この計画のStep 5を実行してください。ここで現行ソースの監査と最終修正を完了させます。

1. 次の対象を`rg`または同等の高速検索で確認する。
   - `src/autotrade`
   - `ui/app`
   - `scripts/application_server`
   - `scripts/start_autotrade.ps1`
   - `scripts/stop_autotrade.ps1`
   - 現行品質ゲートが参照するUI/API起動設定
2. `ui/mock`、`scripts/phase5r`、旧API起動ファイル名、`p5r`、`p5r2`、`phase5r`の残存を検索する。
3. 見つかったものを次の3種類に分類する。
   - 現行実装・起動設定の誤った参照: 必ず修正する。
   - 既存証跡・Run ID・承認ID・永続互換性の固定値: 書き換えず、現行ソースからの参照方法だけを確認する。
   - 旧品質ゲートの履歴専用コード: 現行起動経路を壊さない範囲で、参照先だけを修正する。改名で証跡が壊れる場合は改名しない。
4. UIの`mock`というpackage名、title、説明、テスト出力名など、単なるテンプレート残りも修正する。
5. Step 1の構造ガード、Python関連pytest、UI lint/test/build、必要なPlaywright smokeを再実行する。
6. `git status --short`で今回の変更だけを確認し、差分・Secret・意図しない履歴/証跡変更がないことを確認する。
7. 全検証が通ったら、最終コミット・プッシュを行う。失敗した場合は修正を続け、未解決のまま完了扱いにしない。

最終報告には、現行ソースから除去したもの、意図的に残した固定識別子と理由、検証結果、ブランチ、コミット、プッシュ先を記載してください。
```

## 5. 検証・受入条件

### 必須

- 現行UIの正本が`ui/app`であり、`ui/mock`が現行実行経路に存在しない。
- 現行API起動ソースの正本が`scripts/application_server`であり、`scripts/phase5r`が現行実行経路に存在しない。
- 現行UIとPython Application APIの内部実装名・関数名・現行APIパス・画面表示にP5R/P5R2のフェーズ名が残っていない。
- 既存のBacktest機能、時間足生成、Catalog、Run一覧、結果表示、取消・削除、日時入力の動作が変わっていない。
- 旧証跡、承認ID、Run ID、手順書の証拠リンクを改変していない。
- UIのlint、unit、build、および現行ローカルAPIを使うsmokeが成功する。
- Python側の関連pytestとcompile確認が成功する。
- 今後旧配置・旧内部名へ戻す変更を検知する構造ガードがGREENになる。

### 不合格条件

- 旧パスを残したまま新パスを追加するだけの二重配置。
- 旧APIパスを黙って互換維持するために、現行ソースへフェーズ名を残すこと。
- 既存証跡のJSON・画像・承認ファイルを改名・上書きすること。
- 外部Provider接続、Secret利用、ログイン、費用発生、外部Data downloadを伴う検証。
- 既存の未コミット変更を今回のコミットへ混ぜること。

## 6. 完了時の扱い

全Step完了後、現行プロダクトのソース配置と命名が機能名中心に統一され、UIが`mock`として扱われない状態を完了とする。フェーズ名を含む履歴・証跡が残ることは不具合ではなく、過去の事実を保持するための設計上の例外として最終報告に明記する。
