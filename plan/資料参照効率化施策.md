大量のドキュメント（md, html）を抱えるフルAIエージェント開発において、「トークン消費の削減（コスト・コンテキスト汚染防止）」**と**「高速・正確な参照導線（検索精度の向上）」**を両立させるアプローチは、2026年現在のAI開発において**「コンテキスト・エンジニアリング（Context Engineering）」における最重要テーマの一つです。

従来の「全ドキュメントをベクターDBに放り込んで単にRAG（ベクトル検索）をかける」手法では、チャンクの分断による誤参照や不要なトークン消費が発生しがちです。

現在（2026年時点）の実務でベストプラクティスとされている**3層構造の階層型ルーティング設計**および**導入すべきツール／手法**を解説します。

## 2026年のベストプラクティス：3層階層型ドキュメント・ルーティング

全ドキュメントを常時コンテキストに載せるのではなく、「メタデータ層（マッピング） ➔ リレーショナル層（依存関係） ➔ 実データ層（JIT取得）」の3段階で参照を制御します。

```
[ ユーザー/タスクの入力 ]
        ↓
  ① ルーティング層 (Manifest / Router LLM)
     「このタスクに必要なドキュメントのID/パスを特定」
        ↓
  ② グラフ/依存関係解決 (Graph / Context Map)
     「関連する前提ドキュメントや補足資料を追加」
        ↓
  ③ JIT（Just-In-Time）ドキュメント取得 (MCP Server)
     「必要な1〜3件のドキュメント本文のみをコンテキストに注入」
        ↓
[ メインAIエージェントによる実行 ]

```

## 具体的な構築・改善ステップ

### 1. マニフェスト（`context_map.json`）の自動生成と常駐

全ドキュメントの本文を読ませるのではなく、各ドキュメントの「概要」「参照すべき場面」「キーワード」だけをまとめた軽量なマッピング情報（マニフェスト）を作成します。

* **実装手法**: CI/CDパイプライン（GitHub Actionsなど）でドキュメントが更新された際、軽量モデル（GPT-4o-miniやClaude Haiku等）を回して以下のようなメタデータを自動抽出し、単一の軽量JSON（または`ROUTER.md`）に集約します。

```json
[
  {
    "doc_id": "auth-jwt-setup",
    "path": "docs/auth/jwt_implementation.md",
    "summary": "JWT認証のセットアップ、トークン発行・検証手順、エラーハンドリング",
    "triggers": ["ログイン機能の実装", "トークンエラー", "認証ミドルウェア"],
    "related_docs": ["auth-oauth-google", "security-policy"]
  }
]

```

### 2. Router Sub-Agent（または軽量分類器）の配置

メインの高性能モデル（Claude Opus / GPT-4oなど）を実行する前に、**軽量・高速なルーターエージェント**または関数を挟みます。

* ルーターは`context_map.json`のみを参照し、「ユーザーの入力（タスク）に対して参照すべき`doc_id`」を1〜3件選定してパスだけを返します。
* これにより、メインモデルのシステムプロンプトに無駄なドキュメント全文が載るのを完全に防ぎます。

### 3. Model Context Protocol (MCP) によるオンデマンド取得

2026年現在のAIエージェント構築においては、ツール連携の標準プロトコルである **MCP（Model Context Protocol）** を用いてドキュメント検索・取得ツールを構築するのが定石です。

* **`search_docs_index`**: キーワードや意図からドキュメントのメタデータを検索
* **`fetch_doc_content`**: 指定された`path`の本文のみを取得

メインエージェントが必要になったタイミングでMCPツールを実行して本文を取得（Just-In-Timeインジェクション）させることで、トークンを大幅に節約できます。

## おすすめの運用フローまとめ

1. **CI/CDでの自動マッピング**: ドキュメントリポジトリの更新時に、各ファイルのSummaryとTrigger条件を`context_map.json`に自動更新する。
2. **MCPサーバー化**: ドキュメント取得用のMCPサーバーを立て、エージェントには`search_map`と`get_doc`の2つのツールを与える。
3. **ルーターによる絞り込み**: エージェントの最初のステップで「どのドキュメントを見るべきか」を`context_map`から判断させ、選択されたドキュメント本文のみをロードしてタスクを実行する。

この構成をとることで、全体のトークン消費量を**70%〜90%削減**しつつ、誤ったドキュメントの参照（ハルシネーション）を激減させることが可能です。


[ちなみに上記施策は、ソースコードに対しても適用可能？]


**はい、完全に適用可能です。** むしろ、ソースコードに対してこそより高い絶大な効果（トークン削減・検索精度向上）を発揮します。

自然言語のドキュメントと異なり、ソースコードは構造化（関数・クラス・依存関係）されているため、マッピングや階層型ルーティングとの相性が極めて抜群です。

ソースコードに適用する際の、2026年現在のベストプラクティスと具体的なやり方を解説します。

## ソースコードに適用する際の2つの方針

ドキュメントの「概要（Summary）」にあたる部分を、コードでは「シグネチャ・インターフェース情報」に置き換えて管理します。

```
[ タスク/バグ修正依頼 ]
        ↓
  ① コード・マニフェスト層 (Code Map / AST / Ctags)
     「関係しそうなファイルと、その中の関数名・型定義だけを把握」
        ↓
  ② 依存関係グラフ (Dependency Graph / Call Graph)
     「その関数が呼び出している/呼び出されている関連ファイルを特定」
        ↓
  ③ JIT（Just-In-Time）コード取得
     「該当の関数（またはファイル単位）の実装本文（ロジック）のみをコンテキストに読み込む」

```

## 実装・運用の具体的なアプローチ

### 1. 「スケルトン（型・シグネチャ）」の抽出とマッピング

ファイル全体のコード（実装詳細）を読ませるのではなく、**「どのファイルにどんなクラス/関数があるか」だけを定義した軽量マップ**を作成します。

* **手法**: `AST (Abstract Syntax Tree)` 解析や `ctags` / `tree-sitter` を用いて、実装ロジックを除外した「関数の定義・型・JSDoc/Docstring」のみを自動抽出します。

**例：軽量コードマップ（`code_manifest.json`）**

```json
[
  {
    "file": "src/services/payment.ts",
    "summary": "決済処理、Stripe API連携、返金処理",
    "exports": [
      "class PaymentService",
      "processPayment(orderId: string, amount: number): Promise<PaymentResult>",
      "refundOrder(orderId: string): Promise<boolean>"
    ],
    "dependencies": ["src/models/order.ts", "src/utils/stripe.ts"]
  }
]

```

### 2. コード構造特化型のサードパーティ製ツールの利用

ソースコードの依存関係や構造をコンテキスト化するために、以下のツールが標準的に活用されています。

| ツール / ライブラリ | 役割・メリット |
| --- | --- |
| **Aider / `repomap**` | `tree-sitter` を利用してリポジトリ全体の関数のシグネチャ・呼び出し関係を自動でグラフ化し、トークン上限に収まるように最適化された「コードマップ」を出力する標準手法。 |
| **tree-sitter** | 多言語対応の構文解析パーサー。関数の実装部分（Body）を削り、宣言部分だけを残した軽量版ファイルを自動生成するのに最適。 |
| **GraphRAG / Code Property Graph (CPG)** | コードの呼び出し関係（Call Graph）やデータフローをグラフ化。関数の修正時に「影響を受ける別ファイル」を正確にルーティングできます。 |

## ドキュメントとコードで異なる注意点

1. **実装の詳細は必要な時だけ読み込む（JIT読み込み）**
* **NG**: 「決済機能を直して」と言われて、関連する10ファイルをすべてフルロードする。
* **OK**: まず `repomap`（シグネチャ一覧）を見て `src/services/payment.ts` の `processPayment` 関数が怪しいと特定 ➔ **その関数の行数（L10-L45）だけをピンポイントで取得する**。


2. **型定義（TypeScript/Go等）を最優先ルーティングに載せる**
* コードのロジックを読む前に、型定義ファイル（`types.ts` や `interfaces/`）だけを読み込ませると、エージェントは全体のアーキテクチャを誤解せずに最小トークンで理解できます。

## 結論

ドキュメント構築で導入した「マニフェスト（マップ）＋MCPによるオンデマンド読み込み」の仕組みは、ソースコード検索（Code Search / Navigation）においてもそのまま流用できます。

ドキュメント用マップとコード用マップ（`repomap`等）を両方持たせておくことで、**「まず仕様ドキュメントで該当機能を特定 ➔ コードマップから該当ファイルを特定 ➔ ピンポイントでコード取得」** という完璧な高速導線が完成します。
