# バックテストデータ取得・運用および戦略検証 全会話記録

---

## Q1. バックテスト用のヒストリカルデータを入手するベストプラクティスを教えて。出来れば安価な手段が良い

### A1.

バックテスト用のヒストリカルデータを安価（または無料）に入手するためのベストプラクティスを、**「資産クラス別のデータソース」「データ管理手法」「バイアス対策」**に分けて解説します。

---

### 1. 資産クラス別：おすすめデータソース（無料〜低価格）

目的の資産クラスと取得したい時間足（日足 / 分足 / ティック）に応じて最適なソースを選択します。

#### ① 日本株
* **J-Quants API（JPX公式）**【推奨】
  * **特徴:** 日本取引所グループ公式のAPI。過去の株価、財務データ、銘柄情報が取得可能。
  * **コスト:** Freeプランあり（過去データを一部制限付きで利用可）。有料プラン（Light等）も月額数千円程度と個人向けに非常にリーズナブル。
  * **メリット:** 公式データのため信頼性が非常に高く、株式分割などの権利落ち調整も扱いやすい。
* **yfinance (Pythonライブラリ)**
  * **特徴:** Yahoo! Financeからデータをスクレイピング/抽出するライブラリ。
  * **コスト:** 無料
  * **注意点:** 公式APIではないため非推奨になるリスクがあり、データ欠損や調整誤差が含まれる場合があるためプロトタイプ（PoC）向き。

#### ② 米国株・海外ETF
* **Polygon.io**【推奨】
  * **特徴:** 開発者フレンドリーで高品質なAPI。
  * **コスト:** 無料枠あり（過去5年分のデータ、リクエスト制限あり）。Starter/Developerプランも手頃。
* **Alpha Vantage / Tiingo**
  * **特徴:** 日足〜 intraday（分足）まで幅広くカバーする定番金融API。
  * **コスト:** 無料枠あり（1分あたりのリクエスト数制限あり）。
* **yfinance**
  * **特徴:** 米国株の日足・週足などをサクッと手に入れるには最も手軽。

#### ③ FX（外国為替）
* **Dukascopy（デュカスコピー）データ**【推奨】
  * **特徴:** スイスのFX銀行が提供しているヒストリカルデータ。Tickデータや1分足データが**完全無料**で取得可能。
  * **入手方法:** Pythonライブラリ（`nseta`や`dukascopy-node`など）や、無料のダウンロードツール（Tickstoryの無料版、QuantDataManagerなど）経由でダウンロード。
* **FX会社公式データ（Axiory / FXDD等）**
  * **特徴:** MetaTrader (MT4/MT5) 用のヒストリカルデータ（HST形式やCSV）を公式サイトで無料配布している。

#### ④ 暗号資産（Crypto）
* **Binance Data Vision**【推奨】
  * **特徴:** Binanceが過去の全取引（Tickデータ）やK線（ローソク足）の全データをパブリックS3バケットで無償公開している。
  * **コスト:** 完全無料（APIキー不要で直接zipダウンロード可能）。
* **CCXT (Python Library)**
  * **特徴:** 主要な暗号資産取引所のAPIを統一インターフェースで叩けるライブラリ。過去のOHLCVデータを取得可能。

### 2. データの取得・保存・管理のベストプラクティス

大量の過去データを効率よく扱うためのシステム構成・データ形式のプラクティスです。

#### CSVではなく「Parquet」や「DuckDB」を採用する
* **CSVのデメリット:** 容量が大きく、Python（Pandas）等での読み込み速度が極めて遅い。
* **Parquet / Feather:** 圧縮率が高く、PandasやPolarsとの相性が抜群に良い列指向フォーマット。
* **DuckDB / SQLite:** ローカルでSQLを用いて超高速にフィルタリング・結合を行いたい場合に最適。

#### データ構造の整理
ストレージ保存時は以下のようにディレクトリ階層またはパーティションを分けると管理が容易になります。
```text
data/
  ├── raw/                  # 取得した生のデータ（書き換え不可）
  │     ├── japan_stocks/
  │     └── fx_dukascopy/
  └── processed/            # 前処理済み（調整後株価・欠損補正済み）
        └── daily_ohlcv.parquet
```

### 3. バックテストで陥りがちなデータ注意点

安価なデータを使用する際、バックテスト結果を歪めないために以下の補正・考慮が必要です。

1. **株式分割・配当の調整（Adjusted Price）**
   * 分割・併合の履歴が反映されていない生データを使うと、チャートに巨大なギャップが生じ、誤った売買シグナルが出ます。調整後株価（Adjusted Close）を使用するか、分割履歴データ（Corporate Actions）を用いて自前で補正する必要があります。
2. **サバイバーシップ・バイアス（生存者バイアス）**
   * 「現在の構成銘柄」だけで過去10年分を検証すると、倒産・上場廃止になった企業が除外され、パフォーマンスが過大評価されます。厳密な検証をする場合は、過去時点で存在していた全銘柄を含める必要があります。
3. **スプレッドとスリッページ**
   * 特にFXや暗号資産の1分足以下・Tickバックテストでは、固定スプレッドではなく「時間帯やボラティリティに応じた可変スプレッド・スリッページ」をバックテストコード側でシミュレートすることが重要です。

### 4. 段階別おすすめロードマップ

* **Step 1（アイデア検証・PoC）**
  * **日本株:** J-Quants（Free）または `yfinance`
  * **FX / Crypto:** Dukascopy（無料Tick/1分足）/ Binance Vision
  * **ライブラリ:** Python + `pandas` + `backtesting.py` または `vectorbt`
* **Step 2（精度向上・本格バックテスト）**
  * **日本株:** J-Quants Light/Standardプランで財務・調整後データを取得
  * **FX:** Tickstory / Tick Data Suite（TDS）などで変動スプレッド付き高品質Tickデータを導入
  * **データ管理:** Local Parquet / DuckDB で高速読み込み環境を構築

## Q2. では、本格的なユーザの入手先のベストプラクティスは？

### A2.

「本格的（プロクオンツ・ヘッジファンド・専業アルゴトレーダー）」な水準でのヒストリカルデータ入手および運用のベストプラクティスは、単に「価格データを落としてくる」ことではなく、**「バイアスを完全に排除した高品質なデータパイプラインを構築すること」**にあります。

---

### 1. 本格派クオンツが選ぶ高品質データベンダー

用途（時間足・資産クラス）に応じて、業界標準となっているプロ仕様のデータベンダーを選定します。

#### ① Tick〜分足（高頻度・Intradayトレード向け）
* **Databento**【現在最も人気のある現代的クオンツ向けAPI】
  * **特徴:** CME、NASDAQ、NYSEなどの生データ（MBO: Market-by-Order、L2/L3オーダーブック）をナノ秒単位のタイムスタンプで提供。APIが極めて洗練されており、Python/Rust/C++等で高速取得可能。
  * **コスト:** 従量課金制（データ量に応じた課金）のため、数千ドル/月かかる伝統的ベンダーに比べて初期コストを抑えて機関級データが手に入る。
* **AlgoSeek / Theta Data**
  * **特徴:** 米国株・オプションのTick/Intradayデータで非常に高い評価。オプションのGreaks（デルタ・ガンマ等）の過去履歴やヒストリカル気配値（Quotes）の精度が高い。
* **LSEG Tick History（旧 Thomson Reuters Tick History）**
  * **特徴:** 機関投資家・ヘッジファンドのデファクトスタンダード。全世界の全銘柄のTickデータを数十年にわたり網羅。ただし年間数百万円〜のエンタープライズ契約が必要。

#### ② 日足・ファンダメンタルズ（中長期・スイング・ファクター投資向け）
* **Norgate Data**【日足クオンツのベストプラクティス】
  * **特徴:** 米国株・先物などの日足データ。最大の強みは**生存者バイアス（Survivorship Bias）の完全排除**（過去に上場廃止・倒産・買収された全銘柄を網羅）と、**ティッカー変更・株式分割・配当の厳密な追跡**。Python/Rとの連携も容易。
* **FactSet / S&P Capital IQ / CRSP**
  * **特徴:** 学術研究や大手クオンツファンドで使われる「Point-in-Time（時点確定）」財務データ・株価データ。

#### ③ 暗号資産（Crypto）
* **CoinMetrics / Kaiko**
  * **特徴:** 主要CEX（Binance, Coinbase等）およびDEXの板情報、Tickデータ、ならびにオンチェーン指標を統合した機関投資家向けデータプラットフォーム。

---

### 2. 本格運用におけるデータパイプラインのアーキテクチャ

大量のTick/分足データをバックテストで高速に回すため、適切なデータエンジニアリングが必須です。

```text
[ Data Provider (Databento / Norgate) ]
                  │ (API / Batch Fetch)
                  ▼
[ Raw Layer ] ── Storage: S3 / GCS (Compressed Parquet Files)
                  │ (Pre-processing / Cleaning)
                  ▼
[ Analytics Layer ] ── DB: ClickHouse / DuckDB / TimescaleDB
                  │ (Fast Querying & Feature Engineering)
                  ▼
[ Backtest Engine ] ── Python (Polars / VectorBT / Custom C++)
```

1. **形式は「Parquet」か「ClickHouse」の一択**
   * **Parquet:** 列指向・高圧縮なファイルフォーマット。S3などに保管し、Pythonの **Polars** や **DuckDB** を使って数億行のTickデータを数秒でオンメモリ処理します。
   * **ClickHouse:** 超高速なオープンソース列指向DB。Tickデータや分足データを高速に集約・タイムシリーズ分析する際、業界で最も採用されているDBです。
2. **生データ（Raw）の不変性（Immutability）**
   * ベンダーから取得したデータは加工せずそのまま「Raw Layer」として保管し、前処理（権利落ち補正や指標計算）は別レイヤーでパイプライン化して生成します。

### 3. バックテストの信頼性を担保する「3大バイアス対策」

本格的なバックテストで最も警戒すべきは、**「バックテストでは勝てるのに実運用で負ける（Overfitting / Bias）」** 現象です。データ設計で以下の3点を厳格に処理します。

#### ① Survivorship Bias (生存者バイアス) の排除
現在上場している銘柄だけで過去10年のスクリーニングを行うと、倒産・上場廃止した企業が抜け落ち、パフォーマンスが大幅に底上げされてしまいます。
* **対策:** Norgate DataやCRSPなど、**「過去の特定の時点で存在していた全銘柄（上場廃止株含む）」**のユニバースを保持できるデータソースを使用する。

#### ② Point-in-Time Data (時点確定データ) の徹底
決算数値や経済指標は「対象期間の終了日」ではなく「実際に公表された日時」にデータが利用可能になります。また、後日数値が修正（Revision）されることもあります。
* **対策:** 「決算発表日」「修正履歴」のタイムスタンプが保持されたPoint-in-Time形式のファンダメンタルデータを使用し、発表前の未来の数値をバックテストで参照する「ルックアヘッド・バイアス」を完全に防ぎます。

#### ③ Dynamic Universe Definition (動的ユニバース定義)
「S&P 500構成銘柄」でバックテストを行う場合、現在のS&P 500銘柄を過去に適用してはいけません（10年前は構成銘柄が異なります）。
* **対策:** 日次または月次で「その時点でS&P 500に組み込まれていた銘柄」のリストを復元して検証対象を動的に切り替えます。

---

### まとめ：何から始めるべきか？

* **Intraday / 高頻度・アルゴリズム検証:** **Databento** を契約し、従量課金で関心のある銘柄のTick/L2データを取得。Polars + DuckDB でデータ基盤を組む。
* **日足 / システムトレード・ファクター投資:** **Norgate Data** を導入し、生存者バイアスフリーな環境でPythonを用いて検証する。

## Q3. 対象にしたい時間足は15分足〜日足の範囲です。この場合のベストプラクティスは？

### A3.

15分足〜日足（Intraday〜スイングトレード領域）に特化する場合、高頻度取引（HFT）のようなナノ秒単位のTickデータや巨大なL2/L3オーダーブックは不要なため、**「データコストを抑えつつ、サバイバーシップ・バイアスや権利落ち（調整後株価）の補正が完璧になされたデータパイプラインを組むこと」**がベストプラクティスになります。

市場（日本株・米国株・FX/Crypto）に応じた具体的なベストプラクティスを提案します。

---

### 1. 資産クラス別：15分足〜日足の最適データソース

#### ① 日本株（15分足〜日足）
* **ベストプラクティス:** **J-Quants API (JPX公式)**
  * **日足:** J-Quantsで完全に網羅できます。株式分割・併合、権利落ち調整後株価、ファンダメンタルズデータ（Point-in-Time）が公式精度で揃います。
  * **分足（15分足）:** J-Quantsのプラン（Premium等）で四半期・年単位の分足（OHLCV）データが取得可能です。
  * **強み:** 上場廃止銘柄のデータも保持されているため、生存者バイアスを完全に排除した日本株バックテスト環境が最も安価に構築できます。

#### ② 米国株・海外ETF（15分足〜日足）
* **日足のベストプラクティス:** **Norgate Data**
  * 日足クオンツ検証の絶対的デファクト。上場廃止株を含む完全なユニバース定義、SP500やNASDAQ100のヒストリカル構成銘柄切り替え、配当・分割の厳密な調整が自動化されています。
* **15分足のベストプラクティス:** **Polygon.io** または **Financial Modeling Prep (FMP)**
  * **Polygon.io:** 過去数年〜十数年分の15分足（Aggregate Bars）をREST API/Bulkダウンロードで高速取得可能。開発者体験が非常に高く、Pythonとの相性が抜群です。
  * **Tiingo / Alpha Vantage:** 予算を抑えたい場合の代替案（15分足・日足ともにAPIがシンプル）。

#### ③ FX（外国為替）
* **ベストプラクティス:** **Dukascopy データ（Tickから15分足を自作）**
  * **理由:** Dukascopyは1分足やTickデータが完全無料で取得できます。
  * **プラクティス:** 無料で取得できる1分足（1m OHLCV）をローカルに取り込み、Pandas/Polarsで**15分足へリサンプル（Resample）**して保存します。FX取引所の提供する15分足を生で落とすより、1分足から自作した方がタイムゾーン（UTC / EST / JST）やロールオーバー時刻の調整が自由自在になります。

#### ④ 暗号資産（Crypto）
* **ベストプラクティス:** **Binance Data Vision（無料全件） or CCXT**
  * Binanceが公開している過去の1分足/15分足の全期間Zipアーカイブ（Klineデータ）を直接ダウンロードし、Parquet化してローカルに保持します。コスト0で最高精度のデータが手に入ります。

---

### 2. データ構造・パイプラインのベストプラクティス

15分足〜日足データは、全銘柄・過去10年分を揃えても数GB〜数十GB程度に収まるため、極めて扱いやすいサイズ感です。

#### ① 1分足から15分足・日足をローカルで動的生成する
15分足データだけを個別に管理するのではなく、**「基底データとして1分足（または日足）をParquet形式で保持し、バックテスト実行時に15分足へリサンプルする」**パイプラインが最も柔軟です。

```text
[ Raw Data (1分足 Parquet) ] 
         │
         ├── (Pandas / Polars で Resample)
         ▼
  [ 15分足 OHLCV ] ────► [ バックテストエンジン ]
```

* **メリット:** 15分足だけでなく、「20分足」「1時間足」「4時間足」など、マルチタイムフレーム（複数時間足）を使った戦略検証へ即座に拡張できます。

#### ② 効率的なローカルデータ管理（Parquet + DuckDB）
* **ファイルフォーマット:** CSVではなく **Apache Parquet** を使用（圧縮率が非常に高く、読み込みがCSVの100倍以上高速）。
* **保存構造例:**
  ```text
  data/
    ├── us_stocks_1m/
    │     ├── AAPL.parquet
    │     ├── NVDA.parquet
    │     └── ...
    └── japan_stocks_daily/
          └── jquants_daily_2010_2026.parquet
  ```
* **クエリ処理:** Python環境から **DuckDB** または **Polars** を使用することで、数億行の15分足データから「特定の100銘柄の2020年〜2025年の15分足」を1秒未満で抽出できます。

---

### 3. 15分足〜日足のバックテストで注意すべき3つのポイント

1. **タイムゾーンと「足の確定タイミング（Look-ahead Bias）」の厳格化**
   * 15分足の場合、`09:00:00` の足は `09:00:00 〜 09:14:59` のデータを集計したものです。
   * **NG例:** `09:00` の足の終値（Close）を使って `09:00` 時点の発注処理を行う（未来の価格で発注してしまうルックアヘッド・バイアス）。
   * **OK例:** `09:00` の足の終値が確定するのは `09:15:00` なので、シミュレーション上のシグナル点灯・発注は **`09:15:00` の始値（Open）** で行うよう設計する。

2. **日またぎ・セッション境界の処理（Overnight Gap）**
   * 15分足では、前日終値から翌日始値への「窓開け（ギャップ）」が発生します。
   * イントラデイ限定戦略（デイトレ）の場合は、セッション終了時（例: 15:00や16:00）に強制決済するロジックをデータパイプライン上で正しく扱えるようにしておく必要があります。

3. **株式分割・併合の15分足への適用**
   * 日足であれば「調整後株価（Adjusted Close）」が最初から提供されますが、15分足などのIntradayデータでは未調整の生株価で提供されるベンダーもあります。
   * 分割（例: 1:10分割）があった日を境に15分足の価格が1/10に飛ぶため、分割履歴データ（Corporate Actions）を用いて過去の15分足データ全てに分割比率を掛け合わせる調整処理が必要です（Norgate DataやPolygon等を使うとこの問題が解消されます）。

---

### まとめ：15分足〜日足戦略の推奨構成

| 資産クラス | 推奨ベンダー / データ源 | 推奨ストレージ / フォーマット | バックテスト処理ライブラリ |
| :--- | :--- | :--- | :--- |
| **日本株** | J-Quants API | Parquet (年別/銘柄別) | Polars + vectorbt / backtesting.py |
| **米国株** | Norgate (日足) / Polygon (15分足) | Parquet | Polars + vectorbt / Custom Python |
| **FX** | Dukascopy (1分足を15分足化) | Parquet / DuckDB | vectorbt / Backtrader |
| **Crypto** | Binance Data Vision | Parquet | Polars + vectorbt |

## Q4. Cryptoでタートルズ戦略は利用できますか？

### A4.

結論から申し上げますと、**Crypto（暗号資産）市場においてタートルズ戦略（Turtles Trading System）は非常に相性が良く、極めて有効に機能する戦略の一つ**です。

タートルズ戦略は、リチャード・デニスらが開発した「ドンチャン・チャネル（Donchian Channel）」を用いた純粋な**ブレイクアウト型トレンドフォロー（順張り）システム**ですが、これがCrypto市場で特に機能する理由と、検証・運用する際の注意点を解説します。

---

### 1. なぜCrypto市場とタートルズ戦略は相性が良いのか？

#### ① 圧倒的なトレンドの長さとボラティリティ
タートルズ戦略のようなトレンドフォロー手法は、「レンジ相場での騙し（ダマシ）による小幅な損切り」を何度も繰り返しながら、「数ヶ月〜数年に1度訪れる巨大なトレンド」で一気に莫大な利益を上げる仕組みです。
* Crypto市場（BTCやETH、主要アルトコイン）は、伝統的金融（株やFX）に比べて**ボラティリティが圧倒的に高く、一度トレンドが発生すると数ヶ月〜半年以上一方向に伸び続ける傾向**が強いです。
* そのため、勝率自体は30〜40%程度と低くなりますが、プロフィットファクター（総利益÷総損失）やリスクリワード比が非常に高くなりやすい特徴があります。

#### ② ATR（True Range）に基づいたポジションサイジングが機能する
タートルズ戦略の核心は、エントリー条件そのものよりも**「ATR（Average True Range）を用いたリスク管理とポジション調整（N値）」**にあります。
* Cryptoは時期によってボラティリティが激変しますが、タートルズの「ボラティリティ（N）が大きい時はポジションサイズを小さくし、ボラティリティが小さい時は大きくする」ルールが、過度なロスカットを防ぎつつ資金管理を安定させます。

#### ③ 24時間365日取引（ギャップリスクが少ない）
株式市場などと異なり、Cryptoは市場が閉じないため「週末の窓開け（Overnight Gap）」による想定外のスリッページリスクが少ない点も、ブレイクアウト戦略には追い風となります。

### 2. Crypto用にチューニングすべきポイント（15分足〜日足）

オリジナルのタートルズ戦略は「日足（20日・55日ブレイクアウト）」を基準として設計されていますが、Crypto市場や15分足〜日足のタイムフレームに適用する場合は、以下のカスタマイズが効果的です。

#### ① 時間足の選定
* **日足 / 4時間足（推奨）:** 本来のタートルズの強みが最も発揮されます。騙しが少なく、大きな波（ビットコインの半減期サイクルやバブル相場）を完璧に捉えられます。
* **15分足 / 1時間足:** エントリー機会は増えますが、ノイズ（突発的な liquidation / 清算ラダーによるヒゲ）が多くなり、ダマシによる連敗（ドローダウン）が増加します。15分足で運用する場合は、**「フィルター（例: 200SMAより上の時だけロング等）」**を追加するのが一般的です。

#### ② 期間パラメータの最適化
* **オリジナル:** システム1（20日高値/安値ブレイク）、システム2（55日高値/安値ブレイク）
* **Crypto向け調整:** Cryptoは相場のサイクルが早いため、**「10日〜20日（短期）」「30日〜50日（中期）」**程度にパラメータを短縮して調整するアプローチもよく使われます。

#### ③ レバレッジと破産確率のコントロール
タートルズ戦略はピラミッディング（含み益が出たらポジションを段階的に増し建てする手法）を行いますが、Cryptoのボラティリティでハイレバレッジ＋増し建てを行うと、一瞬の逆行で即座に清算（強制ロスカット）されます。
* **バックテスト時のルール:** レバレッジは無制限にかけず、1回あたりのトレードリスク（許容損失）を**全資金の1%〜2%以内**に厳格に抑える設計が必須です。

### まとめ

タートルズ戦略は、Crypto市場（特にBTC, ETHなどの主要銘柄）で**「シンプルなロジックでありながら、長期的にプラスの期待値を持ちやすい代表例」**です。

まずは **Binanceの無料日足/4時間足データ（Parquet形式）** を使って、BTC/USDTなどで「20日ブレイク・10日手仕舞い」「ATRポジションサイジング」のバックテストを回してみることを強くおすすめします。
