## 3. 選定基準

UIモックは「一度見た目がきれい」だけでは不十分である。次の順番で選定する。

1. **再現できること**：同じ入力、同じSeed、同じ画面幅で同じ結果になる。
2. **状態を漏らさないこと**：通常だけでなく、読込中、空、警告、停止、失敗、復旧待ち、Human Gate待ち、未承認を確認できる。
3. **操作を確認できること**：クリック、入力、取消、削除、状態遷移を実ブラウザで確認できる。
4. **見た目を比較できること**：PC・スマートフォンの基準画像との差分を保存できる。
5. **操作しやすいこと**：キーボード操作、ラベル、フォーカス、表の見出し、色だけに頼らない説明を検査できる。
6. **外部依存を限定できること**：AIサービスへSecret、Broker情報、口座情報、実データを送らない。
7. **差分をレビューできること**：生成コードをリポジトリ内で読み、版、ライセンス、依存追加、変更理由を確認できる。

## 4. 外部調査結果と採否

### 4.1 Vercel v0（限定採用）

公式情報から、v0は自然言語でUIとコードを生成でき、Vercel上へデプロイできるAI開発支援サービスである。また、公式のDesign Systems説明では、shadcn/uiを既定のコンポーネントシステムとして扱い、独自RegistryをAIへ渡せる。

このプロジェクトでは、v0を「画面案を複数作るための外部デザイン補助」としてだけ使う。生成結果は次の手順を必須にする。

1. 要件ID、画面状態、禁止事項を含むプロンプトを作る。
2. v0へSecret、APIキー、口座情報、実Broker情報、未公開の実データを送らない。
3. 生成結果をローカルへ保存し、依存、ライセンス、外部通信、状態欠落を確認する。
4. shadcnのローカル部品と比較し、必要部分だけを手動で移植する。
5. Storybook、Playwright、axeで合格するまで本線へ引き渡さない。

v0のAPI利用や有料プランは、外部アカウント・費用・入力データの扱いを運用者が承認するまで行わない。

### 4.2 shadcn/ui CLI＋Registry（必須採用）

公式CLIには、Vite用の初期化、部品の閲覧、追加、独自Registryの利用、Registry APIが用意されている。部品をリポジトリへ取り込んでソースとして管理できるため、AI生成コードの出所と差分を確認しやすい。

ただし、shadcnの基礎部品はRadixまたはBase UIを選べる。公式の2026年1月の案内では新規プロジェクトにはBase UIを推奨している一方、既存調査書はRadixを前提としている。よって、初回導入では次の小規模比較をHuman Gateとする。

- Button、Dialog、Select、Tabs、Table、Toastを同じ画面で作る。
- PC幅とスマートフォン幅でキーボード操作、フォーカス、開閉、長い文字を確認する。
- `@storybook/addon-a11y`とPlaywrightで同じテストを実行する。
- Base UIとRadixの差を記録し、どちらか一方を正式な基礎部品として固定する。

### 4.3 Storybook＋Vitest＋axe（必須採用）

Storybookは部品を状態ごとのStoryとして並べる。公式のVitest addonはVite環境でStoryを実ブラウザのテストへ変換し、Playwright Chromiumを使った操作検証を行える。公式のAccessibility addonはaxe-coreを使い、Storyごとのアクセシビリティ違反を表示・失敗扱いにできる。

今回の採用範囲はローカル実行である。StorybookのVisual Testsをクラウドで行うChromaticは、外部送信と費用の確認後に再評価する。

### 4.4 Playwright（画面比較・E2E基盤）

Playwright公式の`toHaveScreenshot()`は、初回に基準画像を作り、次回以降に画面画像を比較できる。OS、ブラウザ、フォントなどで差が出るため、基準画像を作る環境を固定し、動的な日時・乱数・通信中表示をSeedやマスクで安定させる。

既に決めている「React画面をTypeScript版PlaywrightでE2E確認する」方針を、標準CLIと画面比較へ具体化する。次を必須にする。

- PC幅、スマートフォン幅、必要なら中間幅のviewport表。
- 各画面の通常・空・警告・停止・復旧・Human Gate待ちの基準画像。
- 重要操作のキーボード経路とフォーカス表示。
- 差分画像、テストログ、失敗時スクリーンショットの保存。

### 4.5 Faker.js（必須採用・開発専用）

Faker公式は、デモ、単体テスト、性能テスト、未完成バックエンドの代替データ作成を用途として示している。Seedを固定すれば同じデータを再現できるが、ライブラリ更新で同じSeedの結果が変わる可能性がある。また相対日付は基準日を固定しないと再現できない。

したがって、次を必須にする。

- `@faker-js/faker`のバージョンをlockfileで固定する。
- 画面ごとにSeedと固定基準日を記録する。
- 取引画面用の型付きFactoryを作り、実データ・Broker情報を混ぜない。
- 生成結果またはSeedをテスト証跡へ残す。
- ライブラリ更新時は基準画像と期待値を再確認する。

### 4.6 Figma MCP Server（保留）

Figma公式MCPは、Figmaのファイルから設計情報をAIへ渡し、コード生成やFigmaキャンバスへの書き戻しを支援する。Remote MCPが推奨されているが、現在はベータで、将来は従量課金になる予定と公式に記載されている。利用できるAIクライアントもカタログで制限される。

このプロジェクトでは、現時点の正本がHTMLとリポジトリであり、Figmaファイルがないため導入しない。将来Figmaをデザイン正本にする場合だけ、次の別判断を行う。

- Figmaを正本にするか、HTMLを正本にするかを決定する。
- Remote／Desktop MCP、アカウント、権限、費用、データ範囲を承認する。
- Code Connectで実際の部品とFigma部品を対応付ける。
- リポジトリとFigmaのどちらが変更を決めるかを明記する。

### 4.7 Playwright CLI（標準CLIは必須、AI向けCLIは限定採用）

Playwrightの公式CLIには、通常のテスト実行だけでなく、コード生成、ブラウザの導入、HTMLレポート表示、Trace表示、UIモードがある。公式ドキュメントの標準入口は、プロジェクトにインストールした版を`npx playwright`（または使用するパッケージマネージャの同等コマンド）で呼び出す方式である。

#### 4.7.1 標準CLI（必須採用）

このプロジェクトでは、`@playwright/test`をFrontendの開発用依存に固定し、次の用途に使う。

- `npx playwright test`：正式なE2E受入テストを実行する。
- `npx playwright codegen`：画面操作を記録し、テストのたたき台とLocatorを作る。生成コードは必ず人またはレビューAgentが確認する。
- `npx playwright show-report`、`npx playwright show-trace`：失敗時のHTMLレポートとTraceを確認し、証跡を保存する。
- `npx playwright install chromium`：固定したPlaywright版に対応するブラウザを導入する。ブラウザの取得は外部I/Oを伴うため、実行計画上の承認・版固定・hash記録の対象にする。
- `npx playwright test --ui`、`--debug`：開発時の画面確認に使う。正式な合否判定は通常の固定コマンドで再実行する。

採用理由は、既に方針決定済みの「React＋TypeScript画面をTypeScript版PlaywrightでE2E確認する」構成と一致し、画面比較、操作、レポート、Traceを同じローカル入口で統制できるためである。現在のリポジトリにはPlaywrightのFrontend実体と依存がまだないため、現時点で「導入済み」とは扱わない。

#### 4.7.2 AI向け`@playwright/cli`（限定採用）

Microsoft公式の`microsoft/playwright-cli`は、`playwright-cli open`、`snapshot`、`click`、`fill`、`screenshot`、セッション管理、画面ダッシュボードなどを備えた、コーディングAgent向けのCLIである。Node.js 18以上が必要で、公式パッケージのライセンスはApache-2.0である。AIへ大きな画面構造を毎回渡さず、簡潔なSnapshotを使って探索操作を行える点は、UIモックの操作漏れを探す補助として有用である。

ただし、次の理由から正式な受入テストの実行器にはしない。

1. 現時点のパッケージは0.1系であり、標準の`@playwright/test`に比べてプロジェクト内の正式テスト契約が少ない。
2. セッション、永続プロファイル、Storage Stateを扱えるため、実アカウントやSecretを誤って保存・再利用する危険がある。
3. Snapshotや対話操作の成功だけでは、要件ID、期待結果、画面差分、a11yの合否を固定できない。
4. グローバルインストールは版がリポジトリのlockfileから外れるため、まずローカル版の`npx playwright cli`を確認する。

したがって、`playwright-cli`は次の範囲で限定採用する。

- 固定モック画面の探索、操作漏れの発見、画面説明用のスクリーンショット取得。
- PC幅・スマートフォン幅の簡易確認、Trace・Console・Requestの調査。
- Agentが作った操作手順を、最終的には`@playwright/test`の固定テストへ移し替える。
- 実Broker、口座、Secret、実市場データ、外部サイトへの接続は禁止する。
- `--persistent`、`state-save`、Cookie保存は、匿名の固定モック以外では使わない。

この役割分担により、AI向けCLIは「探索と発見」、標準CLIは「再現可能なテストと正式証跡」とする。別途Playwright MCPを導入する必要は、現時点ではない。

## 7. 品質Gateと禁止事項

### 7.1 必須Gate

- 生成されたUIは、採用済み要件IDと画面状態IDへ追跡できる。
- 実Broker、口座、APIキー、Secret、実市場データを外部AIへ入力しない。
- v0等の外部生成物は、ローカルへ取り込む前に依存、ライセンス、外部通信、入力データを確認する。
- モックデータは固定Seed・固定基準日・固定版で再現できる。
- PC・スマートフォンのviewportで、通常・空・読込中・警告・停止・失敗・復旧待ち・Human Gate待ち・未承認を確認する。
- Storybook操作テスト、Playwright画像比較、axe検査、キーボード操作を全て記録する。
- 正式な受入コマンドはFrontendに固定したローカル版の`npx playwright`とし、実行前にNode・Playwright・ブラウザ版を記録する。
- `playwright-cli`の探索結果は補助Findingとして保存し、Playwright Testの期待値・画像・Traceへ移し替えたものだけを正式証跡とする。
- CriticalまたはHighのUI欠陥が残る場合は、要件定義HTMLやUIモックHTMLの正式版へ引き渡さない。
- 基準画像の更新は、意図した変更の理由、承認者、変更前後の画像、テスト結果を記録する。

### 7.2 禁止事項

- v0の生成結果をレビューせずに本線コードへ貼り付ける。
- AIに「見栄えよくして」とだけ指示し、状態・操作・停止条件を未定義のまま作る。
- 乱数・現在日時・外部API応答を固定せずに画像比較を合格扱いする。
- Storybookの通常状態だけを確認してUI品質を宣言する。
- axeが検出できない問題を、axe PASSだけで安全と宣言する。
- `npm install -g @playwright/cli@latest`を、版・許可範囲・証跡を確認せずに正式環境へ入れる。
- `playwright-cli --persistent`、`state-save`、Cookie・Storage保存へ、実アカウント、Secret、Broker、実市場データを渡す。
- `playwright-cli`のSnapshot、画面表示、操作成功だけで、要件受入・アクセシビリティ合格・画面差分合格と宣言する。
- Figma、v0、Chromaticの外部サービスを、費用・権限・データ範囲の承認なしに接続する。
