# RQV2-11 Phase 4以降再編ロードマップ HTML再作成プロンプト

## 0. このプロンプトの使い方

このファイル全体を、同じリポジトリを読み書きできるAIエージェントへ、そのまま渡して実行する。質問を返して停止せず、入力資料に書かれている事実だけを使って、指定されたHTMLを作成し、指定された索引を更新し、機械検証まで完了する。

この作業は、既存のPhaseを開始したり、実装したり、外部接続したりする作業ではない。Phase 4以降のロードマップを、初めて読む人でも「各Phaseで何を作るのか」「なぜその順番なのか」「どこで止まるのか」を確実に理解できる正式HTMLへ再構成する文書作成作業である。

---

## 1. あなたの役割と最終目的

あなたは、自動トレードシステムの計画文書を、技術者だけでなく、運用者、承認者、初めて読む人にも誤解なく伝わる正式HTMLへ変換する文書編集担当である。

最終目的は、次の一文を読者が迷わず説明できる状態を作ることである。

> Phase 4ではローカルで操作できるBacktest製品の土台を作る。Phase 5では市場Dataを実証する。Phase 6では実注文を出さずにPortfolio／Risk／OMSと停止・復旧を作る。Phase 7ではそれらが完成した後にBroker AdapterとPaperを検証する。Phase 8では長期Paperと運用の頑健性を確かめる。Phase 9では実資金なしでLive候補を審査する。Phase 10で初めて、承認された小さな範囲だけを実運用する。Phase 11で通常運用と段階拡大を行う。

この説明をHTMLの最初の画面で理解でき、各Phaseの詳細を読み進めれば、成果物、入力、依存、開始条件、禁止事項、完了条件、Evidence、次Phaseへの引渡しまで確認できるようにする。

使用するSkillは次の2つとする。

- `autotrade_skill_source_reader_v0_1`: 元資料、制約、Unknown、参照元を事実ベースで整理する。
- `autotrade_skill_html_doc_writer_v0_1`: 単体で読める日本語HTMLを作成し、`doc/index.html`から到達可能にする。

AI部品の新設・変更、Phaseの実装、外部調査、外部I/O、Secret投入、Broker接続、実注文、実資金の利用は行わない。

## 3. 作業前に作る事実整理表

HTMLを書き始める前に、内部作業用として次の事実整理を行う。内部作業用の表はHTMLへ必ずしもそのまま出さなくてよいが、HTMLの全内容はこの表と元資料を照合してから書く。

### 3.1 Phase事実表

Phase 4、5、6、7、8、9、10、11について、最低限、次の列を埋める。

| 列 | 内容 |
|---|---|
| Phase | 4〜11 |
| 正式名称 | 元資料の名称を維持 |
| 一言で作る物 | 専門用語を減らした一文 |
| 利用者ができること | そのPhaseが終わった時に利用者が操作・確認できること |
| 主な成果物 | 元資料の主成果物を漏れなく列挙 |
| 再利用する物 | Core、既存契約、既存Evidenceなど |
| 新しく設ける境界 | API、UI、Persistence、Risk、OMS、Adapterなど、元資料にある範囲 |
| このPhaseで作らない物 | 外部Data、Broker、Paper、Live、実資金、Cloudなど |
| 前に必要な物 | 依存Phase、承認、設計、RED、Evidence |
| 開始条件 | Gateと技術条件 |

### 3.2 変更してはいけない事実

次の事実は、読みやすく言い換えてよいが、意味を変えてはいけない。

- Phase間の順序は `RQV2-H3 → P4 → P5 → P6 → P7 → P8 → P9 → P10 → P11`。
- Broker／PaperはPortfolio／Risk／OMS・Kill・照合・復旧より前に置かない。
- Phase 4〜11の各Phaseは、開始前にそのPhase専用の複数Step実行計画書、詳細設計、品質Gate、Human Gateを必要とする。
- Phase 1〜3のPython Coreは原則凍結・再利用であり、固定Coreの合格を実市場、利益性、Broker、Paper、Liveの合格へ一般化しない。
- `CONFIRMED`は方針回答の採用であり、実装済み、実証済み、利益性の確認を意味しない。
- `LATER_GATE`、`UNKNOWN`、`BLOCKED`、`HISTORY`をPassへ変換しない。
- `RQV2-BLK-001`の物理Evidence欠落と運用者Overrideを、機械的な実証Passへ変換しない。
- 外部Data、Provider、Secret、Broker、Paper、実注文、実資金、Cloud公開は、独立した承認なしに開始しない。
- Liveは、候補審査、Small Live、Normal Liveの3段階へ分ける。

## 4. HTMLに必ず含める構成

HTMLは次の順番で作る。この順番を変えない。最初に全体像を示し、その後で詳細へ進む。

### 4.1 入口部分：30秒で分かる説明

冒頭に次を置く。

1. 文書タイトル
2. 「この文書を一言でいうと」の短い説明
3. 大きな警告カード
   - これは実装開始承認書ではない。
   - Phaseごとに別計画・別設計・別品質Gate・別Human Gateが必要。
   - 現時点の説明に含まれる実注文・実資金・外部接続は未承認である。
4. 「まずこれだけ読めばよい」3行
5. `P4→P5→P6→P7→P8→P9→P10→P11` の大きな視覚的な流れ
6. Phase 4〜11を1行ずつ並べた一覧カード

### 4.2 読者別の読み方

次の読者に対して、どこを読めばよいかを説明する。

- 初めて読む人：最初の全体像、Phase一覧、用語集
- 実装担当者：各Phaseの「作る成果物」「依存」「開始条件」「完了条件」
- 運用者：各Phaseの「できること」「できないこと」「停止条件」「Human Gate」
- レビュー担当者：Gate／Unknown／Evidence／旧新対応
- 承認者：承認する範囲と、承認しても許可されない範囲

### 4.3 Phase一覧表

横に広すぎて読めなくならないよう、PCでは表、スマートフォンでは縦積みカードとして読めるCSSにする。最低限、次の列を含める。

| Phase | やさしい名前 | このPhaseで作るもの | 終了後にできること | まだしないこと | 次のPhase |
|---|---|---|---|---|---|

Phase 4〜11のすべてを埋める。「実装」「検証」「承認」など抽象語だけで終わらせず、成果物名と利用者の操作を具体的に書く。

### 4.4 Phaseごとの詳細カード

Phase 4〜11をすべて、まったく同じ見出し構成で書く。各Phaseには次の見出しを必ず置く。

1. `このPhaseを一言でいうと`
2. `なぜこのPhaseが必要か`
3. `このPhaseで作るもの`
4. `作る成果物の一覧`
5. `このPhaseが終わると利用者ができること`
6. `このPhaseで作らないもの`
7. `前のPhaseから受け取るもの`
8. `開始するための条件`
9. `作業のまとまり（実行計画でStep化する単位）`
10. `品質GateとEvidence`
11. `Human Gateで承認すること・承認しないこと`
12. `Unknown／LATER_GATE／BLOCKEDの扱い`
13. `完了条件`
14. `次のPhaseへ渡すもの`
15. `保存先と関連資料`

「作業のまとまり」は、元資料に書かれている成果物を、読者が作業順として理解できる粒度に分ける。ただし、正式なStep IDが元資料にない場合は新しい正式Step IDを発明せず、「Phase実行計画書で具体的Step IDを確定する」と明記する。

### 4.5 Phase別に必ず説明する内容

次の内容を各Phaseの該当箇所へ必ず反映する。内容の抜けを防ぐため、次の箇条書きをチェックリストとして使う。

#### Phase 4：Product／Application基盤とBacktest製品化

- 型付き設定、Run、Job、Queue、Worker、API、UI、Persistenceの製品境界を作る。
- Single Backtest、Sweep、Result、Chart、取引明細、Evidenceを操作できるようにする。
- Replay、Fill、Cost、Roll、Gap、Calendar、Holdout、Turtle Strategy、Manifest、固定fixtureなど、既存Coreの必要最小範囲を再利用する。
- Coreを無承認で改変しない。
- 外部Data取得、Broker、Paper、Live、Secret、実資金、Cloudは対象外である。
- 開始にはRQV2-H3、Phase 4計画、詳細設計、RED、Core差分確認、Human Gateが必要である。
- 完了ではUI／API／Worker／Persistenceの境界と再現可能なRun／Result／Evidenceを確認する。

#### Phase 5：市場Data運用化と実証

- MCL、M6A、MZC、MZS、MZWの5候補を、実Symbol、取引所、限月、Roll、単位、Provider／Broker対応へ整理する。
- 4資産種類、D1／H4／H1／M30／M15を対象にする。
- Catalog、Data contract、Raw／Normalized、Quality、Calendar、Provenance、Manifest、hash、Cost／Slippage／Gap、長期、Holdout／Walk-forwardをEvidence付きで検証する。
- `UNK-P3-01`、`UNK-P3-05`、`UNK-P3-07`を解消または未解消のまま再分類する。
- 外部Data取得、Provider、費用、Secret、外部I/Oには別Human Gateが必要である。
- 欠損や不明値を推測で埋めず、未来Data、Calendar不明、entitlement不明、費用上限不明なら停止する。
- 利益性、Live適合、Broker、PaperをこのPhaseの完了だけで主張しない。

#### Phase 6：複数運用単位・Portfolio／Risk／OMS・Forward／Shadow

- 複数Unit、Portfolio、Account、資金配分、Risk限度、Order前判定、OMS状態、Idempotency、競合、部分約定、Reject、Expire、Kill、照合、再起動、復旧を作る。
- `Signal → Target Position → OrderIntent → Order → Fill → Position` の流れを、外部注文なしの固定Simulationで検証する。
- Forward／Shadowの仮想実行と、Incident、Snapshot、手動再開を作る。
- Broker送信、Secret、Paper、実Account、実資金、Live、Cloudは対象外である。
- Risk bypass、Duplicate、Unknown Fill、差分無視、自動Resume、Mode混同があれば停止する。
- 完了後も、実Risk値、1N、初回Order上限、実Broker差異、長期負荷は後続Gateへ残る。

#### Phase 7：Broker AdapterとPaper Trading

- Broker固有依存をAdapter境界へ閉じ込める。
- Account、Order、Fill、Positionの同期、注文Lifecycle、Partial、Reject、Cancel、Expire、再接続、照合、重複防止、停止・復旧を作る。
- Paper仮想Ledgerと、仮想状態・外部状態を見分けられる表示を作る。
- Broker採否、Secret管理、Sandbox／Paper契約、費用、Rate Limit、外部I/Oを別Gateで承認する。
- 未知応答を成功扱いしない。Secretを平文保存しない。照合前にResumeしない。PaperからLiveへ自動昇格しない。
- Live注文、実資金、通常Liveは対象外である。

#### Phase 8：運用堅牢化・長期Paper

- Dashboard、通知、Incident、Kill、Backup／Restore、容量制御、Soak／Load、20〜40 Unit、長期Paperを作る。
- PC、スマートフォン、HTTPS中継、端末Pairing／失効、Visual／a11y、運用Checklistを検証する。
- 長期中の自動Resume、Audit破壊、端末未登録、Backup復元不一致を停止条件にする。
- 自PCでの安定稼働、RPO／RTO、障害復旧、実測容量を確認する。
- Cloud移行、無制限Remote公開、実資金Liveは対象外である。

#### Phase 9：Live候補・小規模Live準備

- 実注文を出さずに、最終Engine、実Symbol／契約、Risk実値、1N、Limit、費用、法務、Runbook、Kill drill、停止・照合・復旧を確定する。
- Candidate checklistと未達一覧を作る。
- Candidate判定をLive承認と同一視しない。
- 未解決Critical／Highが0であること、実値、費用、法務、Kill drill、損失上限、停止条件がEvidence付きで確認できることを完了条件にする。
- Small Liveの対象、資金、期間、Order上限、Auto-approval、停止条件は別Human Gateで承認する。

#### Phase 10：小規模Live

- 初めて、明示承認された少額・少数Unit・限定期間・限定Symbol／Account Scopeで実資金・実注文を扱う。
- 開始、日次確認、停止、照合、Incident、損失・Exposure・Order上限、Audit、Backup、手動介入を運用する。
- Small Live実行計画、運用Runbook、実運用Evidence、Incident／損失報告、通常Liveへの拡大判定を作る。
- Phase 9完了と別Human Gateがない限り開始しない。
- 期間中にLimit超過、照合差異、Risk不明、通信不明、手動介入不能、日次確認欠落があれば停止する。

#### Phase 11：通常Live・継続運用

- Small Liveで承認された範囲を、対象、Unit、資金、Riskごとに段階的に拡大する。
- 継続監視、SLO／SLA候補、定期再検証、Audit、Backup、Incident、復旧、変更管理、Rollback、降格、再承認を作る。
- Cloud／VM移行は将来判断として別Gateにする。
- 一度の承認で無制限に拡大しない。ScopeやRisk変更ごとに再承認する。
- SLO逸脱、Limit超過、照合差異、Audit欠落、Version不一致、復旧不能、承認期限切れを停止条件にする。

### 4.6 依存DAGとGate表

視覚的なDAGに加え、次の内容を表で説明する。

- RQV2-H3が正式v2基準線を作る。
- P4がProduct／ApplicationとBacktestの接続点を作る。
- P5がDataの実証を行う。
- P6がBrokerの前にRisk／OMS／Kill／照合／復旧を完成させる。
- P7が承認範囲内のBroker AdapterとPaperを行う。
- P8が長期Paperと運用堅牢化を行う。
- P9が実資金なしのLive候補審査を行う。
- P10が限定されたSmall Liveを行う。

各Phaseについて、「開始Human Gate」「外部I/Oの可否」「実資金の可否」「主な停止条件」を一目で分かる表にする。Human Gateは、承認した範囲だけを許可し、承認していない範囲を許可しないことを日本語で説明する。

### 4.7 Unknown、LATER_GATE、BLOCKED、HISTORYの説明

専門用語の羅列で終わらせず、次の形式で説明する。

| 状態 | やさしい意味 | このロードマップでの扱い |
|---|---|---|
| `UNKNOWN` | まだ事実確認ができていない | 仮の値で合格にせず、ID・期限・証拠・停止条件を残す |
| `LATER_GATE` | 今は決めず、後の承認点で決める | 後続Phaseと開始条件を明示する |
| `BLOCKED` | 安全に進めるために足りないものがあり停止中 | 根本原因、再開条件、Evidenceを記載する |
| `HISTORY`／`SUPERSEDED` | 過去には使ったが現在の基準線ではない | 削除せず、現在状態と混同しない表示にする |
| `CONFIRMED` | 方針として採用した | 実装・実証・利益性の合格とは書かない |

- `UNK-P3-01`
- `UNK-P3-05`
- `UNK-P3-07`
- Q-243
- 実Risk／1N／Kill待ち／初回Order上限
- Provider／Broker／Secret／Paper
- 端末／HTTPS中継／実到達
- 性能／容量／20〜40 Unit／RPO／RTO

旧計画を否定・削除せず、次を表で説明する。

- 旧Phase 2 Market Data → 新P5
- 旧Phase 3 Strategy／Backtest → 新P4
- 旧Phase 4 Broker／Paper → 新P7

### 4.9 共通のPhase開始手順

読者が次に何をすればよいか分かるよう、次の手順を図と文章で示す。

1. 統合台帳でBlocked／Unknown／Human Gateを確認する。
2. そのPhaseの入力、Core再利用範囲、前Phase Evidenceを固定する。
3. そのPhase専用の複数Step実行計画書を`plan/`へ作る。
4. 詳細設計、REDテスト、停止条件、Evidence配置を確定する。
5. 機械品質Gate、専門レビュー、独立レビューを行う。
6. 人間が承認した範囲だけを開始する。
7. 完了時に成果物、証拠、Unknown、次Phase入力、`doc/index.html`導線を同期する。

「Phaseの名前が決まっただけでは実装開始できない」ことを明記する。

## 5. HTMLの表現・アクセシビリティ要件

### 5.1 基本要件

- `<!doctype html>`、`<html lang="ja">`、UTF-8、viewportを使う。
- 外部CDN、外部フォント、外部JavaScript、外部画像に依存しない。
- CSSはHTML内に置き、オフラインで開いても読めるようにする。
- 見出しの階層を崩さない。
- `main`、`nav`、`section`、`footer`、`table`、`details`など意味のあるHTML要素を使う。
- 色だけで状態を区別せず、ラベル、アイコン文字、説明文も併記する。
- キーボードで目次リンクを使えるようにする。
- 長い表には、スマートフォンで横スクロールまたは縦積みとなるCSSを用意する。
- `pre`やコード表示は折り返し、横幅が広い画面でしか読めない状態にしない。
- 本文のフォントサイズ、行間、余白はPCで長時間読めるようにする。

### 5.2 視覚要素

少なくとも次を、外部資産なしで実装する。

- Phaseの横方向の流れ（CSSまたはインラインSVG）
- Gateの停止／通過／未承認を示す凡例
- Phaseカードの色分け。ただし色だけで意味を伝えない
- 「作る」「作らない」「次へ渡す」の3列または3ブロック
- 重要な停止条件の警告カード

Mermaid CDNは使用しない。Mermaidが必要な場合は既存のローカル資産を正しく参照するが、この文書ではCSS／インラインSVGだけで表現できるならそれを優先する。

### 5.3 文体

- 文章は日本語で書く。
- ID、API名、正式名称、コード、パス、状態値は原文どおり残す。
- 先に結論、次に理由、最後に詳細を書く。
- 「何を作るか」「なぜ必要か」「終わると何ができるか」「何をしないか」を必ず分ける。
- 英語の専門語を使うときは、最初に日本語の意味を添える。
- 「安全」「検証済み」「完了」などの言葉は、対象範囲を明記する。固定fixtureの完了を実市場の完了と書かない。
- 投資助言、利益の保証、特定商品の推奨は書かない。

### 5.4 メタ情報

HTML冒頭のメタカードに次を含める。

- 文書ID: `RQV2-ART-11-ROADMAP-001`
- Step ID: `RQV2-11`
- Phase ID: `REQUIREMENTS_V2_REBUILD_2026_08_11`
- Plan: `RQV2-PLAN-001 v0.1`
- 作成日: `2026-08-12`
- 状態: HTML化・説明拡充版であること、および実装開始承認ではないこと
- 正本入力: 元MarkdownとRQV2-PLAN-001 §13
- 出力ファイル: 本HTMLの相対パス
