## 1. 記録上の重要な扱い

今回の回答により、技術構成の大きな方向はかなり明確になりました。PythonのStrategy・Backtestコアを維持し、Python API、React + TypeScript画面、SQLite、ファイル保存、ローカルの別作業プロセス、TypeScript版Playwrightを組み合わせる方向です。

ただし、次の回答は、選択肢としては回答済みでも、正式要件へそのまま確定させる前に整合性または具体値の確認が必要です。

1. Q-158：Phase 3で実証した先物中心の範囲から、先物・株式・FX・暗号資産の4種類すべてへ初期対象を広げる回答である。Phase 3完了を取り消すものではないが、各市場のデータ・取引単位・Calendar・Adapterの受入条件を追加する必要がある。
2. Q-159、Q-164、Q-165：銘柄名、時間足別の欠落判定値、Risk初期値などの具体値が未入力である。
3. Q-167：Liveの自動承認をいつでも設定可能とする回答は、既存のHuman Gate、確認表、Fail-Closed（危険時に止まる）方針と衝突する。回答意図は記録するが、安全確認が終わるまで正式採用扱いにしない。
4. Q-190：自PCと自分のスマートフォンからのみ開く要求は、アプリ認証不要という既存方針と両立方法が未確定である。ネットワーク範囲だけでは「自分の端末だけ」を保証できない。
5. Q-198：性能基準を設けない回答は、Q-157の実時間運用数上限なし、Q-186の長時間ジョブ、Q-194の大きな結果表を受入確認する基準を未定義のままにする。

```text
ブラウザ（自PC・スマートフォン）
        |
React + TypeScript + Vite  ── Playwright(TypeScript)
        |
Python API層（フレームワークは未選定）
        |                         \
SQLite（設定・Run・進捗・検索）    ローカル作業プロセス
        |                               |
        +── ファイル保存（市場データ・結果・ログ・証跡）
        |
Python Strategy / Backtest コア
        |
Adapter境界 ── LEAN / NautilusTrader（最終採用はPhase 4後）
```

この図は回答から整理した暫定像であり、正式なアーキテクチャ決定ではありません。特に、Q-190の端末アクセス、Python APIフレームワーク、Q-198の性能基準が決まるまで、正式要件・詳細設計へ固定しません。
