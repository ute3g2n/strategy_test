## 1. 今回の前提決定

### 1.1 利用者モデル

このシステムは、基本的に開発者本人だけが使用する。従って、現行要件定義書で別々に扱っていた次の役割は、すべて一つの利用者へ統合する。

- 一般利用者
- 運用者
- 承認者
- 管理者
- 監査者・閲覧者
- Strategy開発者

正式な利用者名は、すべて次とする。

> **運用者（開発者本人）**

### 1.2 認証・権限の扱い

本システム内に、次のユーザー管理機能は設けない。

- ログイン・ログアウト
- ユーザー登録・削除
- パスワード管理
- ロール切替
- RBACによる権限分離
- MFA
- 複数承認者の割当

このシステムでは、ローカル環境へアクセスできる者を運用者本人とみなす。OS、端末、リポジトリ、Secret保管場所へのアクセス保護はシステム外の環境管理責任とする。

### 1.3 認証と安全確認の区別

認証は不要だが、次の安全確認は残す。これは本人確認や権限分離ではなく、誤操作防止と証跡のためである。

| 操作 | 認証 | 明示確認・Human Gate | 証跡 |
|---|---|---|---|
| ローカル設定閲覧・Backtest準備 | 不要 | 原則不要 | 必要に応じて操作ログ |
| Backtest実行・停止 | 不要 | 実行／停止確認を表示してよい | Run、設定版、hash |
| Shadow／Paper開始 | 不要 | 運用者の明示確認 | 開始記録、設定、Run |
| Broker接続・Secret投入 | アプリ内認証は不要 | 別Human Gate・外部資格情報が必要 | Secretを出力せず、承認と接続結果のみ保存 |
| 少額Live／本番Live移行 | 不要 | Human Gateによる運用者の明示承認が必要 | 承認、チェックリスト、移行証拠 |
| Kill Switch・全体停止 | 不要 | 即時実行可能。確認は設定可能 | 停止理由、時刻、対象範囲 |

Human Gateを残す理由は、認証するためではなく、実資金・外部接続・Secret・費用・次段階移行を無意識に開始しないためである。プロジェクトの安全境界上、認証不要という決定によって、Human Gateや安全停止を削除してはならない。

## 3. 運用者の目的

運用者は、同じシステムを次の目的で使用する。

- 市場データを準備し、品質を確認する
- Turtleを含むStrategyを設定する
- 複数の銘柄・時間足・Strategyを組み合わせる
- Backtestを実行する
- Backtest結果、取引、Signal、損益、Drawdownを確認する
- 複数条件を比較する
- Holdout、Walk-forward、Forward Testを行う
- Shadow、Paper、Liveの稼働状況を確認する
- Risk、口座、ポジション、注文を確認する
- 異常時に停止・復旧する
- 結果・設定・操作・承認の証跡を保存する
- 将来の設定変更や運用移行を判断する

## 4. 運用モードの要件

「Forward Test」は意味が混同されやすいため、次の二つに分ける。

| モード | 意味 | 資金 | 外部注文 |
|---|---|---:|---:|
| Backtest | 過去データを決定的にReplayする | 使わない | なし |
| Holdout / Walk-forward | 過去データの未学習期間で評価する | 使わない | なし |
| Real-time Forward Test | 将来時点から収集したデータでStrategyを検証する | 使わない | なし |
| Shadow | 実時間の市場データでSignal・仮想ポジションだけを追跡する | 使わない | なし |
| Paper | 模擬口座へ注文を送る | 実資金なし | 模擬注文 |
| 少額Live | 制限した実資金で運用する | 使う | 実注文 |
| 本番Live | 承認済みの実運用を行う | 使う | 実注文 |

各モードについて、以下を要件化する。

- 目的
- 使用するデータ
- 実行可能な機能
- 開始前の条件
- 操作手順
- 画面表示
- 実資金への影響
- 停止条件
- 異常時の動作
- 結果・証拠
- 次のモードへ移行する条件

## 6. 5時間足の要件

ユーザーが取引対象として選択できる時間足は、次の5種類とする。

- 15分足（M15）
- 30分足（M30）
- 1時間足（H1）
- 4時間足（H4）
- 日足（D1）

M1は、内部の正本入力または発火専用として扱う。ユーザーが取引時間足としてM1を選べるかは別途決定する。

各時間足について、次を定義する。

- 生成元データ
- 足の開始・終了時刻
- 取引所セッションとCalendar
- タイムゾーン、夏時間、休日、短縮日、休場
- ClosedBarの条件
- 欠損・重複・途中終了時の扱い
- ウォームアップに必要な本数
- Signal評価のタイミング
- 注文を出す時点
- Backtest／Forward／Shadow／Paper／Liveでの意味の共通化
- UIでの選択・表示方法
- 時間足別の性能・遅延・監視値

同一時刻に複数時間足が確定する場合は、すべてのViewを更新してからStrategy判断を一回だけ行う。途中のViewで重複Signalを出してはならない。

## 15. 主要状態と操作

### 15.1 Strategy設定

`下書き → 検証済み → 運用候補 → 稼働中 → 無効化／廃止`

### 15.2 Backtest

`待機 → 入力検証中 → 実行中 → 完了／停止／失敗／取消`

### 15.3 運用単位

`下書き → 開始確認 → 稼働中 → 一時停止 → 再開／終了`

### 15.4 注文

`生成 → Risk確認 → 送信 → 受付 → 部分約定 → 約定／拒否／取消`

### 15.5 障害

`検出 → 通知 → 対応中 → 復旧確認 → 解決`

各状態で、運用者が実行できる操作、実行できない操作、保存する証跡、再開条件を定義する。

## 16. 異常系・誤操作

- 必須設定不足
- 対応していない時間足
- データ期間不足
- 欠損・重複・時刻逆行
- Calendar不一致
- Strategy版不一致
- 同じRunの二重実行
- 同じ注文の二重送信
- データ提供元切断
- Broker切断
- 注文拒否・部分約定
- 証拠金不足
- Risk上限超過
- 稼働中設定の変更
- 承認期限切れ
- プロセス再起動
- ネットワーク・電源障害
- システムとBrokerのポジション不一致
- Kill Switch後の誤再開

各異常について、画面表示、自動停止の範囲、運用者の対応、再開条件、証跡を記載する。

## 17. 非機能・運用要件

認証・ユーザー管理を除き、次の非機能要件は必要である。

- 画面応答時間
- Dashboard更新間隔
- 同時運用数・同時Backtest数
- 最大銘柄数・最大データ量
- 再起動・復旧時間
- Snapshot・バックアップ・復元
- Result・注文・操作履歴の保存期間
- Secret非表示・最小露出
- 通信・保存データの保護
- 時刻同期
- 監査ログの改ざん検知
- 環境分離
- 保守時間
- 費用上限
- 障害通知
- ローカル端末アクセスはシステム外の環境責任であること

## 18. 明示する対象外

- 複数ユーザー対応
- ユーザー登録・ログイン
- ロール・権限管理
- 複数承認者ワークフロー
- 外部ユーザー向け公開
- 手動裁量取引画面を提供するかどうか
- 税務計算
- 利益保証
- Backtest結果だけを根拠にしたLive許可

「対象外」は、将来追加する可能性があるものと、意図的に提供しないものを分ける。

## 19. 未確定事項

認証不要の前提を維持したまま、次の事項は別途決定が必要である。

- UIをWebにするかDesktopにするか
- 対応ブラウザ・画面幅
- 対象Asset Class・銘柄
- データ提供元と最終Broker
- Forward Testの正式定義
- Strategyごとの判断時間足と参照時間足
- 同時運用数
- 同一銘柄のnetting／hedging方針
- Strategy別資金配分
- Paper／LiveのRisk採用値
- 通知サービス
- Cloud構成
- 操作履歴・Resultの保存期間
- UI更新間隔
- 独自Strategy Pluginを運用者が追加できるか

これらは勝手に補完せず、正式決定時に既存のUnknown・Human Gate・要求追跡表へ登録する。

## 20. 追跡性と受入条件

最終的に、次の関係を追跡できるようにする。

`運用目的 → ユースケース → 機能要件 → 運用モード → 画面ID → UIモック → テスト → 証拠`

各機能は、最低限次の書式で記述する。

> 誰が／何のために／どの画面で／何を入力し／何を操作し／何が起き／失敗時にどうなり／どこで結果を確認するか

受入条件は次とする。

- 運用者が要件定義書だけで、できること・できないことを判断できる
- 運用者が各モードの開始・停止・確認手順を追える
- 5時間足の意味と使い分けを確認できる
- 複数Asset Class・複数時間足の同時運用可否を確認できる
- UIモックから対応ユースケースと要求IDへたどれる
- 正常系、停止系、異常系、未承認状態をモックで確認できる
- Backtestの結果を、どの画面で何を見るかが明確である
- 認証不要の前提と、Human Gate・安全停止の役割が混同されない
