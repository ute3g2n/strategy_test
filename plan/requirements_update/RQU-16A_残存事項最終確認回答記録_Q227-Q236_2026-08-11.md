## 1. Q-227のPhase記録調査結果（混同訂正）

先の版では、P2-12-03の実DBN変換結果「4レコード中3レコードを正規化」を、初期候補の銘柄選定結果と誤って解釈していた。この解釈は誤りである。本節では、アセット選定とデータ変換を分けて記録する。

### 1.1 確認できた事実

1. Phase 0のP13最終選定記録は、初期検証候補を次の5件としている。
   - `MCL`：WTI原油
   - `M6A`：豪ドル米ドル
   - `MZC`：とうもろこし
   - `MZS`：大豆
   - `MZW`：小麦
2. Phase 2のP2-01スコープでは、`MCL/M6A`を本線候補、`MZC/MZS/MZW`を条件付き候補として整理している。これは5候補の扱いを分けたものであり、「5件から3件を選び、1件を除外した」という決定ではない。
3. 既存記録を再検索した範囲では、上記5件から特定の3件だけを初期運用対象として確定した記録、または4件中1件をアセット選定として除外した記録は確認できない。
4. P2-12-03の実DBN入力は、アセット選定とは別の**データ変換・Replay検証用の4レコード**である。
5. その4レコードのうち、通常の先物契約レコードは次の3件である。
   - `MCLN6`（内部ID `instrument-mcln6`）
   - `MCLQ6`（内部ID `instrument-mclq6`）
   - `MCLU6`（内部ID `instrument-mclu6`）
6. 除外されたレコードは `MCLN6-MCLQ6`（スプレッド、`record_ordinal=1`）である。

### 1.2 スプレッド除外の意味

`MCLN6-MCLQ6`は、MCLの2つの限月を組み合わせたスプレッド商品レコードである。P2-12-03では、`instrument_class=future`かつ`instrument_status=active`の通常先物だけを本線へ流し、スプレッドはRaw・監査記録に残すが、NormalizedBar・MarketEvent・Signalには使わない、というデータ品質・変換上の方針を採用した。これは「初期候補から1銘柄を落とした」という意味ではなく、1つのDBN入力内でデータ型を分離したものである。

### 1.3 Q-227の現時点の結論

- 文書上確認できる初期候補は、Phase 0の5件（`MCL/M6A/MZC/MZS/MZW`）である。
- `MCLN6/MCLQ6/MCLU6`は、初期候補3銘柄ではなく、P2-12-03のMCLデータ変換で採用された3契約レコードである。
- 運用者は今回、初期候補を5件すべて（`MCL/M6A/MZC/MZS/MZW`）と明示的に決定した。「4銘柄」は運用者の勘違いであり、4件から1件を除外する決定は存在しない。
- よってQ-227は解消済みであり、`MCLN6-MCLQ6`のspread除外は初期候補からの除外ではなく、P2-12-03のデータ変換で本線データからspread型を分離した記録である。

## 2. Q-233のネットワーク前提（追加補足反映）

今回の回線前提を次のように訂正する。

- 自PCのインターネット回線：楽天モバイル
- 自分のスマートフォンのモバイル回線：IIJmio

楽天モバイル公式サポートは、APN設定によりインターネットへ接続できること、APNプロトコル・PDPタイプとしてIPv4/IPv6を案内している。[楽天モバイル公式APN設定案内](https://network.mobile.rakuten.co.jp/faq/detail/00001495/)

また、楽天モバイル公式のテザリング案内は、スマートフォンからPCなどをインターネットへ接続できることを説明している。[楽天モバイル公式テザリング案内](https://network.mobile.rakuten.co.jp/service/tethering/)

IIJmio公式のギガプラン案内も、契約・開通後にインターネットを利用できることを案内している。[IIJmio公式ギガプラン](https://www.iijmio.jp/gigaplan/index.html)

### 2.1 Q-233の結論

- スマートフォン（IIJmio）から、公開されたHTTPS画面へ接続する構成を想定する。
- PC（楽天モバイル）は、外部のHTTPS入口・中継先へ**外向きに接続**し、スマートフォンからの要求を受ける方式を第一候補とする。
- 公式情報だけでは「楽天モバイル回線のPCへ外部から直接着信できる」「PCのポートを直接公開できる」とまでは確認できない。したがって、直接着信を要件の前提にしない。
- 実際のIIJmioスマートフォン → HTTPS入口 → 楽天モバイル接続PCの到達確認は、公開Endpointと中継方式を用意した後の技術確認で行う。今回、外部Endpointの作成や接続試験は実施していない。

## 4. 今回の回答で確定した方向

### 4.1 銘柄選定

文書上の初期候補は、Phase 0/P2-01で管理された5件（`MCL/M6A/MZC/MZS/MZW`）である。P2-01では`MCL/M6A`を本線、`MZC/MZS/MZW`を条件付きとして扱ったが、運用者の最新決定により初期候補はこの5件すべてとする。P2-12-03の`MCLN6/MCLQ6/MCLU6`は、初期候補設定ではなく、MCLの実DBN変換で本線へ採用した契約レコードである。

### 4.2 運用者権限とLive

運用者は一人であり、Live運用可否を決める権限者も運用者本人だけとする。状態表示は行うが、別の承認者を要求しない。運用者がLive自動承認をONにした操作は、対象・設定・Risk・時刻とともにHuman Gate記録として保存する。

### 4.3 スマートフォン・PCの回線

スマートフォンは閲覧専用ではなく、PCと同じ操作を許可する。スマートフォンはIIJmioで外部HTTPS入口へ接続し、PCは楽天モバイル回線から外部入口へ外向き接続する中継方式を第一候補とする。自宅PCの直接公開は前提にせず、HTTPS入口、端末ペアリング、失効、緊急停止、再起動後の自動承認OFFを一体で設計する。
