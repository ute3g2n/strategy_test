# プロダクト品質を維持する軽量開発運用改善提案

## 1. 目的

本提案の目的は、個人開発プロジェクトとして必要なプロダクト品質を維持しながら、プロジェクト管理やドキュメント管理のためだけに発生している作業を、可能な限りゼロへ近づけることである。

今後は、コード、テスト、利用者向け仕様、操作マニュアルなど、プロダクトの完成度や利用可能性に直接寄与する成果物を優先する。AIの作業を管理・証明・追跡するためだけの成果物は、原則として作成しない。

## 2. 基本方針

通常の開発では、次の考え方を標準とする。

1. 一つの依頼に対して、必要な調査、実装、関連テスト、必要最小限の文書更新までを直接行う。
2. プロダクト品質は、管理文書の量ではなく、動作するコード、関連テスト、明確なエラー処理、利用者が必要とする説明によって確保する。
3. AI Agent、Human Gate、実行証跡、管理台帳などは標準処理から外し、ユーザーが明示的に要求した場合だけ使用する。
4. 調査対象は依頼に関係するコード、テスト、仕様だけに限定し、プロジェクト全体の文書を毎回読み直さない。
5. 判断可能な小さな不明点は既存実装と一般的な設計原則から合理的に補い、製品仕様が変わる重要事項だけをユーザーへ確認する。

## 3. 成果物の分類

### 3.1 標準で作成・更新してよい成果物

以下はプロダクト品質または実際の利用に直接必要なため、通常の開発対象に含める。

- プロダクトのソースコード
- 自動テストコード
- テストに必要なfixtureや固定データ
- 実装判断に必要な仕様書、詳細設計書
- ユーザーが操作時に参照するマニュアル
- ユーザーが明示的に依頼した計画書
- 障害の再現や修正に直接必要な最小限の調査記録
- プロジェクト全体の現在状態を一つに集約する必要がある場合の総合台帳

ただし、仕様書、計画書、マニュアル、総合台帳は、依頼または製品仕様の変更によって更新が必要な場合だけ変更する。

### 3.2 標準では作成しない成果物

以下はAIや作業工程を管理するための二次的成果物であり、通常の開発では作成しない。

- 作業開始確認書
- 作業完了確認書
- Stepごとの実行ログ
- runtime receipt
- Agent起動記録、受領記録、失敗時fallback記録
- Human Gate packetと承認記録ファイル
- レビューを実行した事実だけを証明する文書
- hash管理、manifest、stale判定、fingerprint、hash receipt
- 同じUnknownやBlockedを複数箇所で管理する台帳
- 次のStepを実行するためだけの大量のプロンプト集
- 文書更新のたびに作る変更履歴ファイル
- テスト結果を転載しただけの証跡ファイル
- Phase完了packet、次Phase引き渡しpacket
- AIの実行経路を説明するためだけの図表や一覧

これらが必要な場合は、ユーザーが成果物名と目的を明示したときだけ作成する。

## 4. 標準開発フロー

通常の機能追加、修正、障害対応は、次の流れで完了させる。

### Step 1: 関連箇所だけを調査する

- 依頼に関係するソースコード、テスト、仕様を検索する。
- 全Phaseの計画書、全台帳、全設計書は読まない。
- 外部仕様の確認が必要な場合だけ、該当する公式情報を参照する。

### Step 2: 必要なら仕様を確認する

- 製品の動作が大きく変わる不明点だけをユーザーへ質問する。
- 質問する場合は、背景、各選択肢の意味、影響、推奨案を示す。
- 実装方法の細部は、既存コードとの整合性を優先してAIが判断する。

### Step 3: 直接実装する

- 関連コードとテストだけを変更する。
- 将来使うかもしれないという理由だけの抽象化や拡張は行わない。
- 同じ仕様を複数の文書へ重複記載しない。

### Step 4: 変更に応じた品質確認を行う

- 変更箇所に関係するテストを実行する。
- UI変更では、必要に応じてUIテスト、アクセシビリティ確認、主要操作のE2Eを行う。
- APIや永続化の変更では、正常系、主要異常系、データ整合性を確認する。
- 削除処理では、削除対象、対象外データ、二重実行時の挙動を確認する。
- 全プロジェクト試験は、共通基盤への変更やリリース前など、影響範囲が広い場合だけ行う。

### Step 5: 必要な文書だけを更新する

- ユーザー操作が変わった場合は操作マニュアルを更新する。
- 実装者が将来判断できなくなる重要仕様だけを仕様書へ反映する。
- 内部実装だけの変更で利用方法や仕様が変わらない場合、文書は更新しない。

### Step 6: チャットで簡潔に報告する

報告内容は次の範囲に限定する。

- 何を変更したか
- どの品質確認を実行したか
- 未解決事項があるか
- 必要な場合のみ、変更ファイルやGit情報

同じ内容を別の実行ログやreceiptへ転載しない。

## 5. プロダクト品質を落とさないための最低基準

管理作業を削減しても、以下の品質基準は維持する。

### 5.1 コード品質

- 既存の責務分割、命名、型、例外処理に合わせる。
- 入力値を検証し、異常時には利用者が理解できるエラーを返す。
- データ破損や意図しない取引につながる処理はfail-closedとする。
- Secret、認証情報、個人情報をコードやログへ含めない。
- 無関係な既存変更を上書きしない。

### 5.2 テスト品質

- 不具合修正では、可能な限り再現テストを先に用意する。
- 新機能では、主要正常系と重大な異常系を自動テストする。
- 金額、注文、ポジション、ヒストリカルデータ、物理削除など、誤りの影響が大きい処理は境界値と再実行を確認する。
- テスト結果はチャットで報告し、結果を複製した証跡文書は作成しない。

### 5.3 UI品質

- 主要操作がキーボードでも実行できることを確認する。
- ボタンの二重押下や多重送信を防止する。
- 処理中、成功、失敗、データ不足の状態を画面で明示する。
- 破壊的操作は対象を明示し、必要な確認操作を設ける。
- 画面変更に応じて、利用者が実際に参照するマニュアルを更新する。

### 5.4 自動売買システム固有の品質

- Backtest、Paper、Liveの実行環境を混同しない。
- 外部APIへの接続、実注文、費用発生、Secret利用は、ユーザーの明示的な許可なしに実行しない。
- 対象銘柄、時間足、期間、データ充足性を実行前に検証する。
- 既存データのマージ、上書き、削除は仕様に従い、処理途中で不整合を残さない。
- 物理削除では、CSVなどユーザーが明示的に保存した外部成果物を削除対象に含めない。

## 6. 文書運用の軽量化

### 6.1 Single Source of Truth

同じ情報を複数の文書で管理しない。

- 現在の製品仕様は仕様書またはコードのどちらか一方を正本とする。
- 操作方法は操作マニュアルを正本とする。
- 未完了事項を管理する必要がある場合は一つの総合台帳だけを使う。
- 過去の検討経緯はGit履歴に残し、別の変更履歴文書を作成しない。

### 6.2 Just-In-Time Context

AIには、その依頼に必要な情報だけを与える。

- 関連コード
- 関連テスト
- 該当仕様の必要な章
- 変更差分

README、全Phase成果物、全Agent仕様、全Skill仕様を毎回読み込ませない。

### 6.3 文書更新の発火条件

次の場合だけ文書を更新する。

| 変更内容 | 更新対象 |
|---|---|
| ユーザー操作が変わる | 操作マニュアル |
| 外部APIや保存形式が変わる | 該当仕様書 |
| 重要な製品要件が変わる | 要件・仕様の正本 |
| 実装内部だけが変わる | 原則として文書更新なし |
| テストだけを追加する | 原則として文書更新なし |
| AIの進め方だけが変わる | 通常は文書更新なし |

## 7. AI Agent・Skill・Orchestratorの扱い

通常の開発では、単一のAIが直接作業する。

Agent、Skill、Orchestratorを使用するのは、次のいずれかに該当する場合だけとする。

- ユーザーが名称を指定して使用を求めた場合
- 一つのAIでは処理しきれない独立した大規模作業がある場合
- 取引安全、認証、Secretなど、独立レビューが実質的な品質向上につながる場合

使用した場合も、Agent起動記録やruntime receiptは作らない。必要な結論だけをコード、テスト、仕様またはチャットへ反映する。

## 8. Human Gateの扱い

Phase番号を理由とする定型的なHuman Gateは廃止する。

ユーザー確認が必要なのは、次の場合だけとする。

- 実際の取引を発生させる
- 外部サービスへログインする
- Secretや認証情報を使用する
- 費用が発生する
- 外部へデータを送信する
- 既存の重要データを物理削除する
- 要件に複数の解釈があり、選択によって製品動作が大きく変わる

確認はチャット上で行い、承認packetや承認ログファイルは作成しない。Git履歴または会話履歴で十分な場合は、それを追加文書で複製しない。

## 9. Git運用

- 通常は、機能または修正が完了した単位で一度だけcommitする。
- Stepごとのcommitは行わない。
- 文書同期だけを目的とするcommitを作らない。
- pushは機能完了時またはユーザーが求めた場合に行う。
- commit前には、今回の変更だけが含まれていることを確認する。
- Git履歴を作業履歴の正本とし、同じ内容の変更履歴文書を作成しない。

## 10. 依頼種別ごとの標準動作

| ユーザーの依頼 | 標準動作 |
|---|---|
| 原因を調査して | 読み取りと原因報告だけを行う |
| 修正して | 調査、実装、関連テストまで行う |
| 計画を作って | 原則チャットへ計画を提示し、ファイル指定時だけ保存する |
| 仕様書を作って | 指定された仕様書だけを作る |
| マニュアルを直して | 対象マニュアルだけを更新する |
| レビューして | Findingsと改善案を報告し、実装は依頼がある場合だけ行う |
| Phaseを進めて | 製品作業を直接進め、定型Gateやreceiptは生成しない |

## 11. 導入手順

運用変更は次の順で行う。

1. プロジェクトのAI向けルールから、Agent起動、Human Gate、runtime receipt、hash policy、台帳同期の自動実行義務を外す。
2. 標準フローを「関連箇所の調査、実装、関連テスト、必要文書の更新、簡潔な報告」に置き換える。
3. Phase計画と大量の実行プロンプトを、通常タスクの必須条件から外す。
4. テスト実行範囲を変更箇所中心にする。
5. 既存の管理専用成果物は直ちに一括削除せず、新規生成を止める。必要になった範囲だけ別途整理する。
6. 次の通常機能開発で、管理専用成果物が新規作成されないことを確認する。

導入のために、新たなGate、receipt、移行台帳、完了証明書は作成しない。

## 12. 改善後の受入基準

通常の機能追加または不具合修正について、次をすべて満たせば運用改善は成功とする。

- 必要なコードが実装されている。
- 変更リスクに応じた関連テストが通っている。
- ユーザー操作が変わった場合だけマニュアルが更新されている。
- 重大な外部接続、費用、Secret、物理削除は実行前に確認されている。
- 作業のためだけのGate packet、receipt、Agent記録、hash管理文書が作られていない。
- 同じ情報が複数の計画書、ログ、台帳へ転載されていない。
- AIの最終報告だけで、変更内容、検証内容、残課題を把握できる。

## 13. 標準指示文

今後の通常タスクでは、AIに対して次の方針を適用する。

> プロダクトのコード、関連テスト、必要な仕様書・操作マニュアルだけを対象として作業すること。Agent起動、Human Gate、runtime receipt、hash管理、作業ログ、証跡文書、Phase完了packet、次Step用プロンプト、台帳・index同期は、明示的に依頼されない限り実行しないこと。変更リスクに応じたテストを行い、結果はチャットで簡潔に報告すること。

この指示を標準とすることで、プロダクト品質をコードとテストで維持しつつ、管理のための成果物を生成する作業を可能な限りゼロへ近づける。
