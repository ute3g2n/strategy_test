# AIハーネス（Agent Control）の過剰設定と過剰ドキュメンテーションに関する議論

## 概要
AIエージェントやAIアシスト開発において、AIハーネス（指示、ルール、システムプロンプト、`.cursorrules` / `CLAUDE.md` 等）を過剰に厳格化・増大させた際に発生する課題、世の中の開発現場で報告されている悪影響、およびその解決のためのベストプラクティスについてまとめたドキュメント。

---

## 1. 発生している主な課題と現象（アンチパターン）

### 1.1 課題の構造
AIの暴走や誤実装を防ごうとしてルールやプロンプトを固めすぎると、1プロンプトに対して管理ドキュメント（要件定義書、進捗ログ、設計書等）を大量に生成・更新するようになる。結果として**過剰ドキュメンテーション（Over-documentation）**や**文脈膨張（Context Bloat）**を引き起こし、本質的なコード開発にかかる時間とトークン消費量が跳ね上がる。

### 1.2 主な症状
* **ドキュメント更新の無限ループ:** 1行のコード修正に対して数十KBの管理用テキストを再生成し、開発作業に入る前にコンテキスト上限やリトライに達する。
* **Context Rot（コンテキストの劣化・腐敗）:** 入力コンテキストが大きくなりすぎるとLLMのアテンション（注意機構）が分散し、指示の読み飛ばしや精度低下が発生する。
* **過剰プロンプト（Over-prompting）による効率低下:** Claude 3.5/3.7やGPT-4oなどの最新モデルの推論能力に対し、過去のモデル用の冗長・丁寧すぎる手順指示がノイズとなり、無駄な思考ループを生む。

## 2. 世の中の事例・開発現場で報告されている悪影響

| 悪影響 | 詳細・症状 | 開発現場へのインパクト |
| :--- | :--- | :--- |
| **コンテキストの劣化 (Context Rot) と指示無視** | コンテキストが大量のドキュメントで埋まり、注意機構が分散。前半に設定した制約（API変更禁止、テスト必須等）を忘れたり無視し始める。 | 制御目的で増やすほど、AIが制御不能になる本末転倒。 |
| **「ループ地獄」の発生 (Deadlock Loops)** | 変更のたびにドキュメントA→B→コードの不整合を解消しようとし、相互更新の無限ループに陥る。 | 「作業した」と主張されるが、管理ドキュメントのみ生成され実装が進まない。 |
| **コストとレイテンシの跳ね上がり** | 簡単な関数・バグ修正の1プロンプトで数万〜十数万トークンを消費。 | 開発者の待ち時間増加、API利用料金の激増（ROI悪化）。 |
| **ハルシネーションの連鎖** | 高頻度更新により新旧記述が混ざり、存在しない仕様や過去の廃棄仕様が「最新」として定着。 | 誤ったドキュメントを「正」として参照し、存在しないコード呼び出しを繰り返す。 |

## 3. ベストプラクティスと解決策

### 3.1 「ドキュメント生成」と「コード実装」のセッション分割
1つのセッション・プロンプト内で「要件確認〜ドキュメント更新〜実装」を一気にやらせない。
* **設計フェーズ:** 要件整理や設計ドキュメントの更新だけを行い、セッションをリセット。
* **実装フェーズ:** 確定したドキュメントのみを最小限コンテキストとして読み込み、コードのみを書かせる。

### 3.2 Just-In-Time (JIT) コンテキスト化
全てのドキュメントを常に読み込ませるのではなく、必要な情報だけを必要な時にアタッチする。
* 毎回すべての設計書を書き直させるのではなく、「変更のあるセクションのみDiff形式で追記する」ルールに変更する。
* ルールファイル（`CLAUDE.md` や `.cursorrules`）は**30〜50行程度**に絞り、詳細な情報は別ファイルへのリンク・参照にとどめる。

### 3.3 管理・記録の外部ツール化
LLMに自然言語で管理用ドキュメントを書かせるのはトークン効率が最悪であるため、決定事項や変更の追跡は既存ツールに委ねる。
* **履歴管理:** GitコミットメッセージやIssue/PRのステータスで管理。
* **検証の自動化:** AIにチェックさせず、コミット前フック（pre-commit hook）やCI/CDでの静的解析・リントに任せる。

### 3.4 ルールファイルの「軽量化（Lean Harnessing）」
ハーネスの記述スタイルを「丁寧な手順指示（Do）」から「明確な制約（Don't & Must）」へ変更する。
* ❌ **アンチパターン:** 「〇〇のフォーマットに従い、A、B、Cのドキュメントを作成し、それぞれの整合性を確認した上で〜〜」
* ⭕ **推奨設定:** 「コード変更時は関連テストを通すこと。ドキュメントの自動生成は指示がない限り禁止。」

## 4. 現場での結論・まとめ

* **教訓:** 「AIにドキュメントの整合性管理までさせようとすると破綻する」
* **基本原則:**
  1. **ルールで縛りすぎず、ツール（CI/CDやGit）で検証する。**
  2. **1セッションのスコープとコンテキストサイズを最小限に維持する。**
  3. 不要なドキュメント自動生成指示を即座に削除し、局所的なコード実装に集中させる。
