# 軽量開発運用への移行計画書

## 0. 最新方針の追加

本計画の作成後、ユーザーから「Agent、Skill、Orchestratorの完全名を毎回明示しなくても、AIが必要な部品を自動選択できるようにする」という追加指示があった。以降は、次の読み替えを本計画全体へ適用する。

- AIは依頼内容、変更範囲、品質リスクから、必要最小限のAgent、Skill、Orchestratorを自動選択してよい。ユーザーへ完全名の指定を求めない。
- 自動選択した部品も、PRODUCT_ONLYの原則に従い、コード、関連テスト、必要な仕様書・マニュアル、製品安全上の確認だけを対象にする。
- 部品を使った事実だけを示すreceipt、Agent一覧、fallback記録、Human Gate packet、台帳、hash、manifest、doc/index同期は作成しない。
- 計画書、正式設計書、全体レビュー、全テスト、再現可能な証跡、外部I/O、重要データ削除など、成果物または安全確認が必要な作業は、依頼内容とリスクに応じてAIが最小限の部品を自動選択する。ただし、ファイル生成や外部操作自体を依頼なしに開始しない。
- Phase 1の凍結・legacy部品は履歴として保持し、新しい通常作業へ自動適用しない。

この追加方針は「部品を使うための明示指定」を解除するものであり、管理専用成果物を通常タスクへ戻すものではない。

## 1. 計画の目的

本計画は、「プロダクト品質を維持する軽量開発運用改善提案」で定めた方針を、このプロジェクトのAI向けルールと通常開発フローへ反映するための実行計画である。

移行後は、コード、関連テスト、必要な仕様書、操作マニュアルなど、プロダクトに直接必要な成果物を中心に作業する。Agent起動記録、Human Gate packet、runtime receipt、hash管理文書、重複台帳など、作業管理のためだけの成果物は、ユーザーが明示的に要求しない限り生成しない。

## 2. 達成する状態

移行完了後の標準動作を次の状態にする。

1. 機能追加や不具合修正は、関連箇所の調査、実装、関連テスト、必要な利用者向け文書の更新、チャット報告だけで完了できる。
2. Phase、Agent、Skill、Orchestrator、Human Gate、runtime receiptを通常タスクの必須条件にしない。
3. プロダクト品質は、変更リスクに応じたコードレビューとテストによって確保する。
4. 同じ情報を複数の計画書、ログ、台帳、HTMLへ転載しない。
5. 外部接続、実取引、費用、Secret、重要データの物理削除など、実害が発生し得る操作だけは事前確認を残す。
6. ユーザーが成果物を指定した場合は、指定された成果物だけを作成する。

## 3. 適用範囲

### 3.1 対象

- プロジェクトルートのAI向け作業ルール
- AI部品の使用条件と発火条件
- Phase実行計画の必須化ルール
- Human Gateの適用条件
- runtime receipt、実行ログ、証跡の作成条件
- hash policyと管理manifestに関する通常経路
- 文書、台帳、HTML indexの更新条件
- テストと品質確認の選択基準
- Git commit、pushの実施条件
- AIの進捗報告と最終報告の形式

### 3.2 対象外

- プロダクトの機能仕様変更
- 既存ソースコードの機能改修
- 既存テストの削除や品質基準の引き下げ
- 過去のPhase成果物や実行証跡の一括削除
- Git履歴の書き換え
- 外部サービスへの接続
- 実取引、Secret利用、費用発生を伴う操作

既存の管理文書は、今回の移行では削除しない。まず新規生成と自動更新を停止し、過去資料は履歴として残す。整理や削除が必要になった場合は、別途ユーザーが指定した範囲だけを対象とする。

## 4. 変更対象候補

実行時には、最初に以下のファイルから、通常タスクへ管理作業を強制している記述を確認する。

| 対象 | 主な変更内容 |
|---|---|
| `AGENTS.md` | 通常タスクの標準フローをPRODUCT_ONLYへ変更する |
| `settings/ai_component_rules.md` | Agent、Skill、OrchestratorをPRODUCT_ONLYの範囲で自動選択できるようにし、管理専用の強制発火を解除する |
| `README.md` | 人間・AI向けの入口に古い必須運用が残る場合だけ修正する |
| `doc/ai_foundation/` の入口文書 | Phase計画やAI部品利用を必須とする導線が現行ルールと矛盾する場合だけ、legacyまたは任意利用と明記する |
| `.codex/agents/` | 定義は保持し、依頼内容と品質リスクに応じて最小限を自動選択する。管理専用成果物は作成しない |
| `.codex/orchestrators/` | 定義は保持し、依頼内容と品質リスクに応じて必要な場合だけ自動選択する |
| `.codex/skills/` | Skillを削除せず、必要な責務に応じて自動選択する。管理専用の強制発火は解除する |

変更対象は、調査で実際に強制ルールまたは矛盾が確認されたファイルに限定する。関連がないファイルを「念のため」更新しない。

## 5. 新しい標準運用モード

プロジェクトの通常モードとして、`PRODUCT_ONLY`を定義する。

### 5.1 PRODUCT_ONLYで実行すること

- 依頼に直接関係するソースコードとテストの調査
- 必要なコード変更
- 変更リスクに応じた関連テスト
- 必要なエラー処理、入力検証、安全停止の実装
- ユーザー操作が変わる場合の操作マニュアル更新
- 重要な製品仕様が変わる場合の該当仕様書更新
- 変更内容、検証結果、残課題のチャット報告

### 5.2 PRODUCT_ONLYで管理のためだけに自動実行しないこと

- Phase実行計画書の作成
- 次Step用プロンプトの作成
- 部品を使った事実だけを残すためのOrchestratorや複数Agentの起動
- Human Gate packetの作成
- runtime receiptの作成
- 実行ログ、完了ログ、受領証跡の作成
- A90、A95などの定型レビュー起動
- 管理用hash、manifest、stale、fingerprintの管理
- Unknown、Blocked、承認待ち情報の複数台帳への転載
- 全HTMLの定型的なリンク・ID検査
- Phase完了packetと次Phase引き渡しpacketの作成
- doc/indexや総合台帳の無条件同期
- Stepごとのcommitとpush

### 5.3 依頼内容または製品リスクに応じて自動選択すること

- 計画書のファイル生成、正式な設計書セットの生成、全体レビューなどは、依頼内容に含まれる場合だけ実行する。実行する場合の部品名はAIが自動選択する。
- 複数Agentによる独立レビューは、製品品質または安全上の直接的な必要性がある場合だけ自動選択する。
- プロジェクト全体のテスト
- 全文書のリンク検査
- 総合台帳の更新
- Phase単位の進行管理
- commitまたはpush

## 6. 実行ステップ

### Step 1: 強制ルールの最小調査

#### 目的

通常タスクのたびに管理作業を発火させているルールと、その参照元を特定する。

#### 実施内容

- `AGENTS.md`と`settings/ai_component_rules.md`を正本候補として読む。
- `Phase実行計画`、`Human Gate`、`runtime receipt`、`A95`、`hash`、`統合台帳`、`commit`、`push`などの強制表現を検索する。
- 同じ強制ルールがREADMEやAI Foundation文書に重複しているか確認する。
- 調査結果は新しい棚卸し文書へ保存せず、そのままStep 2の編集対象選定に使う。

#### 完了条件

- 変更が必要なファイルだけが特定されている。
- 過去成果物と現行ルールが区別されている。
- 調査専用のログや台帳を作成していない。

#### AIエージェント実行プロンプト

```text
軽量開発運用への移行計画 Step 1「強制ルールの最小調査」を実行してください。

目的は、通常タスクのたびに管理作業を発火させている現行ルールと、その直接の参照元だけを特定することです。

実施内容:
- 最初に `AGENTS.md` と `settings/ai_component_rules.md` を読んでください。
- `Phase実行計画`、`Human Gate`、`runtime receipt`、`Agent`、`Orchestrator`、`A90`、`A95`、`hash`、`manifest`、`統合台帳`、`commit`、`push` に関する必須表現を検索してください。
- READMEまたは `doc/ai_foundation/` に、上記ルールを通常タスクへ強制する直接参照がある場合だけ、その箇所を確認してください。
- 過去のPhase成果物に書かれた履歴と、現在のAI動作を強制する現行ルールを区別してください。
- Step 2以降で変更が必要なファイル、該当箇所、変更理由をチャットに簡潔にまとめてください。

禁止事項:
- ファイルを変更しないでください。
- 新しい棚卸し文書、調査ログ、runtime receipt、Human Gate、台帳、証跡を作成しないでください。
- Agent、Skill、Orchestratorを起動しないでください。
- テスト、外部接続、Git commit、pushを実行しないでください。
- 関連がない文書を網羅的に読まないでください。

完了時は、変更候補ファイルと理由、変更不要と判断した主要ファイル、次のStepを安全に開始できるかだけをチャットで報告してください。
```

### Step 2: `AGENTS.md`をPRODUCT_ONLY中心へ変更

#### 目的

プロジェクト全体の標準動作を、直接的な製品開発中心へ切り替える。

#### 実施内容

- 通常タスクの標準フローをPRODUCT_ONLYとして明記する。
- Phase計画、Agent、Skill、Orchestratorを管理目的だけで自動利用しない。製品品質または安全に必要な部品はAIが最小限を自動選択できるようにする。
- Human Gateを、外部接続、実取引、費用、Secret、重要データ削除などの実害があり得る操作に限定する。
- runtime receipt、作業ログ、完了packet、管理用hashを通常の完了条件から外す。
- 文書更新は、ユーザー指定または製品仕様・操作変更がある場合だけに限定する。
- 「指定された成果物だけを作る」という指示を追加する。
- 調査、説明、レビューの依頼が、実装や外部操作を自動的に許可しないことは維持する。
- 無関係な既存変更を保護する規則、Secret保護、破壊的操作への注意は維持する。

#### 完了条件

- 通常の機能修正が、Phase計画やHuman Gateなしで実行可能になっている。
- 製品・データ安全に必要な制約は残っている。
- 管理文書の生成が標準完了条件から外れている。

#### AIエージェント実行プロンプト

```text
軽量開発運用への移行計画 Step 2「AGENTS.mdをPRODUCT_ONLY中心へ変更」を実行してください。

Step 1で特定した現行ルールを入力として、`AGENTS.md`の通常開発フローをPRODUCT_ONLYへ変更してください。

必須要件:
- 通常タスクは「関連箇所の調査、必要な実装、変更リスクに応じた関連テスト、必要な仕様書または操作マニュアルの更新、簡潔なチャット報告」で完了できるようにしてください。
- Phase計画、Agent、Skill、Orchestrator、Human Gate、runtime receipt、実行ログ、完了packet、管理用hashを通常タスクの必須条件から外してください。
- 文書は、ユーザーが指定した場合、製品仕様が変わる場合、またはユーザー操作が変わる場合だけ更新する方針にしてください。
- ユーザーが成果物を限定した場合は、その成果物以外を変更しない規則を追加してください。
- 外部接続、実取引、費用発生、Secret利用、重要データの物理削除は、実行前にユーザー確認が必要なままにしてください。
- 無関係な既存変更の保護、Secret保護、破壊的操作への注意、依頼範囲を越えない原則は維持してください。
- 同じ方針を複数箇所へ重複記載せず、通常運用の正本となる箇所へ集約してください。

禁止事項:
- `AGENTS.md`以外を変更しないでください。ただし、Step 1で `AGENTS.md` が参照する同一ファイル内の記述だけでは矛盾を解消できないと確認済みの場合は、作業を止めてチャットで報告してください。
- Agent、Skill、Orchestrator、Human Gate、runtime receipt、hash管理を起動または生成しないでください。
- 過去のPhase成果物を変更しないでください。
- テスト、Git commit、pushを実行しないでください。

変更後は、PRODUCT_ONLYの標準フロー、安全上維持した制約、削除または任意化した管理義務をチャットで簡潔に報告してください。
```

### Step 3: AI部品ルールをPRODUCT_ONLY自動選択へ変更

#### 目的

Agent、Skill、Orchestratorを、ユーザーの完全名指定が必要な仕組みから、依頼内容と製品リスクに応じてAIが必要最小限を自動選択できる道具へ変更する。

#### 実施内容

- `settings/ai_component_rules.md`の自動選択条件を確認する。
- ユーザーが完全名を指定しなくても、依頼内容、変更範囲、品質リスクから必要な部品を自動選択できる規則へ変更する。
- Skillを使用した事実を証明するためのreceiptやAgent一覧を不要とする。
- Orchestratorの起動失敗時にfallback文書を生成する要件を削除する。
- 既存のAgent、Skill、Orchestrator定義自体は削除しない。
- Phase専用部品は過去成果物として保持し、通常タスクの読み取り対象から外す。

#### 完了条件

- 通常タスクで管理目的だけのAI部品起動は発生しない。
- 製品品質または安全上必要な場合は、ユーザーの名前指定なしで既存部品を自動選択できる。
- AI部品の利用有無が、コード変更の完了条件になっていない。

#### AIエージェント実行プロンプト

```text
軽量開発運用への移行計画 Step 3「AI部品ルールをPRODUCT_ONLY自動選択へ変更」を実行してください。

対象は `settings/ai_component_rules.md` です。Agent、Skill、Orchestratorの完全名をユーザーへ要求せず、依頼内容と製品リスクに応じてAIが必要最小限を自動選択できるルールへ変更してください。ただし、管理専用成果物を増やさないPRODUCT_ONLY方針は維持してください。

必須要件:
- ユーザーが完全名を指定した場合は、指定されたAI部品を利用できるようにしてください。
- ユーザー指定がない場合でも、依頼内容、変更範囲、製品品質・安全リスクから必要な部品をAIが自動選択できるようにしてください。
- 通常の調査、実装、テスト、文書更新では、部品の利用自体を必須にせず、管理専用の部品起動も行わないでください。
- Agent起動記録、受領記録、runtime receipt、fallback記録を完了条件から外してください。
- Orchestratorを起動できなかった場合に、代替管理文書を生成する規則を削除してください。
- 既存のAgent、Skill、Orchestrator定義は保持し、削除しないでください。
- Phase専用部品は過去成果物として利用可能なまま残し、通常タスクの読み取り対象から外してください。

禁止事項:
- `settings/ai_component_rules.md`以外を変更しないでください。
- Agent、Skill、Orchestratorを実際に起動しないでください。
- AI部品のJSONやSKILL.mdを変更しないでください。
- runtime receipt、実行ログ、台帳、証跡を作成しないでください。
- テスト、Git commit、pushを実行しないでください。

完了時は、完全名の明示要求を外した自動選択条件、管理専用の起動を防ぐ条件、引き続きAI部品を利用できる条件だけをチャットで報告してください。
```

### Step 4: 文書・台帳・hash運用を軽量化

#### 目的

文書を更新したことを管理するための二次的成果物を停止する。

#### 実施内容

- 管理用hash、manifest、stale判定、fingerprint、retryを通常経路から完全に外す。
- runtime receipt、実行ログ、Agent受領証跡を標準成果物から外す。
- Unknown、Blocked、Human Gate待ちを複数文書へ転載する規則を解除する。
- 総合台帳は、ユーザーが更新を依頼した場合、または実際に管理対象を一元化する必要がある場合だけ更新する。
- `doc/index.html`は、正式文書を新設・削除して導線が変わる場合だけ更新する。
- 過去文書へ現在状態を同期するためだけの更新を行わない。
- Git履歴で確認できる変更履歴を別文書へ複製しない。

#### 完了条件

- コード変更だけのタスクで文書・台帳・hash関連ファイルが変更されない。
- マニュアルや仕様書を更新しても、receiptや証跡ファイルが追加されない。
- 文書の正本が必要以上に複数存在しない。

#### AIエージェント実行プロンプト

```text

Step 1で特定した現行ルールのうち、文書、台帳、実行証跡、管理用hashを通常タスクへ強制している記述だけを変更してください。

必須要件:
- 管理用hash、manifest、stale判定、fingerprint、hash retry、hash receiptを通常経路と完了条件から外してください。
- runtime receipt、実行ログ、Agent受領証跡、完了packetを標準成果物から外してください。
- Unknown、Blocked、Human Gate待ちを複数文書へ転載する義務を解除してください。
- 総合台帳は、ユーザーが明示的に依頼した場合、または現在状態を一元管理する実用上の必要がある場合だけ更新する方針にしてください。
- `doc/index.html`は、正式文書の追加、削除、移動によって利用者の導線が変わる場合だけ更新する方針にしてください。

- Git履歴と同じ内容の変更履歴文書を自動作成しない方針にしてください。
- 詳細方針は一つの正本へ置き、他の入口には必要最小限の参照だけを残してください。

作業範囲:
- Step 1で変更必要と判定されたルールファイルだけを編集してください。
- 過去のログ、receipt、台帳、Phase成果物は削除しないでください。

禁止事項:
- 新しい運用台帳、移行ログ、receipt、hashファイル、証跡を作成しないでください。
- 文書全体の体裁統一や無関係な文言修正を行わないでください。
- Agent、Skill、Orchestratorを起動しないでください。
- テスト、Git commit、pushを実行しないでください。

完了時は、変更したファイル、通常経路から外した管理義務、維持した正本だけをチャットで報告してください。
```

### Step 5: 品質確認ルールを変更リスク基準へ変更

#### 目的

管理作業を減らしても、プロダクト品質を維持できる検証方法へ切り替える。

#### 実施内容

- 変更ファイルと直接関係するテストを標準検証とする。
- 共通基盤、永続化、注文、ポジション、金額計算、削除処理では、影響範囲を広げて検証する。
- UI変更では、主要操作、二重送信、エラー表示、必要なアクセシビリティを確認する。
- 外部API境界はmockまたはlocal fixtureで確認し、実接続は明示許可時だけ行う。
- 全テスト、全HTMLリンク検査、全設計レビューは、影響範囲が広い場合またはユーザー指定時だけ行う。
- テスト結果はチャットへ簡潔に報告し、証跡ファイルへ複製しない。

#### 完了条件

- 変更リスクに対応したテスト基準がルール化されている。
- 「管理文書を作ったため品質が高い」という判定がなくなっている。
- 重大な取引・データ処理に必要な検証は維持されている。

#### AIエージェント実行プロンプト

### Step 6: Git運用を機能単位へ変更

#### 目的

Step単位のcommit、push、Git報告をやめ、製品変更の意味が分かる単位へまとめる。

#### 実施内容

- Stepごとのcommit義務を解除する。
- 通常は機能または修正が完了した単位でcommitする。
- pushはユーザー指定時または機能完了時に限定する。
- 文書同期やreceipt追加だけを目的とするcommitを作らない。
- commit前に今回変更だけを確認し、既存のユーザー変更を混ぜない規則は維持する。
- ユーザーが「ファイル生成のみ」と指定した場合、commitとpushを実行しない。

#### 完了条件

- 一つの機能に対して管理用commitが連続しない。
- 指定された作業範囲をGit処理が越えない。
- 既存変更の保護は維持されている。

#### AIエージェント実行プロンプト

```text

Step 1で特定したGit運用ルールを、Step単位のcommit・pushから、ユーザーの依頼範囲と機能完了単位を尊重する方式へ変更してください。

必須要件:
- Stepごとのcommit義務を解除してください。
- 通常は、機能追加または不具合修正が完了した意味のある単位でcommitする方針にしてください。
- pushは、ユーザーが依頼した場合、またはユーザーの依頼範囲に機能完了時のpushが明確に含まれる場合だけにしてください。

禁止事項:
```

### Step 8: 静的確認と小規模な運用確認

#### 目的

新運用が管理タスクを自動発火させず、製品品質のための作業を阻害しないことを確認する。

#### 実施内容

- 変更したルールファイルに矛盾した必須表現が残っていないか検索する。
- Markdownの最低限の構文と参照先を確認する。
- 次の想定依頼に対して、期待される動作をルールから確認する。

| 想定依頼 | 期待される動作 |
|---|---|
| 「この不具合の原因を調べて」 | 読み取りと原因報告だけを行う |
| 「この不具合を修正して」 | 実装と関連テストを行う |
| 「この仕様書だけ直して」 | 指定仕様書だけを変更する |
| 「UIを変更して」 | UI、関連テスト、必要なマニュアルだけを変更する |
| 「計画をチャットで示して」 | ファイルを作らずチャットに回答する |
| 「計画書をmdで作って」 | 指定されたMarkdownだけを作成する |
| 「実データをダウンロードして」 | 外部I/Oの実行前に確認する |
| 「既存データを物理削除して」 | 対象と復元可否を確認してから実行する |

- この確認のためのreceipt、評価票、証跡ファイルは作成しない。

#### 完了条件

- 通常タスクから管理専用成果物が自動生成されない。
- 製品品質に必要なテスト、安全確認、ユーザー確認は残っている。
- 指定成果物だけを作成する依頼に、余分なGit操作や文書更新が付随しない。

## 7. 実行時の変更原則

移行作業そのものが新たな過剰管理にならないよう、次の原則を適用する。

- 本計画を細分化した追加計画書は作らない。
- 本計画内にユーザー指定で記載した各Stepの実行プロンプトだけを使用し、別ファイルのプロンプト集は作らない。
- Agent、Orchestrator、Human Gateは使用しない。
- runtime receipt、作業ログ、完了packetは作らない。
- 変更内容を別の台帳へ転載しない。
- 必要なルールファイルだけを直接変更する。
- 確認結果は最終回答で簡潔に報告する。
- 移行作業は可能な限り一つの実装タスクとして完了させる。

## 8. 品質を維持するために残す制約

次の制約は管理品質ではなく、プロダクト、データ、利用者を守るために必要なので維持する。

- 無関係なユーザー変更を上書きしない。
- Secret、鍵、認証情報を成果物やログへ含めない。
- 実取引、外部接続、費用発生、Secret利用は明示許可なしに行わない。
- 重要データの削除前に、対象と影響範囲を確認する。
- 変更内容に応じたテストを行う。
- 取引、金額、ポジション、データ整合性に関わる変更はfail-closedで扱う。
- 問題を診断する依頼と、修正を実装する依頼を区別する。
- 指定範囲を超える変更が必要な場合は、実行前にユーザーへ説明する。

## 9. 移行完了の受入条件

以下をすべて満たした時点で移行完了とする。

1. 通常タスクの標準モードがPRODUCT_ONLYになっている。
2. Phase計画、Agent、Skill、Orchestratorが通常タスクの必須条件から外れている。
3. Human Gateが、実害のあり得る操作と重要な製品判断に限定されている。
4. runtime receipt、hash管理、実行証跡、完了packetが通常の成果物から外れている。
5. コード変更では、変更リスクに応じた関連テストが引き続き必要とされている。
6. 仕様書とマニュアルは、製品仕様または操作が変わる場合だけ更新される。
7. 指定成果物だけを作成する依頼では、それ以外のファイルやGit状態を変更しない。
8. 同じ情報を複数の文書、台帳、ログへ転載する義務がない。
9. 外部接続、実取引、費用、Secret、重要データ削除の安全確認が残っている。
10. 移行のための新しい管理文書、receipt、Gate、台帳が追加されていない。

## 10. 実行依頼文

本計画を実行するときは、次の依頼文だけで開始できるものとする。

> `plan/軽量開発運用への移行計画書.md`に従い、プロジェクトの標準運用をPRODUCT_ONLYへ移行してください。管理専用の新規成果物、Agent起動、Human Gate、runtime receipt、hash管理、追加計画書、実行ログは作成せず、必要なルールファイルの変更と最小限の静的確認だけを行ってください。

この依頼の実行後は、通常の製品開発を、コード、関連テスト、必要な仕様・マニュアル、簡潔なチャット報告だけで進められる状態とする。
