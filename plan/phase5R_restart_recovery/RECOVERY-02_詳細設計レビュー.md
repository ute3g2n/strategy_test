# RECOVERY-02 実装詳細設計レビュー記録

- 実行日: 2026-08-16
- 対象: `doc/phase5R/02_実装詳細設計/03_再起動後バックテスト履歴復元実装詳細設計書.html`
- レビュー方法: 独立Agent起動失敗後のルート責務チェックリストによる代替レビュー
- 独立レビュー状態: `SELF_REVIEW_FALLBACK`
- 判定: `CONDITIONALLY_ACCEPTED_FOR_RED_TESTS`

## 前提事実

1. 現在のHTTPサービスは、プロセス起動時に `BacktestProductService` を新規生成する。
2. 現在の履歴一覧は `_runs` というメモリ上の辞書だけを読む。
3. `result.json` はEドライブに残るが、結果を履歴として読み戻す処理はない。
4. P4の `MetadataStore` は既定値がインメモリSQLiteで、現在のP5R HTTP履歴の永続化契約とは接続していない。

## チェックリスト

| 観点 | 確認内容 | 判定 | 根拠／対応 |
|---|---|---|---|
| 要件追跡 | 再起動後の一覧・詳細・行・比較・CSV・復旧状態が要件とテストへ結び付く | PASS | 設計書のREQ-R01〜REQ-R08、RECOVERY-T-01〜T-10 |
| 永続化 | Cドライブや一時領域を使わず、Eドライブ配下へ原子的に保存する | PASS | `storage_paths.py` のEドライブ契約、catalog JSON案 |
| 旧データ | 既存の結果JSONだけを壊さず、旧形式は推測を明示して読み込む | PASS | `LEGACY_RESULT_ONLY` 分類と未知値明示 |
| 不完全状態 | QUEUED／RUNNING／CANCELLEDの旧プロセス状態を勝手に成功扱いしない | PASS | `RECOVERY_REQUIRED` として表示する設計 |
| 破損耐性 | 1件のJSON破損で全履歴を消さず、該当件だけ問題として報告する | PASS | ファイル単位の例外隔離とRecoveryReport |
| データ整合性 | カタログのrun_idと結果JSONのrun_idを照合する | PASS | 不一致を復旧必須へ分類 |
| 秘密情報 | 設計・カタログにAPIキー、パスワード、トークンを保存しない | PASS | 保存項目を仕様・結果・メトリクスに限定 |
| 書込み安全 | 途中でプロセスが落ちても完成前JSONを正式ファイルとみなさない | PASS | 同一ディレクトリのwritingファイルからreplaceする契約 |
| API互換 | 既存のhistory／detail／rows APIの形を壊さない | PASS | 既存ビュー項目を保持し、recovery APIを追加 |
| UI理解性 | 起動直後に履歴を読み、復旧が必要な件を平易な警告で知らせる | PASS | UI契約に初期ロードと警告を記載 |
| レース | 実行中のスナップショットを保存し、端末停止後は自動再開しない | PASS | 状態保存と明示的な再実行方針 |
| 大量データ | 全履歴を無制限にメモリへ読み込む上限・整理方法が未確定 | OPEN | UNK-R05。今回の最小実装では既存UI互換を優先し、計測と上限を後続課題へ記録 |
| 保持・バックアップ | Eドライブ障害時のバックアップ／世代管理が未確定 | OPEN | UNK-R06。今回の受入条件には含めないが台帳で追跡 |
| P4 DB統合 | SQLiteへ統合するか、ファイルカタログを維持するか | OPEN | UNK-R01。今回の機能ではファイルカタログを採用 |

## 実装へ進む条件

- `RECOVERY-T-01`〜`RECOVERY-T-10` のREDテストを追加する。
- RED確認後に、設計書のJSON契約と既存API互換を満たす最小実装へ進む。
- 大量データ上限、バックアップ、P4 DB統合は、今回の履歴復元の完了条件に混ぜない。
- 旧形式を復元した結果は、完全な実行条件が分からない限り `LEGACY_RESULT_ONLY` と表示する。
