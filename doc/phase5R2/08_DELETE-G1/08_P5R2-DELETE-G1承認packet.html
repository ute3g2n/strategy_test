このpacketは、削除機能を実行するものではない。
ここで判断するのは、画面から結果表示を削除するときに、どのResultArtifactだけを物理削除してよいかである。Historical Data、Run本体、Export済みCSV、Audit、Evidenceを一緒に消す許可は、このpacketに含めない。
承認結果：APPROVED_BOUNDED_P5R2_21_FIXTURE_ONLY
移譲されたHuman Gate権限に基づき、P5R2-21の実装と、新規一時fixtureだけを使う物理削除受入を承認する。通常のResultArtifact削除契約はこのpacketの制約内で実装してよいが、既存の実Data／Run／CSV／Audit／Evidenceへ物理操作を行ってはならない。P5R2-H2、P6開始、外部Provider利用、Secret、費用は承認しない。

1. 利用者の確定方針

確認された方針P5R2での契約
画面に表示したい結果は残す。必要な結果はCSVへExportする。画面上の結果を削除する前に、CSVを先にExportする注意を表示する。Export済みCSVはResultArtifact削除の対象外とする。
古い結果は基本的に見ず、復元予定もない。物理削除後のrestore APIは作らない。削除後はAudit上のRESULT_DELETED記録だけを残す。
二重押下はフロントエンドで禁止する。UIの押下中無効化に加え、server側でも同じoperation tokenを冪等処理し、別tokenの同時要求もlockで直列化する。
削除後に古いBacktest結果が変わってもよい運用を想定する。このGateは結果Artifactの削除だけを扱う。Historical Dataのmerge／replaceやRun再実行の扱いは別契約であり、削除に連動させない。

2. 承認した範囲

アプリの通常ResultArtifact削除契約を実装し、P5R2-21の物理削除受入は新規に作成した一時fixtureだけで行う。既存の利用者Dataを実際に消す試験は行わない。

項目承認範囲制限
削除できるもの利用者が明示したterminal状態のBacktest結果ResultArtifactディレクトリだけartifact_kind=RESULT、RunがSUCCEEDEDまたは明示されたterminal failure、active／recovery中でないこと。
論理IDRESULT-<safe_run_id>のlogical result_artifact_id呼出元からpathを受け取らず、台帳／Run IDからサーバーが解決する。別ID、空ID、traversalは拒否する。
許可rootサーバーが設定したBacktest runtimeのResultArtifact root（テスト時は新規fixture root）ブラウザ指定rootや任意絶対pathを採用しない。root外は拒否する。
物理削除の受入対象tests/evidence/phase5R2/RUN-P5R2-21-DELETE-LOCAL-001/delete-fixture/配下で新規作成したResultArtifact既存Evidence、既存Data、既存Run、既存CSV、既存Auditはfixtureに含めず、削除対象にもできない。
確認操作UIの明示確認、CSV先行注意、押下中無効化確認なし、active Run、Export中、保持指定中は拒否する。

3. 削除対象と、絶対に保護するもの

対象扱い理由
terminal ResultArtifact承認済み（P5R2-21限定）。対象ディレクトリ内のresult.json、result.commit.jsonなど結果表示専用ファイルだけを削除する。利用者が結果画面から削除したい対象だから。
Export済みCSV常に保護。CSV Job、Export先、利用者が指定したCSVはcascade削除しない。利用者が保存しておくと決めた成果物だから。
Historical Data / Catalog常に保護。source、derived、Catalog current、staging、quality情報を削除しない。他のRunや再計算に共有される入力Dataだから。
Run本体・Run manifest常に保護。Runの一覧、設定、状態、cancel記録を削除しない。後から何を実行したかを確認する台帳だから。
Audit常に保護。削除成功・失敗・拒否・操作IDを残す。誰がいつ削除を要求したかを確認できるようにするため。
Evidence / screenshot / quality receipt常に保護。P5R2のEvidence rootを削除対象rootにしない。品質確認の証拠を消すと、合否を再確認できなくなるため。
保持選択中・Export中・active／RECOVERY_REQUIRED拒否。ResultArtifactも削除しない。処理途中や復旧中のデータを壊さないため。

4. サーバー側の物理対象解決

削除APIは、ブラウザからファイル名やpathを受け取らない。次の順でサーバーが対象を解決し、1つでも不一致があればfail-closedで停止する。

  1. logical_result_artifact_id、operation_token、request_id、明示確認を受け取る。
  2. logical IDからRun／Artifact台帳を解決し、Artifact種別、Run状態、CSV状態、保持選択、削除済み状態を確認する。
  3. 台帳のRun IDから、サーバー設定の固定root配下にあるcanonical pathを組み立てる。呼出元指定のpath、absolute_path、target_pathは受け付けない。
  4. root自身、すべての親ディレクトリ、対象ディレクトリ、配下ファイルについてsymlink／Windows reparse pointを検査する。検査不能なら削除しない。
  5. ..、root外、任意absolute path、別Run、ID不一致、active Run、TOCTOU（検査後の対象差替え）を拒否する。
  6. 検査を通過したときだけDELETE_PENDINGをAuditへ記録し、サーバー側lock下で対象の同一性を再確認してから物理削除する。

Windowsではjunctionやreparse pointを通常のフォルダとして扱わない。Linux／WSLでもsymlinkを実体とみなさない。削除のために管理用hash、manifest hash、fingerprint、stale判定を新設しない。

5. 状態、失敗、再起動、同時要求

状態意味次の扱い
DELETE_PENDING対象と保護境界の確認を終え、削除直前である。UIは押下中無効。再起動後にpendingだけ残った場合は自動で再削除せず、DELETE_FAILEDまたは要確認として停止する。
RESULT_DELETEDResultArtifactだけの物理削除が完了した。結果画面から非表示にし、Audit／tombstoneを残す。restore APIは提供しない。同じ要求の再送は成功済みとして冪等に返す。
DELETE_FAILED対象の一部または全部を削除できなかった。cascadeを続けず、保護対象を変更しない。原因と対象をAuditへ残し、再試行は新しい明示操作として安全確認からやり直す。
同一operation token二重押下または同じ要求の再送。最初の結果を返し、二度目の物理操作をしない。
別operation tokenの同時要求別tabや二重操作。server lockで直列化し、先に削除済みなら後続は物理操作をせず既存tombstoneを返す。
停止条件：部分削除、対象差替え、path検査不能、root不一致、Audit保存失敗、保護対象混在、active／recovery状態、CSV Export中、承認範囲外の実Dataが検出された場合は、そこで停止する。別のファイルへ広げたり、復元処理を自動開始したりしない。

8. 運用者向けのやさしい説明

結果画面の「削除」は、計算に使った材料を全部消す操作ではありません。画面に出ている計算結果のファイルだけを消します。

消す前に、必要ならCSVへ保存します。保存したCSV、元のHistorical Data、実行記録、監査記録、品質確認の証拠は残します。

実行中や復旧中のものは消せません。削除ボタンを連続で押しても、サーバーが二回消さないようにします。削除後に元へ戻す機能はありません。

このpacketの承認後も、本番で既に存在するDataを使って削除試験はしません。まず新しく作った練習用の一時ファイルだけで、安全確認をします。
