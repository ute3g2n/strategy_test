バックテスト手順書

この手順書の目的：画面のボタンを押したとき、実際のP5R Application APIがローカルDataを読み、計算した結果・進捗・失敗理由を画面に返していることを、誰でも同じ順番で確認できるようにする。画像は、Playwrightが画面の確認に成功した直後に撮影した実画面である。

1. まず知っておく安全範囲

項目P5Rで使うもの使わないもの
Data既存P5 EvidenceのローカルData。BTCUSDT / ETHUSDT、Spot、1分足、UTC、CRYPTO_24_7_UTC。インターネットからの新規取得、別Provider、未承認Data。
実行過去の完成Barを順番に既存Strategy Coreへ渡し、選択したTurtle SystemのSignalを使って再生する仮想Fill Backtest。Broker接続、Secret、実注文、実資金、Paper、Live。
数字総損益、最大ドローダウン、勝率、取引回数、最終残高。将来の利益保証、実市場で同じ約定になるという保証。
費用手数料・Slippageの明示的な想定値。市場で実際に発生したコストの断定。
期間[2025-02-24T00:00:00Z, 2026-08-01T00:00:00Z) のP5R許可範囲。期間外、未来のData、UTCでない日時。
停止したら無理に進めない：PreflightのFAIL、Data由来が不明、Core検証停止、CSVの結果未完了、Holdoutの確定前アクセスなどは、失敗ではなく「安全のため止まった」状態である。画面に出た停止理由をEvidenceへ残して条件を直す。
Strategyの確認：画面で TURTLE_SYS1 または TURTLE_SYS2 を選ぶと、その選択とEntry／Exit期間がStrategy Coreへ渡される。結果Ledgerの「理由」には、Coreが返した SYS1_ENTRY、SYS2_ENTRY、EXIT_LONG などが表示される。画面の数字だけでなく、この理由まで確認する。

2. 起動前の準備

  1. プロジェクトのルートで、品質確認済みのローカル環境を使う。外部市場Dataを取得するコマンドは実行しない。
  2. Application APIを py -3 scripts/phase5r/backtest_api_server.py --port 8765 で起動する。
  3. UIを ui/mock で npm run build 後、npm run preview -- --host 127.0.0.1 で起動する。Playwright実行時はこの2つを自動起動できる。
  4. ブラウザで http://127.0.0.1:4173 を開き、左の「Backtest条件設定」を選ぶ。
  5. 画面上部の「外部市場データ、Broker、Secret、実注文、Paper／Liveには接続しません」を確認する。

正式なAPI、状態、保存、停止条件はP5R実装詳細設計書、品質GateとRun ManifestはP5R品質Gate_RunManifest設計書を参照する。

各画像は ui/mock/tests/p5r-backtest.spec.ts が、先に画面の要素・状態・停止理由をassertし、その直後にPlaywrightで撮影した。デスクトップ画像を本文に載せ、モバイル画像と全capture情報はEvidenceへ保存した。

BT-MAN-01：Backtest画面を開き、範囲を確認する

ゴール：画面が固定ダミーの結果ではなく、P5R Application APIを使う画面であることを確認する。

  1. 左メニューの「Backtest条件設定」をクリックする。
  2. 「P5R実行範囲」にBTCUSDT / ETHUSDT、Spot / 1m / UTC、期間が表示されることを確認する。
  3. 安全境界に、外部Data、Broker、Secret、実注文、Paper／Liveへ接続しない説明があることを確認する。

異常時：対象外銘柄やP5R外の機能が実行できるなら、P5R-H2へ進めず、画面と理由を記録する。

BT-MAN-02：Preflightを通す

ゴール：実行前に、入力・範囲・UTC・Calendar・Data品質・先読み防止の確認がPASSになる。

  1. 初期値のまま「Preflight実行」をクリックする。
  2. TYPE_AND_UNIT、P5_DATA_SCOPE、UTC_AND_CALENDAR、QUALITY、LOOKAHEAD がPASSであることを読む。
  3. 「Preflight PASS。実Runを開始できます。」を確認する。

BT-MAN-03：不正なUTC入力を安全に止める

ゴール：日時に Z がないなど、UTCと確定できない条件をRun開始前に止める。

  1. 「開始（UTC）」を 2025-02-24T00:00:00 に変更する。
  2. 「Preflight実行」をクリックする。
  3. STOPPEDと停止理由を確認する。停止したまま「Single Run開始」を押してはいけない。
  4. 値を 2025-02-24T00:00:00Z に戻して、もう一度Preflightする。

BT-MAN-04：Single Runを開始し、進捗を見る

ゴール：画面上で生成されたRun ID、QUEUED／RUNNING／SUCCEEDED、進捗Bar数、ETAを確認する。

  1. Preflight PASS後に「Single Run開始」をクリックする。
  2. 「実Run」に RUN-P5R-... が表示されることを確認する。
  3. 状態、進捗率、処理済みBar数／全Bar数、ETAを確認する。画面を勝手に成功へ書き換えていないことが重要である。
  4. SUCCEEDEDになるまで待つ。待機中にブラウザを閉じる場合は、Run IDを記録する。

BT-MAN-05：5つの指標を読む

ゴール：同じRunの結果として、5指標が表示される。

  1. RunがSUCCEEDEDになったら、総損益を初期残高との差として読む。
  2. 最大ドローダウンは、残高が過去最高からどれだけ下がったかを読む。
  3. 勝率は、確定した売買のうち利益が正だった割合である。
  4. 取引回数はVirtual Fill回数、最終残高は最後の評価残高である。
  5. fee／slippageが想定値であることを確認し、数字だけを見て利益を保証されたと判断しない。

BT-MAN-06：DetailsとLedgerを確認する

ゴール：指標だけでなく、Signal・Virtual Fill・残高が同じRunの時系列から得られたことを確認する。

  1. 「結果・詳細を表示」または「Detailsを読込」をクリックする。
  2. Data由来、期間、Data範囲、Core検証が表示されることを確認する。
  3. Ledgerで種類、UTC時刻、銘柄、Signal、方向、価格、Equity、理由を読む。
  4. 必要なら表の全行をCSVで出す。画面に見えない行を想像で補ってはいけない。

BT-MAN-07：実行中に取消する

ゴール：処理途中のRunを取消し、CANCELLEDとcheckpointを確認する。

  1. 終了日時を少し長い期間にしてRunを開始する。
  2. RUNNING中に「取消」をクリックする。
  3. 状態がCANCELLEDになり、停止理由とcheckpointが残ることを確認する。
  4. 取消したRunを成功扱いに変更したり、結果を推測して読んだりしない。

BT-MAN-08：checkpointから再開する

ゴール：保存された途中状態から再開し、再開回数と最終状態を確認する。

  1. CANCELLEDでcheckpointが表示されているRunの「チェックポイントから再開」をクリックする。
  2. QUEUED／RUNNINGへ戻ることを確認する。
  3. SUCCEEDEDになったら、再開回数が1以上であることを確認する。
  4. 結果を最初から作り直したのではなく、途中状態から続いたことをRun IDと証跡で確認する。

BT-MAN-09：Sweepの部分失敗を見る

ゴール：複数候補を一つの親Jobとして動かし、子Runの一部失敗を隠さない。

  1. 「Sweep」タブを開く。
  2. 候補数、候補値、重複検査の説明を確認する。最大200候補である。
  3. 「2番目の候補を意図的に失敗させる」をONにしてSweepを開始する。
  4. 親Jobの状態がPARTIAL_FAILED、成功した子と CANDIDATE_FORCED_FAILURE の子が表示されることを確認する。

BT-MAN-10：履歴からRunを開く

ゴール：過去に作ったRunを履歴から選び、状態・条件・結果を再表示する。

  1. 「履歴・比較」タブを開き、「履歴を更新」をクリックする。
  2. Run ID、銘柄、Strategy、期間、状態、進捗を確認する。
  3. 対象Runのラジオボタンを選び、「結果を開く」をクリックする。
  4. 履歴にないRunを成功扱いにしてはいけない。

BT-MAN-11：2つのRunを比較する

ゴール：条件の異なるRunを並べるが、最良RunやLive昇格を自動で決めない。

  1. 履歴から比較対象とは別のRunを選ぶ。
  2. 「選択Runと比較」をクリックする。
  3. comparable と条件差の理由を確認する。
  4. 総損益だけでなく、最大DD、勝率、取引回数、最終残高、条件を一緒に読む。
  5. 比較結果から自動的に本番へ進むボタンがないことを確認する。

BT-MAN-12：CSVを生成してダウンロードする

ゴール：完了済みRunのLedgerをCSV Jobにし、完了後にDownload導線を表示する。

  1. SUCCEEDEDのRunを選ぶ。
  2. 「CSV生成」をクリックする。
  3. CSV Jobの状態と進捗が表示され、SUCCEEDEDになることを確認する。
  4. 「CSVダウンロード」リンクが表示されたら、必要な列とRun IDを記録して保存する。
  5. 結果未完了のRun、対象外の列、別RunのCSVを混ぜない。

BT-MAN-13：確定前Holdoutを止める

ゴール：HoldoutをStrategy調整に使う前に、確定前アクセスを拒否する。

  1. 「Holdout・Walk-forward」タブを開く。
  2. 「確定前を試す」をクリックする。
  3. EARLY_HOLDOUT_ACCESS と停止表示を確認する。
  4. この期間の結果を使ってパラメータを調整してはいけない。

BT-MAN-14：確定後Holdoutを一度だけ評価する

ゴール：確定後のHoldoutを評価用として一度だけ読み、調整に再利用しない。

  1. 「確定後に評価」をクリックする。
  2. SUCCEEDED、期間、行数、調整へ再利用しない表示を確認する。
  3. 同じApplication APIで再度押して、二重読込がSTOPPEDになることも確認できる。
  4. Holdoutの成績は、学習期間の成績と別の確認として記録する。

BT-MAN-15：Walk-forwardを実行する

ゴール：学習・検証・評価を時間順に分けた3つの窓を実行し、未来参照なしを確認する。

  1. 3窓の学習終了、検証終了、評価終了の日時を読む。
  2. 「Walk-forward実行」をクリックする。
  3. SUCCEEDED、窓3、holdout再利用=false を確認する。
  4. 窓の時刻が逆順、重複、P5R範囲外なら停止される。
  5. Walk-forwardが良かったことだけを理由にLive開始を決めない。Liveは後続PhaseのHuman Gateである。

4. 失敗時の読み方

表示される理由意味次にすること
Preflight STOPPED入力、範囲、UTC、品質などが条件外。画面のchecksとfailure codeを記録し、入力を修正する。
CORE_VALIDATION_...既存Backtest Coreが受け付けなかった。結果を成功扱いにせず、Coreの停止理由を調査する。
CANDIDATE_FORCED_FAILURESweepの候補を意図的に失敗させた例。親JobがPARTIAL_FAILEDであることを確認する。
RESULT_NOT_READYRunが終わる前にDetails／CSVを読もうとした。SUCCEEDEDまで待ち、同じRun IDで再試行する。
EARLY_HOLDOUT_ACCESSHoldoutを早く見ようとした。調整へ使わず、確定後評価まで待つ。
WALK_FORWARD_OVERLAP窓の時間が重なり、未来の情報が混ざる可能性がある。学習・検証・評価の順序と期間を修正する。
