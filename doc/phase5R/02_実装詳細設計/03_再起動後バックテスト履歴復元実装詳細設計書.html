再起動後バックテスト履歴復元 実装詳細設計書

やさしい要約：今のアプリは、バックテストの答案をEドライブへ保存しているが、「どの答案があるか」をアプリ起動時に読み直していない。この設計では、答案本体の result.json と、名前・条件・状態・保存場所を書いた履歴カタログを同じEドライブへ置く。アプリが再起動したらカタログと答案を照合し、過去のRunを画面へ戻す。途中で壊れた答案は成功扱いにせず、確認が必要な状態で止める。

1. 目的・対象・非対象

対象は、P5RのローカルBacktest Application APIとUIである。Windows再起動、APIプロセス停止・再起動、ブラウザの再読込後でも、完了したRunの履歴・指標・provenance・Ledgerを画面から再取得できるようにする。

項目定義今回の扱い
対象要件REQ/P5R-AC-06-R、REQ/P5R-AC-09-R、REQ/P5R-AC-10-R、REQ/P5R-AC-11-R履歴・結果・Ledger・比較・CSVの再起動後利用を実装し、pytestとPlaywrightで受入する。
結果本体Runの指標、取引行、Data由来E:\strategy_test_data\autotrade\backtest\results\<run_id>\result.jsonに保存する。
履歴カタログRun ID、条件、状態、時刻、結果参照E:\strategy_test_data\autotrade\backtest\catalog\runs\<run_id>.jsonに保存する。
対象外Broker、外部Data、Secret、実注文、実資金実装・テストで接続しない。
対象外途中Runの完全な再起動後resumeStrategyStateを完全保存する設計が別途必要なため、再起動後はRECOVERY_REQUIREDにする。
対象外P4の汎用SQLite MetadataStoreとの統合契約が異なるため今回接続しない。将来判断はUNK/P5R-RECOVERY-001。

2. 用語

用語中学生向けの意味技術上の意味
Run1回分の過去問の答案1回のBacktest実行と、その条件・状態・結果。
結果本体答案の中身metrics、rows、provenanceを含むJSON。
履歴カタログ答案の名前と置き場所を書いた台帳起動時に読み込み、RunViewを再構成するJSON記録。
復元保存した答案をアプリの画面へ戻すことディスク上のカタログ・結果を検査し、メモリ上の_Runへ変換すること。
原子的書込み書きかけの答案を完成品と間違えない保存方法同じディレクトリへ書き込み完了後、os.replaceで完成名へ切り替える。
RECOVERY_REQUIRED答案に問題があるので確認が必要な状態保存物の欠落・破損、または再起動後に安全に再開できない状態。

5. 保存場所と保存形式

保存場所は既存のApplication storage boundaryを使う。既定のルートはEドライブで、CドライブやWindows一時フォルダへの代替保存を行わない。テストでtmp_pathを使う場合は、明示的なruntime_rootとしてのみ使う。

保存物相対場所役割上書き規則
結果本体results/<run_id>/result.jsonmetrics、rows、provenance同じ完了Runの結果本体は上書き禁止。書き込み完了後に公開する。
Runカタログcatalog/runs/<run_id>.jsonRunViewの履歴情報実行状態の更新は同じRunのレコードを原子的置換する。書きかけ名は読込対象外。
CSVexports/<job_id>/result.csv復元Runから再生成した表既存Jobの完成CSVを上書きしない。
回復問題プロセスメモリとGET /api/backtest/recovery壊れた保存物を黙って隠さない管理用hashやmanifestは作らない。

5.1 新RunカタログのJSON契約

次の表は、実装者がどの値を保存し、何を必須とするかを判断するためのもの。JSONの説明用例であり、実在Runの値を固定するものではない。

{
  "schema": "autotrade-backtest-history/v1",
  "run_id": "RUN-AUTOTRADE-EXAMPLE",
  "kind": "SINGLE_BACKTEST",
  "parent_id": null,
  "status": "SUCCEEDED",
  "progress": 150,
  "total": 150,
  "started_at": "2026-08-16T08:00:00Z",
  "ended_at": "2026-08-16T08:00:02Z",
  "spec": { "symbol": "BTCUSDT", "market": "SPOT", "timeframe": "1m", "timezone": "UTC", "calendar": "CRYPTO_24_7_UTC", "start": "2025-02-24T00:00:00Z", "end": "2025-02-24T02:30:00Z", "strategy": "TURTLE_SYS1", "parameters": {} },
  "metrics": { "total_pnl": "0.0000", "trade_count": 0 },
  "provenance": { "source_mode": "P5_LOCAL_READ_ONLY" },
  "failure": null,
  "checkpoint": null,
  "resume_count": 0,
  "recovery_mode": "NORMAL",
  "result_reference": "results/RUN-AUTOTRADE-EXAMPLE/result.json"
}
項目型必須検査
schema文字列必須autotrade-backtest-history/v1だけを受け入れ、未知版は問題として報告する。
run_id安全なID文字列必須ファイル名、結果本体のrun_id、カタログのrun_idが一致すること。
specJSON object新形式では必須通常のRun作成時に検証済みのspecを保存する。Secret禁止検査を再利用する。
status状態文字列必須既知状態以外は成功扱いしない。QUEUED／RUNNING／CANCELLEDは再起動後にRECOVERY_REQUIREDへ変換する。
metricsobjectまたはnull状態に応じるSUCCEEDEDでは結果本体のmetricsと整合すること。
provenanceobjectSUCCEEDEDでは必須Data由来・仮定・期間を保持する。利益保証を追加しない。
result_reference相対文字列SUCCEEDEDでは必須絶対パス、UNC、..、results外、別run_idの参照を拒否する。
recovery_mode文字列任意NORMAL、LEGACY_RESULT_ONLY、RECOVERY_REQUIREDを識別する。

6. 起動時復元の処理順

sequenceDiagram
  participant P as API process
  participant S as BacktestProductService
  participant C as HistoryCatalog
  participant R as result.json
  participant U as UI
  P->>S: constructor(runtime_root)
  S->>C: load catalog/runs/*.json
  C-->>S: valid records + recovery issues
  loop each catalog record
    S->>R: read referenced result
    R-->>S: metrics / rows / provenance
    S->>S: validate IDs, paths, schema, status
  end
  S->>C: scan legacy results without catalog
  C-->>S: legacy result candidates
  S->>S: reconstruct _Run objects
  U->>P: GET /api/backtest/runs/history
  P->>S: list_runs()
  S-->>P: RunView list
  P-->>U: history items

6.1 復元アルゴリズム

1. catalog/runs/*.jsonだけを列挙する。書きかけ名・ディレクトリは読まない。
2. ファイル名からrun_idを取り出し、安全なIDか確認する。
3. JSON、schema_version、run.run_idの型と一致を確認する。
4. result_referenceをruntime_rootから解決し、results配下から出ないことを確認する。
5. statusがSUCCEEDEDならresult.jsonを必須とし、run_id、metrics、rows、provenanceを検査する。
6. statusがQUEUED/RUNNINGなら、古いthreadを復元せずRECOVERY_REQUIREDへ変換する。
7. statusがCANCELLEDでcheckpointしかない場合も、StrategyStateなしのresumeを許可せずRECOVERY_REQUIREDへ変換する。
8. statusがFAILEDならfailureを保持して一覧へ戻す。
9. catalogがないresults/<run_id>/result.jsonは旧形式として読み、既知値だけでLEGACY_RESULT_ONLY Runを作る。
10. 壊れた入力はRecoveryReportへ追加し、SUCCEEDED一覧から成功扱いで返さない。
11. 復元したRunを_process内の_runsへ登録する。

7. 状態と失敗時の扱い

検出状態RunViewの扱いユーザーへの意味停止理由
catalog/result一致保存された状態を保持過去の結果を通常表示できるなし
旧形式resultのみSUCCEEDED + legacy表示結果は見えるが、条件の一部は不明LEGACY_RESULT_ONLY
結果JSON欠落・破損RECOVERY_REQUIRED答案の中身を確認できないため成功扱いしないRESULT_REFERENCE_MISSING、RESULT_JSON_INVALIDなど
実行中にAPI停止RECOVERY_REQUIRED途中計算を勝手に成功・再開しないINCOMPLETE_AFTER_RESTART
パス・ID不一致RECOVERY_REQUIRED + RecoveryReport別Runの結果を取り違えないRESULT_REFERENCE_OUT_OF_SCOPE、RESULT_REFERENCE_MISMATCHなど

8. API契約

既存の履歴APIのURLは変えない。新しいRecovery APIは、管理者や手順書が「復元で問題が起きていないか」を確認するための読み取り専用窓口である。

Endpoint入力成功出力失敗・停止副作用
GET /api/backtest/runs/historyなし{items: RunView[]}サービス内部の復元問題を隠さない。API自体は応答する。なし
GET /api/backtest/runs/:id安全なrun_id復元済みRunView不明IDは404、RECOVERY_REQUIREDは状態とfailureを返す。なし
GET /api/backtest/runs/:id/rows安全なrun_id{items: LedgerRow[]}結果欠落は回復エラー。空配列を正常完了の証拠にしない。なし
GET /api/backtest/recoveryなし{status: CLEAN|RECOVERY_REQUIRED, issues: [...], recovery_required_run_ids: [...]}JSON本文にSecretを入れず、問題があれば一覧を正常扱いしない。なし
POST /api/backtest/csv-jobs復元済みSUCCEEDED run_id、列新しいCSV JobRECOVERY_REQUIRED、未完了、列不正は拒否。Eドライブexportsへ新規CSV保存。

9. UI契約

UIは計算を行わず、APIから返された復元結果を表示する。Backtest画面を開いた時点で履歴を取得し、履歴タブの「履歴を更新」でも再取得する。RecoveryReportに問題がある場合は、履歴が全て正常だと誤解させない注意表示を出す。

UI操作API成功表示問題時表示
Backtest画面を開くhistory + recovery履歴取得済みローカルAPIエラーまたは復元注意
履歴・比較タブGET historyRun ID、条件、状態、進捗RECOVERY_REQUIREDと理由を表示
結果を開くGET run、GET rows5指標、provenance、LedgerLedgerを取得できない理由を表示
CSV生成POST csv-jobs新しいCSV Job復元不完全Runは開始ボタンを使えない

10. 主要処理の擬似コード

def restore_history(runtime_root):
    records, issues = catalog.load_run_records()
    restored = {}
    for record in records:
        try:
            view = validate_catalog_record(record)
            if view.status in {"QUEUED", "RUNNING", "CANCELLED"}:
                view = mark_recovery_required(view, reason_for_restart(view.status))
            if view.status == "SUCCEEDED":
                result = read_result(view.result_reference)
                ensure_result_run_id(result, view.run_id)
                view.metrics = result["metrics"]
                view.rows = result["rows"]
                view.provenance = result["provenance"]
            restored[view.run_id] = build_run_without_thread(view)
        except RecoveryError as error:
            issues.append(error.report)
    for result_path in scan_legacy_result_files(runtime_root):
        if result_path.run_id not in restored:
            restored[result_path.run_id] = build_legacy_run(result_path)
    return restored, issues

11. テスト仕様

この表は、設計の各約束がどのテストで証明されるかを示す。各行には条件、操作、期待結果、合否判定を文章で記す。

ID条件操作期待結果合否判定
RECOVERY-T-01小さな合成OHLCVでRunを完了させ、同じruntime_rootを使う。サービスAでRunを作り、完了後にサービスBを生成してlist_runsを呼ぶ。サービスBの一覧にサービスAと同じRun IDがあり、状態がSUCCEEDEDになる。Run IDが一致し、重複がなく、別の新規Runを作っていない場合にPASS。
RECOVERY-T-02サービスAのmetrics、provenance、rowsを保存する。サービスBでget_runとget_rowsを呼ぶ。metricsとprovenanceが結果本体から戻り、rowsの件数と代表行が一致する。元と復元後で比較対象のJSON値が一致すればPASS。
RECOVERY-T-03復元後のRunがSUCCEEDEDである。compare_runsとcreate_csv_jobを実行する。比較結果が返り、新しいCSV JobがSUCCEEDEDになり、CSVを取得できる。既存結果を上書きせず、新しいJobのCSVが読めればPASS。
RECOVERY-T-04catalogなしの旧形式result.jsonを用意する。サービスを生成してlist_runs/get_run/get_rowsを呼ぶ。RunがLEGACY_RESULT_ONLYとして表示され、metrics/rowsが戻り、未知のspec値はUNKNOWN扱いになる。推測した作成時刻や条件を出さなければPASS。
RECOVERY-T-05JSON破損、ID不一致、results外参照、result欠落をそれぞれ用意する。サービス起動後にhistoryとrecovery reportを呼ぶ。成功Runとして採用されず、RecoveryReportに問題が出る。黙って消えず、RECOVERY_REQUIREDまたはissueが返ればPASS。
RECOVERY-T-06catalogのstatusをRUNNINGまたはCANCELLEDにする。サービスを再起動相当で生成する。旧threadは存在せず、自動成功・自動resumeされず、RECOVERY_REQUIREDになる。プロセスの外へ実行を続けるthreadがないことも確認してPASS。
RECOVERY-T-07実HTTP serverをloopbackで起動し、Run完了後にサーバーを停止する。新しいHTTP serverを同じstorageで起動し、history/detail/rowsを取得する。同じRun ID、指標、Ledgerが返る。HTTP status、JSON、件数が一致すればPASS。
RECOVERY-T-08UIとAPIをPlaywrightで起動し、Runを1件完了させる。APIだけを対象PIDで停止し、新APIを起動後、履歴タブ→結果を開く。再起動前のRun ID、5指標、Ledgerが表示される。DOM assertion後にスクリーンショットを取得し、外部通信0件ならPASS。
RECOVERY-T-09既定サービスとstorage_pathsを確認する。catalogパスを検証し、禁止候補を拒否する。既定catalogがEドライブのautotrade/backtest配下で、C/temp/tmp/phase5rを含まない。全パス条件と拒否条件が満たされればPASS。
RECOVERY-T-10UI journey中のrequestを監視する。Backtest画面、API、Vite以外へのrequestを記録する。外部URLへのrequestが0件である。外部request配列が空ならPASS。
