0. 先に結論：今回の推奨案

既存のPhase 2決定、P5のData contract、現在のAdapter境界、公式一次情報を合わせると、最初の実取得はDatabento Historical APIのCME系先物データだけに絞る案が最も安全である。

  1. Provider: Databento Historical API
  2. Dataset: GLBX.MDP3（CME、CBOT、NYMEX、COMEXのCME Globex MDP 3.0）
  3. 実取得対象: MCL、M6A、MZC、MZS、MZWの5つ。5つとも資産種類はfuturesである。
  4. Provider入力: MCL.FUT、M6A.FUT、MZC.FUT、MZS.FUT、MZW.FUTをparent symbologyで解決し、spreadを除外した現物の先物契約だけを採用する。
  5. 共通期間: 2025-02-24T00:00:00Z以上、2026-08-01T00:00:00Z未満。これは5候補のMicro契約を同じ条件で比較するための限定期間である。
  6. 時間足: 元データはohlcv-1m。そこからD1／H4／H1／M30／M15をシステム側で作る。
  7. 費用: 事前見積りは必須としない。1 Run上限25 USD、Historicalチーム月額上限50 USD、80%警告・100%停止、Provider／team側budget control、実行後usage監査を必須にする。
  8. Broker／Paper／Live／実資金／実Risk／Cloud: 今回の承認対象から除外する。

4資産種類について: futures／stocks／FX／cryptoはシステムが扱える構造上の4分類である。今回の5候補はすべてfuturesなので、stocks・FXスポット・cryptoの実Dataまで取得済みとは扱わない。これを広げる場合は別のData Gateが必要である。

1. P5-DATA-G1とは何か

一言で言うと、「外部の市場Dataを、どの会社から、何を、いつ、いくらまで、どこへ保存してよいかを、人間が事前に許可するチェックポイント」である。

たとえば「MCLを取ってください」だけでは不十分である。同じMCLでも、どの契約月か、どの期間か、どの時間足か、どの会社のDataか、費用はいくらか、保存してよいかが決まっていないと、あとから同じ結果を再現できない。

Gateやさしい意味今回の範囲
P5-H1固定したダミーData contractを安全に扱えるかの確認。外部Provider、Secret、費用、実Dataは含まない。
P5-DATA-G1外部Providerから実Dataを取得してよいかの許可。Provider、対象、期間、通信、費用、Secret、保存、Runnerをまとめて固定する。
P5-H2P5の実証結果を確認し、P6へData contractを渡してよいかの許可。外部Dataの取得後。P5-DATA-G1の代わりにはならない。

2. 申請項目を、誰でも分かる言葉にすると

この表は「その項目は何を決めるものか」「なぜ必要か」「空欄だと何が危ないか」を説明する。右端の停止コードが出たら、推測で埋めずに止める。

申請項目ひとことで言うとなぜ必要か空欄のまま進むと何が起きるか
対象Symbol／論理市場IDどの商品を取るか。「MCLという名前」だけでなく、システム内のIDとProvider側の名前を対応付けるため。別の商品を取っても気づけない。SCOPE_UNKNOWNで停止。
取引所／限月／契約どの市場の、いつ期限が来る契約か。先物は契約月が変わるため、銘柄名だけでは同じDataにならない。期限切れ契約やspreadを混ぜる。Catalogを確定できない。
対象期間／as-ofいつからいつまでのDataか、未来をどこで切るか。未来の値を過去の判定に混ぜないため。Look-aheadが起き、検証結果を信用できない。PERIOD_UNKNOWN。
時間足／bar境界何分ごとに1本の棒を作るか、1日の区切りをどこに置くか。同じ1分Dataでも、集計の区切り方が違えば別の足になる。ProviderのUTC日足を取引所の営業日足と誤認する。CALENDAR_UNKNOWN。
資産種類先物、株式、FX、暗号資産のどれか。単位、取引時間、休場、契約の扱いが変わるため。先物Dataを株式やFXのDataのように扱う。
ProviderDataを持っている会社。Dataの仕様、品質、費用、利用条件を確認する起点になる。どのDataを使ったか説明できない。PROVIDER_GATE_REQUIRED。
契約／権限／再配布買ったDataを、誰が、何に使ってよいか。取得できても、保存・社内利用・再配布の許可が別の場合がある。規約違反や意図しない公開につながる。
endpoint／通信／rateどこへ、どの通信で、どれくらいの速さで接続するか。外部I/Oの範囲と過剰取得を制限するため。想定外の接続、rate制限、追加費用が起きる。
費用上限いくらまでなら実行してよいか。Data取得は量に応じて課金されるため。大量取得で予算を超える。COST_GATE_REQUIRED。
Secret参照／mask／失効鍵をどこから読み、いつ使えなくするか。API keyをHTML、ログ、コマンド履歴へ出さないため。認証情報が漏れる。漏洩時に止められない。
Raw保存Providerから届いた元のDataを、そのまま残す場所。後から「何を受け取ったか」を確認するため。上書きしない。加工後のDataしか残らず、再現できない。
Normalized保存システム共通の形へ変換したDataの場所。Provider固有の記号や形式をCoreへ漏らさずに使うため。Provider依存がCoreへ入り、別Providerへ変更しにくくなる。
Quality／Calendar欠損や異常、取引時間を確認した記録。Dataがあるだけでなく、使ってよい状態かを判断するため。欠損・休場・DST・Rollを正常Dataと誤認する。
Manifest／Evidence root取得条件と証拠をまとめる台帳と保存場所。Run、HEAD、対象、hash、変換版を一つにつなぐため。同じ条件で取り直せず、Evidenceが孤立する。
保持／再配布いつまで持ち、誰へ渡してよいか。Providerの利用条件と、プロジェクトの保存境界を守るため。期限切れのDataを残す、または無断共有する。
停止条件何が起きたら必ず止めるか。失敗を「たぶん大丈夫」で通さないため。Unknownや部分取得をPassにしてしまう。
Runner／固定command実際に取得する人・機械・手順。誰がやっても同じ範囲で同じ処理をするため。未登録のWorkerを推測起動する。P5-EXTERNAL-WORKER-UNKNOWN。
host isolation外部へ出られる道を必要最小限に絞った証拠。Provider以外へDataやSecretを送らないため。外部通信の範囲が証明できず、品質Gateを通せない。
Run ID／target paths／再現今回の作業番号、書いてよい場所、やり直し方。CoreやP4 DBを誤って変更せず、同じ結果を再現するため。対象外ファイルを変更しても分からない。

6. 値を適用しても、まだ実行開始できないもの

P5-DATA-G1の範囲承認と、外部Dataを実際に取得できる状態は別である。次の項目は、値を適用した後に人間と実行環境で確認しなければならない。

  1. Databentoの実アカウントで、GLBX.MDP3、対象schema、対象期間が有効であること。
  2. 契約・利用権限・保持・再配布条件が、今回の「内部利用・再配布なし」と一致すること。
  3. Provider／team側budget controlが、1 Run 25 USD・Historical月額50 USDの上限と80%警告・100%停止へ設定・確認されていること。事前見積りは必須条件ではない。
  4. DATABENTO_API_KEYを安全に参照できること。値をログや文書へ出さないこと。
  5. P5-EXT-DATABENTO-HIST-001のRunner実体、固定venv／依存、command、target scope、dry-run、外部通信監査が作成・検証済みであること。
  6. 5候補のparent解決結果と、必要期間の個別契約一覧がそろうこと。206 Partial Contentやavailable以外は成功にしないこと。
  7. 外部Run専用のhost isolation Evidenceが、P5-06のlocal Evidenceとは別に存在すること。

したがって、現在の状態は、P5-DATA-G1 APPROVED、P5-EXTERNAL-WORKER-UNKNOWN OPEN / PRECONDITION_UNKNOWN、P5-08 BLOCKEDである。 Runnerとdry-runは作成済みだが、entitlement・budget control・Secret metadata・host isolation・外部Run Evidenceが未確認であり、未確認の項目をPassへ変換していない。事前費用見積りは開始条件から除外した。
