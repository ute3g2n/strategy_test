要約

本書は、NautilusTrader、LEAN / QuantConnect系、その他候補エンジンをPhase 1で比較するためのPoC評価設計である。目的は「好みで決める」ことではなく、OD-02 取引エンジン最終決定に足る証拠条件を明確にすることである。

PoCは実資金機能へ踏み込まない。Paper接続を扱う場合も、接続性、注文状態、再同期、安全停止の検証に限定し、Live注文や実運用Runbookの確定は後続Phaseへ送る。

候補エンジン評価観点

観点NautilusTraderで確認することLEAN / QuantConnect系で確認すること合否判断
共通実行BacktestとLiveでStrategy / Executionの意味論が揃うか。Research、Backtest、LiveのAPI差分とローカル実行差分が許容できるか。D11 Event Envelopeを無理なく実装できること。
Adapter境界Data Adapter、Execution Adapterで外部依存を閉じ込められるか。Brokerage / Data provider連携を内部Portへ隔離できるか。D10の外部ID非漏洩を満たすこと。
再現性同一データ、同一設定でリプレイ結果が決定的か。ローカルBacktestとクラウド/CLI差分を説明できるか。Run Manifestで再実行可能であること。
注文状態Entry / Add / Stop / Exit、部分約定、取消、拒否をモデル化できるか。Brokerageごとの注文状態差分を標準状態へ写像できるか。D06の注文ライフサイクルに写像できること。
安全停止Heartbeat欠損、接続断、状態不明で停止できるか。Brokerage / data provider障害を検知し、停止イベントを出せるか。fail-closedをテストで示すこと。
運用性ログ、監査、再起動、設定管理が十分か。ローカル運用、クラウド依存、CLI、ログ取得が十分か。Paper昇格前に運用証跡を残せること。
拡張性Python/Rust境界、カスタムデータ、複数市場に耐えるか。Python/C#、データプロバイダ、Brokerage追加に耐えるか。Phase 2-4の詳細設計を塞がないこと。

取引エンジン最終決定の証拠条件

  1. 全PoCシナリオのManifest、入力データ、設定、ログ、期待結果、実結果が保存されている。
  2. 同一Manifestで少なくとも2回再実行し、OrderIntent系列、Order状態、Position結果が一致している。
  3. 部分約定、再起動復旧、Open order / Fill / Position再同期、Heartbeat欠損の失敗注入テストが通過している。
  4. 公式一次情報に基づく制約と、未確認事項が台帳化されている。
  5. 採用候補がPhase 2 Market Data、Phase 3 Strategy / Backtest、Phase 4 Broker / Paperの設計を塞がないことを説明できる。
  6. 除外条件に該当しないことをA12/A13観点でレビュー済みである。

設計判断

DEC-P1-POC-01: PoCで最終決定の証拠を作る

エンジン選定を嗜好や知名度で決めず、再現性、安全停止、Adapter境界、運用性の証拠で決める。

DEC-P1-POC-02: Paper接続は検証までに限定する

IBKR Paper接続は注文状態と再同期の検証に使うが、実資金Live接続や運用手順の確定には進めない。

DEC-P1-POC-03: 除外条件を総点より優先する

高機能でも、安全停止、再現性、ID境界、Look-ahead防止を満たさない候補は採用不可とする。
