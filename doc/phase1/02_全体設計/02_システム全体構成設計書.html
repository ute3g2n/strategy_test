全体構成

Phase 1では、モジュラーモノリスを基本構造とし、内部の判断履歴はイベント駆動で扱い、外部依存はAdapterで隔離する。初期段階では分散システム化よりも、検証再現性、責務境界、監査性を優先する。

Market Data Adapter
  -> Data Ingestion -> Raw Store -> Normalization -> Catalog
  -> Event Engine -> Strategy Plugin -> Risk -> OMS
  -> Broker Adapter -> Reconciliation -> Monitoring
構成要素責務依存方向
Core Domainイベント、注文意図、注文、約定、ポジション、口座断面、リスク断面の概念を保持する。外部API、DB、通知、UIに依存しない。
Application ServicesBacktest、Shadow、Paper、Liveの実行ユースケースを組み立てる。Core Domainへ依存し、AdapterはPort経由で扱う。
AdaptersBroker、Market Data、通知、永続化など外部依存を内部モデルへ変換する。外部仕様の差分を閉じ込める。
Operations監視、安全停止、監査ログ、Secrets境界、復旧判断を扱う。実行状態を観測し、停止制御点を持つ。

研究コードと本番運用コードの境界

領域許可すること禁止すること
研究用コード市場候補探索、パラメータ比較、ノートブック、検証ハーネス、候補戦略分析。本番注文、Broker認証情報参照、Live状態の直接更新、監査ログ正本への書き込み。
本番運用コードバージョン固定された設定、正規化データ、イベントジャーナル、Risk、OMS、Broker Adapter、Reconciliation、安全停止。再現不能な手動補正、研究スクリプトからの注文発行、未レビュー戦略のLive接続。
共有境界読み取り専用の共通ドメイン概念、Strategy Plugin Interface、Golden test fixture。研究側から本番DBや本番Adapterを直接importすること。

Backtest / Shadow / Paper / Live で共通化する部分

共通化する部分理由差分の閉じ込め先
イベント封筒、時刻、銘柄ID、価格イベント検証と本番の入力差を小さくする。Market Data Adapter、Clock Adapter
Strategy Plugin Interface戦略差し替えとTurtle比較を同じ入口で扱う。Strategy Module
Risk、OMSの判断順序BacktestとLiveの挙動差を監査可能にする。Execution Mode Adapter
イベントジャーナル、監視イベント再現性、障害調査、照合の基礎にする。Storage Adapter、Monitoring Adapter

設計判断

DEC-P1-ARCH-01: モジュラーモノリス、イベント駆動、Adapter方式を採用する

初期段階では単一デプロイ単位で責務境界を明確化し、イベント記録により再現性と監査性を確保する。外部依存はAdapterへ閉じ込める。

DEC-P1-ARCH-02: 研究用コードは本番注文経路から分離する

研究側は探索速度を優先できる一方、本番側は監査性、安全停止、Secrets境界を優先するため、接点をStrategy Plugin Interfaceと検証済み設定に限定する。

DEC-P1-ARCH-03: Strategyは注文意図までを出力する

StrategyはSignalとOrderIntentを作る。Risk、OMS、Broker Adapter、ReconciliationはStrategy外に置く。
