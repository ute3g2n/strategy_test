2-2. BLK-RUN-002を詳しく説明すると

一言でいうと: 品質確認の最後に必要な「別の権限者による合格判断」が、まだありません。

Human Gateは、AIが自分の作業を自分で合格にする仕組みではありません。テスト、静的検査、レビューがそろった後に、人間が「このRunの範囲、残件、安全条件を確認した」と判断する最後の関門です。

確認するもの現在の状態必要な状態
Human Gate依頼ユーザーは承認を申告済みです。ただし、正式な署名付き承認JSONはまだありません。Run ID、HEAD、change hash、fixture hash、4 Gate、レビュー結果、残件0を記した依頼。
署名済み承認human-gate/approval.jsonは存在しません。worktree外の秘密鍵で権限者が署名したJSON。作業Agentは作成・自己承認しません。
検証項目現在のverificationはBLOCKEDです。ユーザー承認は記録済みですが、正式な署名検証は未完了です。decision=approved、approved_by、approved_at、run_id、commit、change_hash、fixture_hash、remaining_items=[]が一致し、公開鍵検証に成功すること。
設計上の意味H2-0/H2-1の設計承認とは別に、個別の実装Runの受入承認が必要です。承認後にだけ、RunとverificationをPassへ更新し、次のPhaseへ引き渡します。

なぜAIの「承認しました」では足りないのか: AIは実装、テスト、レビューの流れに関わっているため、同じAIが最後の承認者になると独立確認になりません。承認者が別であること、署名が改ざんされていないこと、承認内容が今回のRunと一致することを機械で確認します。

解除方法: BLK-RUN-003を解消し、必要な再確認を終えた後、ユーザー承認内容に対応する正式な署名JSONをworktree外で作成します。Runnerが公開鍵で内容と署名を検証できるまでは、未署名のworktree内JSONを承認根拠にしません。

2-3. BLK-RUN-003を詳しく説明すると

一言でいうと: テスト用の子プロセスが外部ネットワークへ出られないと、OS側で確認できていないため、Runnerがテスト開始前に止まっています。

このRunは、Databento、Broker、Secret、実データ、実取引、外部ネットワークを使わない契約です。テストコードに万一の誤りがあっても外へ出られないよう、二つの壁を置いています。

壁何をするか限界
第一の壁：host確認trusted_scopes.jsonのnetwork_isolation_required=trueを読み、Runnerがhostの隔離確認を要求します。確認できなければ子プロセスを起動しません。現在はOS Firewall/Sandboxなどの実際の隔離を確認できていません。環境変数を置くだけでは証明になりません。
第二の壁：wrapperlocal_p2_pytest.pyが固定のtests/market_dataだけを起動し、socket接続を拒否し、pytest pluginの自動読み込みも止めます。これは子プロセスが起動した後の壁です。hostそのものの隔離確認の代わりにはなりません。
実際の再確認run_quality_gate.py ... --no-write-evidenceを実行し、終了コード1、BLOCKED、理由「host の outbound isolation が確認できないため実行を停止しました」、Gate開始数0を記録しました。そのため、今回の再確認ではformatter/lint/type/pytest subprocessを一つも起動していません。

なぜ「外部接続していないから大丈夫」ではないのか: これまでのコード検索で外部接続呼出しがないことは確認できます。しかし、品質Gateは将来の変更も実行します。host側の最後の防壁が確認できないまま実行すると、次の変更で誤った通信が入ったときに止められない可能性があります。

解除方法（推奨）: Windows Sandboxまたは承認済みの使い捨てVMを用意し、その中でネットワークアダプターを無効化するか、Windows Firewallの送信を既定拒否にします。ホスト管理者が隔離状態を確認し、VM識別子・確認者・確認時刻・Firewall設定の読み取り結果を test/evidence/phase2/RUN-P2-IC-001/host-isolation.json に記録します。その隔離環境の中へ作業ツリーをコピーし、そこでRunnerを実行します。

順番具体的にすること合格条件
1管理者がWindows Sandbox/VMを起動し、ネットワークアダプターを無効化する。または送信通信をすべて拒否するFirewallを有効化する。隔離設定が管理者の記録に残っている。
2隔離環境内で、Runner、固定wrapper、fixture、4 Gateのファイルだけを配置する。Databento、Broker、Secret、実データは配置しない。禁止依存が存在せず、対象パスとManifestが一致する。
3管理者が隔離設定を読み取り確認し、確認者・時刻・VM名・設定の要約を host-isolation.json に署名または承認記録として残す。markerだけでなく、host側の設定証拠がある。
4その環境でだけ QUALITY_GATE_NETWORK_ISOLATION_CONFIRMED=1 を設定し、run_quality_gate.py を実行する。RunnerがBLOCKEDにならず、formatter → lint → type → 固定pytestの順で開始される。
5終了コード、ツールversion、対象scope、fixture hash、target-only change hash、標準出力の要約をverificationへ保存する。4 Gateと証跡がそろい、通信試行がない。

やってはいけないこと: 通常のホストでmarkerだけを設定すること、外部サイトへ接続して「つながらない」と確認すること、BrokerやDatabentoへ接続して確認すること、隔離設定を証明できないままRunnerを変更して通すこと。これらはBLK-RUN-003の解決とはみなしません。

代替策: Sandbox/VMを用意できない場合は、組織が管理するCIのnetwork-disabled runnerを使います。そこでも同じhost隔離証跡とRun Manifestを保存できない場合は、テストを開始せずBLOCKEDのままにします。

WSL2で行う場合の具体的な手順

WSL2の通常設定はNATで、Windowsのネットワークを通って外へ出られるため、WSLを起動するだけでは解決しません。WSL2には networkingMode=none があるので、これを使って「ネットワークなし」の実行環境を作ります。設定値の対応状況は、実行する端末のWSL versionとMicrosoftの設定表を確認します。

Codex CLIにこの環境を構築させるための、そのまま貼り付けられる依頼文は WSL2隔離品質ゲート構築_CodexCLI依頼プロンプト に置きます。

  1. Windows側で wsl --version と wsl -l -v を読み取り、全ディストリビューションが停止中で、対象ディストリビューションがVERSION 2であることを確認します。この確認では wsl -d を呼ばず、WSLを起動しません。
  2. 依存パッケージを先に用意します。ネットワークを切った後はpip installしません。Linux用のPython、ruff、mypy、pytest、pytest-covを、承認済みartifactまたは事前取得wheelからWSL内へ配置します。Windows用の .venv はLinuxで使わず、WSL専用のvenvを作ります。
  3. Windows側の %UserProfile%\.wslconfig に次を設定します。networkingMode=none は全WSL2へ効くため、他のWSL作業を止められる時間帯に行います。
    [wsl2]
networkingMode=none
firewall=true
  4. wsl --shutdown を実行して隔離設定を反映し、その後に対象ディストリビューションを一回だけ起動します。起動後のLinux runnerが uname -r、ip addr、ip route を読み取り、WSL2 kernel、通常の外向きインターフェース、default routeの有無を確認します。外部サイトへの接続試験はしません。
  5. 同じLinux runnerが、repository、Linux用venv、承認済みwheelhouse、fixture、Manifest、registry、固定版ツールを確認します。これらの確認に失敗した場合は4 Gateを開始しません。Databento、Broker、Secret、実データは置きません。
  6. 現在の RUN-P2-IC-001 の固定commandは .venv/Scripts/python.exe（Windows用）です。これをWSLから呼ぶとWindows側で実行され、WSLの隔離を使えません。したがって、WSL用の承認済みscope RUN-P2-IC-001-WSL をregistryへ追加し、.venv/bin/python -m ruff、.venv/bin/python -m mypy、.venv/bin/python -m scripts.quality_gate.local_p2_pytest の固定templateを登録します。target_paths、fixture hash、requirements、designは元Runと一致させます。
  7. Linux runnerが、WSL version、kernel、ディストリビューション、networkingMode、ip addr、ip route、fixture hashを test/evidence/phase2/RUN-P2-IC-001-WSL/host-isolation.json に記録します。markerだけでは証拠にしません。
  8. これらの確認に成功したプロセスだけが QUALITY_GATE_NETWORK_ISOLATION_CONFIRMED=1 を設定し、WSL用にregistry登録したManifestで4 Gateを実行します。終了コード、version、対象scope、hash、fixture hashをverificationへ保存します。

WSL手順の停止条件: networkingMode=none が使えない、WSLがVERSION 1、default routeが残る、依存パッケージを事前取得できない、host-isolation.jsonを管理者が確認できない場合は、通常WSLへ戻して実行せずBLOCKEDのままにします。

6. これからの更新方法

1. 見つける
レビュー、テスト、Human Gateで問題を見つけます。
→
2. 同じ原因か確認
既存IDと同じなら、新しい行を増やさず証拠を足します。
→
3. 安全に止める
してはいけないことと、進めてよい範囲を書きます。
→
4. 証拠を作る
テスト、レビュー、承認記録を所定の場所へ保存します。
→
5. 解決を記録
状態、日付、証拠を更新します。行は削除しません。

更新時の必須項目

  • ID、見つけた日、対象Phase、やさしい説明。
  • 何を止めるか、何なら安全に続けられるか。
  • 元の要件ID・設計ID・Finding ID。重複なら既存の根本ID。
  • 解消条件、担当するPhaseまたはHuman Gate、証拠の保存先。
  • 解消時は、解消日、確認者、テスト・レビュー・承認へのリンク。
証拠の置き場所: テストやRunの生の証拠は test/evidence/{phase_id}/{run_id}/ に置きます。このHTMLには証拠そのものをコピーせず、短い説明とリンクだけを書きます。
