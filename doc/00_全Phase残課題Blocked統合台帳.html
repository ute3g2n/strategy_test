WSL2で行う場合の具体的な手順

WSL2の通常設定はNATで、Windowsのネットワークを通って外へ出られるため、WSLを起動するだけでは解決しません。WSL2には networkingMode=none があるので、これを使って「ネットワークなし」の実行環境を作ります。設定値の対応状況は、実行する端末のWSL versionとMicrosoftの設定表を確認します。

Codex CLIにこの環境を構築させるための、そのまま貼り付けられる依頼文は WSL2隔離品質ゲート構築_CodexCLI依頼プロンプト に置きます。

  1. Windows側で wsl --version と wsl -l -v を読み取り、全ディストリビューションが停止中で、対象ディストリビューションがVERSION 2であることを確認します。この確認では wsl -d を呼ばず、WSLを起動しません。
  2. 依存パッケージを先に用意します。ネットワークを切った後はpip installしません。Linux用のPython、ruff、mypy、pytest、pytest-covを、承認済みartifactまたは事前取得wheelからWSL内へ配置します。Windows用の .venv はLinuxで使わず、WSL専用のvenvを作ります。
  3. Windows側の %UserProfile%\.wslconfig に次を設定します。networkingMode=none は全WSL2へ効くため、他のWSL作業を止められる時間帯に行います。
    [wsl2]
networkingMode=none
firewall=true
  4. wsl --shutdown を実行して隔離設定を反映し、その後に対象ディストリビューションを一回だけ起動します。起動後のLinux runnerが uname -r、ip addr、ip route を読み取り、WSL2 kernel、通常の外向きインターフェース、default routeの有無を確認します。外部サイトへの接続試験はしません。
  5. 同じLinux runnerが、repository、Linux用venv、承認済みwheelhouse、fixture、Manifest、registry、固定版ツールを確認します。これらの確認に失敗した場合は4 Gateを開始しません。Databento、Broker、Secret、実データは置きません。
  6. 現在の RUN-P2-IC-001 の固定commandは .venv/Scripts/python.exe（Windows用）です。これをWSLから呼ぶとWindows側で実行され、WSLの隔離を使えません。したがって、WSL用の承認済みscope RUN-P2-IC-001-WSL をregistryへ追加し、.venv/bin/python -m ruff、.venv/bin/python -m mypy、.venv/bin/python -m scripts.quality_gate.local_p2_pytest の固定templateを登録します。target_paths、fixture hash、requirements、designは元Runと一致させます。
  7. Linux runnerが、WSL version、kernel、ディストリビューション、networkingMode、ip addr、ip route、fixture hashを tests/evidence/phase2/RUN-P2-IC-001-WSL/host-isolation.json に記録します。markerだけでは証拠にしません。
  8. これらの確認に成功したプロセスだけが QUALITY_GATE_NETWORK_ISOLATION_CONFIRMED=1 を設定し、WSL用にregistry登録したManifestで4 Gateを実行します。終了コード、version、対象scope、hash、fixture hashをverificationへ保存します。

WSL手順の停止条件: networkingMode=none が使えない、WSLがVERSION 1、default routeが残る、依存パッケージを事前取得できない、host-isolation.jsonを管理者が確認できない場合は、通常WSLへ戻して実行せずBLOCKEDのままにします。

2026-08-07 実機確認: WSL専用trusted scope RUN-P2-IC-001-WSLをWindows native PowerShellから実行し、host-isolation.jsonのstate=CONFIRMED、4 GateのPASS、restore.jsonのstate=RESTORED、実行ID一致、ユーザーの明示承認を確認したため、BLK-RUN-003を解決済み、RunをPASSへ更新した。

6. これからの更新方法

1. 見つける
レビュー、テスト、人による承認で問題を見つけます。承認・認証が必要なら未承認でも台帳へ登録します。
→
2. 同じ原因か確認
既存IDと同じなら、新しい行を増やさず証拠を足します。
→
3. 安全に止める
してはいけないことと、進めてよい範囲を書きます。
→
4. 証拠を作る
テスト、レビュー、承認記録を所定の場所へ保存します。
→
5. 解決を記録
状態、日付、証拠を更新します。行は削除しません。

更新時の必須項目

  • ID、見つけた日、対象Phase、やさしい説明。
  • 何を止めるか、何なら安全に続けられるか。
  • 元の要件ID・設計ID・Finding ID。重複なら既存の根本ID。
  • 解消条件、担当するPhaseまたは人による承認、証拠の保存先。
  • 解消時は、解消日、確認者、テスト・レビュー・承認へのリンク。
証拠の置き場所: テストやRunの生の証拠は tests/evidence/{phase_id}/{run_id}/ に置きます。このHTMLには証拠そのものをコピーせず、短い説明とリンクだけを書きます。

最新方針の上書き（2026-08-09）

プロジェクトコードの実行ユーザーは固定しない。 本番運用ではroot権限で実行でき、検証では通常ユーザーでも実行できる。実行入口の -RunAsRoot を指定した場合だけrootで動き、指定しなければ通常ユーザーで動く。以前の「rootでプロジェクトコードを動かさない」「sudoグループに属する実行者を別アカウントへ分ける」という記述は、現在の運用方針ではRun停止条件にしない。

やさしい説明: 翻訳プログラムは、強い権限の人でも、普通の権限の人でも動かせます。どちらで動かしたかを記録します。ただし、入力データのhash、読む場所、対象コード、ネットワークなし、固定Gateの確認は、どちらの権限でも続けます。権限を強くしたからといって、勝手に別のデータを読んだり、売買を始めたりはできません。
