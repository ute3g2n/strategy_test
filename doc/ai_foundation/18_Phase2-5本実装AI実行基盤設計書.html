1. 目的、対象、非対象

本書は、Phase 2–5 の Python 実装を、テスト先行、検証、デバッグ、独立レビュー、Human Gate まで一貫して回すための最小 AI 部品構成を定義する。ECC の一般的な実装知識は再利用し、取引システム固有の時系列、データ品質、Secret、安全停止、証跡だけをプロジェクト側で補う。

対象この設計で固定することこの設計で固定しないこと
Phase 2Market Data の一機能をパイロットにし、固定 fixture、data_version、Replay/Data Gate、Python品質ループを検証する。Databentoの費用・権限、実データ取得、Broker接続、注文、Live可否。
Phase 3Strategy/Backtest の Golden、Look-ahead 防止、再現可能な実行証跡へ同じ品質ループを適用する。戦略ルールの新規決定や銘柄推奨。
Phase 4Paper Adapter、order/fill 整合、障害注入、環境分離のレビュー境界を追加する。実口座、発注上限の最終承認。
Phase 5Kill Switch、監視、ロールバック、最小権限を含む事前検証と手動判断の証跡を残す。自律的なLive開始、資格情報登録、発注実行。

4. 共通 Run Manifest と状態遷移

Run Manifest は各実装単位の入力と証跡を一意に結び付ける。以下の必須項目を埋められない場合は、実装を開始せず Unknown として記録する。

実装同期: 実体は JSON のみを受理する。必須項目は orchestrator、agents、skills、input_fixture(name/version/checksum)、data_version、baseline_ref、change_hash、human_gate_policy を含む。human_gate_approved の自己申告は受理せず、証跡直下の human-gate/approval.json を照合する。
図とテキストの区別: 次の黒い枠は機械可読な Run Manifest の項目例であり、図ではない。その直後の状態遷移ブロックが、Mermaid によりブラウザ上で図として描画される状態遷移図である。
run_id: RUN-P{phase}-{step}-{timestamp}
phase_id: Phase 2 | Phase 3 | Phase 4 | Phase 5
step_id: 実行計画書の完全なステップID
orchestrator: AutoTradeProject_ImplementationQuality_Orchestrator_v0_1
agents: 明示指定した AutoTrade_Axx_* の完全名
skills: 明示指定した autotrade_skill_* と ECC Skill 名
requirements: REQ-* の一覧
design: DD-* または承認済み設計書ID
input_fixture: fixture名、fixture_version、checksum
data_version: 未確定なら Unknown とし、Passにしない
target_paths: 変更対象ファイル
excluded_paths: 変更禁止ファイル
human_gate_policy: Gate名、承認者、承認条件
evidence_root: test/evidence/{phase_id}/{run_id}/
stateDiagram-v2
  [*] --> READY
  READY --> TEST_DESIGNED: 入力と範囲を確認
  TEST_DESIGNED --> IMPLEMENTED: red testを保存
  IMPLEMENTED --> VERIFIED: 最小差分を保存
  VERIFIED --> DEBUGGING: 機械Gateが失敗
  DEBUGGING --> VERIFIED: 原因修正後に再実行
  VERIFIED --> REVIEWED: 全機械GateがPass
  REVIEWED --> GATED: 独立レビューがPass
  GATED --> ACCEPTED: Human Gate承認
  GATED --> TEST_DESIGNED: 差戻し
  DEBUGGING --> BLOCKED: 同一失敗2回またはUnknown
  REVIEWED --> BLOCKED: Critical/Highまたは証跡不足
  BLOCKED --> [*]
  ACCEPTED --> [*]

自動ループは DEBUGGING から VERIFIED への再試行を同一原因仮説で最大2回とし、3回目は BLOCKED とする。Human Gate は自動承認しない。

6. 実行・発火制御

制御仕様
明示指定各 Run Manifest と実行プロンプトに Orchestrator、Agent、Skill の完全名を記載する。未指定部品は推測起動しない。
再利用優先A05/A82、A30、A70、A80/A90/A91、既存 test/orchestration/ops Skill、ECC Skill を先に使い、不足責務だけ候補を作る。
モデル候補 Orchestrator は既存汎用ルールに従い gpt-5.6-terra。候補 Agent は実体作成時に `.codex/agents/AutoTrade_A*.json` の個別モデル定義として固定する。
defaultdefault_orchestrator は変更しない。通常のドキュメント依頼に自動発火させず、Phase Runbook の対象ステップで明示する。
並列化A110のテスト設計とA10/A20の設計読解は入力が確定していれば並列可。A120実装、A130検証、A150/A160レビューは順序依存で直列とする。
外部作用検索・公式仕様確認は読み取りに限定。外部API、Broker、実データ取得、資格情報登録、注文、push、mergeはHuman Gateなしに実行しない。

8. 禁止事項と停止条件

自動停止: Secret/APIキー/口座IDの検出、実取引・Broker・Live経路の検出、UnknownをPassにする必要、テスト削除・skip、品質設定の弱体化、対象外差分、同一失敗2回、Critical/High指摘、Human Gate未承認。
  • 新設候補の名前が既存の Skill、Agent、Orchestrator と衝突した場合は上書きせず停止する。
  • Phase 1 専用部品を再利用対象へ昇格させず、参照だけにする。
  • 実装言語のパッケージ管理、型検査、lint、coverage の版が未確定なら、実在しない設定を仮定せず Unknown と Human Gate を作る。
  • コードレビューは実装者と別の視点で実行し、A150/A160が未完了のまま受入判定を出さない。

9. Unknown と Human Gate

IDUnknown決定時期決定前の縮退策
UNK-AIF-01Pythonツールチェーン（uv/pip、ruff、mypy/pyright、pytest、coverage）の正式版。Phase 2 パイロット開始前 H2-AIF-01品質コマンドを実装せず、候補仕様とdry-runだけにする。
