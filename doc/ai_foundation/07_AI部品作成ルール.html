1. 目的

本書は、自動売買システムプロジェクトでSkill、サブエージェント、オーケストレータを作成・更新・利用するときの共通ルールを定義する。AF-03でMarkdown版を settings/ai_component_rules.md として作成し、AGENTS.md から参照する。

3. 作成ルール

  • まず汎用Skill、汎用Agent、汎用Orchestratorで対応できるか確認する。
  • 汎用化できる作業規約は autotrade_skill_*_v0_1 として作る。
  • AI部品の作成・変更は、原則として「既存再利用調査 → 作成または変更 → 対象ドキュメント更新」の順で進める。
  • Phase専用部品は、汎用部品では不十分な理由、利用期限、凍結条件、HTML仕様書がある場合だけ作る。
  • 既存名と衝突する場合は上書きせず、衝突として報告する。
  • 既存Phase 1部品はfrozen / legacy / phase1証跡として扱い、削除、移動、上書き、リネームをしない。
  • default_orchestrator は明示承認なしに変更しない。

4.3 実装詳細設計標準部品

  • 実装着手に用いる詳細設計書は、AF-D14 のDD-01からDD-12を満たす。責務説明、概念図、項目列挙だけでは完了にしない。
  • 標準として AutoTradeProject_ImplementationDesign_Orchestrator_v0_1、AutoTrade_A82_ImplementationDetailDesigner_v0_1、AutoTrade_A91_ImplementationDetailReviewer_v0_1、autotrade_skill_implementation_detail_design_v0_1、autotrade_skill_implementation_detail_review_v0_1 を完全名で指定する。
  • 順序は、AF-D16/AF-D17の確認、A82の詳細化、A91の実装可能性レビュー、A90の横断・Red Teamレビュー、A80/A81の改訂統合、A91の再レビューとする。CriticalまたはHighが残る設計書を実装入力にしてはならない。
  • 詳細設計では、固有名詞・コード以外を日本語で書き、Mermaid図、表の前置き、文章化した全テストケースを必須とする。モジュール構造図の各実線矢印には受渡し名を短く付け、直後に送る部品、受け取る部品、渡すデータ・依頼、用途と停止条件を説明するモジュール間データ受渡し表を置く。
  • 実装対象のリポジトリ、言語、配置、未承認外部依存が未確定ならUnknownとして記録し、コード例は承認済みの境界または擬似コードに縮退する。

4. 発火制御ルール

  • プロンプトには、使用するオーケストレータ、サブエージェント、Skillの完全名を明記する。
  • 完全名で指定されていない既存Skill、既存Agent、既存Orchestratorを推測で起動しない。
  • 指定部品が存在しない場合は、現在ステップが作成ステップかどうかを確認する。作成ステップでなければ停止する。
  • Phase専用部品を使う場合は、理由、利用期限、凍結条件をプロンプトまたは仕様書に明記する。
  • 現行の汎用AutoTrade Orchestrator 6件は gpt-5.6-terra を使用する。サブエージェントのモデルはAgent JSONの個別定義を維持し、オーケストレータのモデル変更で変更してはならない。
  • Phase 1の凍結済みOrchestratorと default_orchestrator は、このモデル割当ルールの変更対象外とする。
  • 完全名の列挙、JSON読込、Skill適用、ルートAgentの自己レビューは起動証跡ではない。直接PromptはOrchestrator実spawn、指定Agent全件の個別spawn、固定model、定義された場合の reasoning_effort、wait完了、receipt保存を要求する。
  • spawn／waitまたは固定model受理ができない場合は、RUNTIME_DISPATCH_FALLBACK_REQUIRED、未起動Agent、理由、agent_id=N/A、independent=false、review_mode=SELF_REVIEW_FALLBACKを記録して継続する。起動不能を独立実行済みと偽らない。
  • Human Gate未承認、外部I/O、Secret、UnknownのPass、Critical／High、必須Evidence欠落はFallback中も停止する。

4.1 AI部品ライフサイクル標準部品

  • Skill / Agent / Orchestrator の作成または変更では、標準として AutoTradeComponentLifecycle_Orchestrator_v0_1、AutoTrade_A06_AiComponentEngineer_v0_1、autotrade_skill_ai_component_lifecycle_v0_1 を使用する。
  • 既存の調査には source_reader、追跡には traceability、HTML追従には html_doc_writer、レビューには design_review を再利用する。
  • 依頼プロンプトの標準雛形は doc/ai_foundation/12_AI部品作成更新依頼プロンプト.html を参照する。
  • CTXMAPの新規／大幅変更文書は autotrade_skill_context_manifest_maintenance_v0_1 と AutoTrade_A07_ContextManifestMaintainer_v0_1 へ1ファイル単位で渡す。A07のvalidator PASSまたは理由付きBLOCKED receiptなしに完了扱いにしない。
  • 参照依頼は autotrade_skill_context_routing_v0_1 と AutoTrade_A08_ContextRouter_v0_1 を使い、validator済みmanifestだけから主資料1〜3件、補助資料0〜6件、JIT範囲を選ぶ。本文を直接読ませない。
  • 日常保守で常時Orchestratorを起動せず、ソースコードの構造変更は決定的コードmanifest更新へ渡す。A07/A08にネットワーク、Secret、任意path、Git書込みを与えない。

4.2 設計書セット作成標準部品

  • Phase内で複数の正式HTML設計書をセットとして作成または更新する場合は、標準として AutoTradeProject_DesignDocSet_Orchestrator_v0_1、AutoTrade_A81_DesignDocSetWriter_v0_1、autotrade_skill_design_doc_set_writer_v0_1 を使用する。
  • 単体HTML作成とレビュー反映には引き続き AutoTrade_A80_DocumentIntegrator_v0_1 を使い、設計書セット全体の共通メタ、相互リンク、Unknown、レビュー履歴、doc/index導線は AutoTrade_A81_DesignDocSetWriter_v0_1 が主担当する。
  • 技術領域の設計判断は、Adapter、Architecture、Execution、QAなどの領域Agentが担当し、A81は承認済み内容の文書セット統合を担当する。

4.4 UIモック専用部品

  • UIモック作成では、まず既存の汎用Skill・Agent・Orchestratorを調査し、必要最小限として autotrade_skill_ui_mock_generation_v0_1、AutoTrade_A170_UiMockEngineer_v0_1、AutoTradeProject_UiMock_Orchestrator_v0_1 を使う。
  • 生成と品質判定を同じ責務にしない。AutoTrade_A171_UiVisualQaReviewer_v0_1 が autotrade_skill_ui_visual_validation_v0_1 と autotrade_skill_ui_accessibility_validation_v0_1 を使い、A170から独立してFindings firstでレビューする。
  • UIは固定Seed・固定基準日時の匿名ダミーデータだけで動かし、Broker、実市場データ、実口座、Secret、外部AIサービス、実注文へ接続しない。
  • 正式合否はStorybook、Vitest/axe、固定 @playwright/test、受入確認表で判定する。AI向け playwright-cli は匿名ローカル探索の補助に限り、探索結果を正式Passへ変換しない。
  • 単一運用者・認証不要の要件を維持し、認証、ユーザー管理、権限管理をUIモックへ追加しない。Unknown、未確認viewport、未確認状態、Critical/HighをPassにしない。

6. 安全ルール

  • 投資助言、売買推奨、特定商品の推奨にならない表現にする。
  • UnknownをPassにしない。未確定事項ID、決定タイミング、後続Phaseを記録する。
  • Secret、APIキー、認証情報を出力しない。
  • 安全停止、監査証跡、手動介入後復旧条件を弱めない。
  • 外部仕様を扱う場合は公式一次情報を優先し、URLと確認日を記録する。
