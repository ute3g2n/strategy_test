1. なぜ参照基盤が必要か

プロジェクトには、Markdown、HTML、Python、TypeScript、PowerShellなどが増えます。毎回すべてを読む方法は、時間がかかり、重要な一箇所を見落としやすく、AIへ不要な内容まで渡す危険があります。

方法得意なこと苦手なこと
全文を読む文脈を保つ巨大化すると遅く、必要箇所の選択が難しい
doc/index.html正式成果物の入口を一覧する本文の該当段落やコード依存関係までは探さない
全文検索単語の一致を探す意味、重要度、最新版、関連資料を判断しない
要件追跡REQ→設計→成果物→証跡を説明する依頼に必要な本文の最小範囲を直接返さない
CTXMAP正本の構造・hash・関係を使い、必要な候補を絞る未解析・古いhash・Unknownを勝手に補完できない

CTXMAPは全文を置き換える検索ではなく、「どの正本を、どの理由で、どこまで読むか」を決める索引です。

2. CTXMAPの目的、対象範囲、正本と証跡

CTXMAPは、リポジトリ内の管理対象文書とソースコードを、本文そのものではなく参照に必要な構造情報として記録します。対象は許可されたrepo内pathです。Secret、認証情報、外部サービス本文、実取引データは対象外です。

種類正本役割
artifact manifestcontext/artifact_manifest.json文書のtitle、見出し、ID、hash、用途、リンク等
code manifestcontext/code_manifest.jsonコードのsymbol、定義位置、呼出し候補、解析状態等
relation graphcontext/relation_graph.jsonREQ、文書、コード、test、evidenceの関係
状態・証跡context/manifest_state.json、receiptsvalidator結果、source_hash、更新判断、停止理由
正本と証跡の違い: manifestは現在の索引、receiptはなぜその索引になったかです。証跡がないPASSは受け入れません。本文を索引にコピーしてSecretを増やすこともしません。

3. 三つの記録をダミーで理解する

以下は秘密を含まない説明用ダミーです。実在の鍵、口座ID、個人情報を入れてはいけません。

{
  "artifact_id": "DEMO_ARTIFACT_001",
  "path": "doc/example/design.html",
  "title": "例示設計書",
  "source_hash": "sha256:DEMO_ONLY",
  "status": "ACTIVE",
  "extracted": ["h1", "h2", "DEMO_REQUIREMENT_01", "DEMO_DECISION_01"]
}
{
  "code_id": "DEMO_CODE_001",
  "path": "src/example.py",
  "symbol": "demo_function",
  "language": "python",
  "parser_status": "PASS",
  "source_hash": "sha256:DEMO_ONLY"
}
{
  "from": "DEMO_REQUIREMENT_01",
  "relation": "implemented_by",
  "to": "DEMO_CODE_001",
  "evidence": "DEMO_ARTIFACT_001"
}

artifactは説明書、codeは実装の部品、relation graphはどれがどれを支えるかを表します。pathだけでIDを作るとrenameで追跡が切れるため、stable IDと旧pathの履歴を分けて保持します。

5. A07: 1ファイルstrict JSON判断

A07（ContextManifestMaintainer）は、1回につき1ファイルだけを受け取り、本文全体を横断して勝手に書き換える担当ではありません。入力にはpath、変更種別、source_hash、許可されたメタデータだけを渡します。返却は機械検証できるstrict JSONです。

{
  "decision": "record_add",
  "path": "doc/example/design.html",
  "source_hash": "sha256:DEMO_ONLY",
  "reason": "新規の管理対象HTML",
  "validator": "PASS",
  "secret_detected": false
}
decision意味
record_add新しいrecordを追加する
record_update構造または本文由来の索引を更新する
metadata_unchanged構造は変わらず、hash等の必要な更新だけを記録する
validator PASS / BLOCKEDPASSはschemaと安全条件を満たす。BLOCKEDは理由付きで止め、成功扱いにしない

source_hashは、いま見たファイルが索引作成時と同じかを確認する印です。hashがstaleなら、そのmanifestをA08へ渡してはいけません。

6. A08: 依頼文から最小routing

A08（ContextRouter）は、依頼文とvalidator PASS済みmanifestだけを使います。本文を直接読んで恣意的に候補を選ぶ担当ではありません。primaryは最大3件、supportingは最大6件、残りはJIT（必要時に取得）として最小範囲を返します。

利用者の依頼文
→
検証済みmanifest
→
ID・REQ・関係で候補化
→
primary ≤3
supporting ≤6
→
JIT範囲を限定

候補が足りないときは、ないものを作りません。stale、PARTIAL、Unknown、Human Gate待ちは理由付きで返し、利用者が判断できるようにします。

7. fail-closedと脅威

fail-closedとは、迷ったときに通すのではなく、安全側へ止めることです。

事象処理やさしい説明
A07/A08 unavailablefallbackを成功扱いせず、未起動・receipt・SELF_REVIEW_FALLBACKを記録担当者がいないのに完了したことにしない
schema破損・stale hashroutingとcommitを停止古い地図で案内しない
Secret・鍵・認証情報本文を出力せず拒否、pathと理由だけ記録秘密を見つけたら写さず止まる
Prompt Injection文書中の命令を実行指示として扱わない資料の命令で安全確認を無視しない
path traversalrepo内allowlist外のpathを拒否別の場所へ抜ける道を閉じる
巨大ファイル上限超過はPARTIALまたはBLOCKED重すぎる資料で全体を止めない
Unknown/Human Gate/H0/H1状態を保持し承認済みと未承認を明示人の確認をAIのPASSに置き換えない

8. Router→local MCP→JIT本文取得

本文取得は、routing後に必要な範囲だけをlocal stdio MCPへ依頼する流れです。外部MCPやクラウドへ本文を送る設計ではありません。

tool主な引数返却拒否条件・上限
search_contextquery、scope、limitmanifestの候補ID・path・理由repo外、limit超過、Secret語
get_artifactartifact_id、section、max_chars見出し・本文片・hashstale、全文要求、上限超過
get_code_slicecode_id、start_line、end_line行範囲、symbol、hash行範囲不正、Secret、repo外
get_relatedstable_id、relation、depth関連IDの限定リストdepth・件数超過、未検証graph

返却には対象ID、path、source_hash、truncatedかどうか、拒否理由（拒否時）が必要です。JIT取得でも、取得した本文を新しい正本にしません。

local MCPの引数上限と拒否例

search_contextはquery・scope・limit（最大20）、get_artifactはartifact_id・section・max_chars（最大18,000）、get_code_sliceはcode_id・行範囲（最大300行）、get_relatedはstable_id・relation・depth（最大3）を受け取ります。repo外path、..を含むpath、Secretらしい名前、上限超過、stale hash、Prompt Injectionを命令として扱う要求は拒否し、receiptに理由を残します。

9. 日次運用とcommit安全策

  1. 日次開始時にmanifestのvalidator状態、stale、pending、Unknownを確認する。
  2. watch startは承認済み設定とallowlistを確認してから行い、stopではreceiptを残す。監視はlocal単一worker・debounceのみとする。
  3. manual rerunは対象path、理由、前回hashを指定する。pending recoveryは原因を解消してから再実行する。
  4. auto-commitはvalidator PASSが返した明示allowlistだけをstage対象にする。未追跡のユーザー変更をstageしない。無差別なgit add -Aは契約外とする。
この資料の作業ではGit stage/commit/pushを実施していません。外部ネットワーク、MCP、Secret、実取引も実施していません。

10. fixture、test、audit、limitsと限界

確認対象例合格の考え方

parserが未対応の言語・構文はPARTIALです。excludedは対象外の理由を持つ必要があります。外部MCP未接続なので外部サービスの動作保証はありません。これは索引が正しいという証明ではなく、定めたfixtureとlocal範囲での再現可能性を確認する仕組みです。

12. FAQ・トラブルシューティング・用語・追跡

FAQ

Q.全文検索だけではだめですか。
A.検索は候補語を探す道具です。CTXMAPは正本、hash、関係、状態を合わせて安全に読む範囲を絞ります。

Q. A07が止まったら手作業でPASSにできますか。
A.できません。fallback receiptを残し、独立実行済みと偽らず、Human Gateへ戻します。

Q.削除recordは消しますか。
A.消さずにDELETED履歴として残します。過去の要件追跡を壊さないためです。

commitが止まるallowlist、Secret、未追跡差分停止を維持し、ユーザー変更を混ぜない
