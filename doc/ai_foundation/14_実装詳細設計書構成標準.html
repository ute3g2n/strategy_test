1. 目的

本標準は、詳細設計書を「方針・責務・属性名の説明」ではなく、独立した実装者が追加の設計判断をせずに実装、テスト、レビューへ進めるための契約として定義する。すべてを一文書に詰め込む必要はないが、設計書セット全体で必須構成要素を漏れなく満たす。

2. 設計文書の区別

種別答える問い十分ではない例
要件・基本設計なぜ必要か、何を扱うか、責務をどこで分けるか。「Adapterが変換する」「Rawを不変にする」だけで実装方法を示さない。
論理データ・アーキテクチャ設計どの概念、境界、論理データ、依存方向を持つか。項目名や概念図だけで、保存キー・型・変換順を示さない。
実装詳細設計どのモジュールに、どの型・関数・保存契約・処理順・失敗時挙動・テストを実装するか。Port名、API名、必須列の列挙だけで、シグネチャ・実装順・異常系・テストを省く。
判定基準: 「実装者が次に何のファイルを作り、どの値を検証し、失敗時に何を返し、どのテストを追加するか」を設計書だけから判断できなければ、実装詳細設計として未完了である。

5. 読解順フォーマット

DD-01からDD-12は充足すべき内容であり、読みにくい順に並べてよい理由にはならない。正式な実装詳細設計書は、実装者だけでなくレビュー担当者と業務担当者も最初に全体を把握できるよう、原則として次の順に置く。技術的な詳細契約は、この導入部の後に続ける。

順先頭に置く節必須の記載対応するDD
1ドメインの概要と機能誰が、何のために使い、何をできるようにする領域かを、略語や内部名に依存しない言葉で説明する。主要機能を列挙する。DD-01
2ファイル構成予定を含むファイルツリーと、各ファイルの責務、テスト・fixtureの配置、対象外を示す。DD-02, DD-03, DD-09
3モジュール構造図呼出元、公開境界、主要モジュール、保存先、外部境界、依存方向を、一枚のMermaid図で示す。各実線矢印には主な依頼・データ・イベント・保存物の受渡し名を短く付け、直後の受渡し表で意味、用途、停止条件を説明する。DD-02, DD-04
4モジュール機能と入出力各モジュールの機能、入力・出力のパラメータ名、型、必須性、意味、エラー、副作用を、技術者以外にも読める日本語の文章で定義する。DD-03, DD-04
5処理フロー正常系、主要な異常系、再試行または停止、境界観測を、Mermaidのシーケンス図・フローチャートなどで示す。図内の説明も日本語にする。DD-06, DD-08, DD-10
6テスト仕様当該設計書のスコープにおける全テストケースを列挙する。各行はテストID、概要、条件（入力値）、操作、期待結果、合否判定基準を持ち、各欄を単語だけで済ませず日本語の文章で記す。DD-09
表と本文の日本語: 固有名詞、コード、変数名、外部仕様の正式名称以外は日本語を基本とする。英単語を説明文で残す必要があるときは、直後に日本語の説明を添える。8章以降の各表にも、何を説明する表かを、表の前に誰にでも分かる言葉で記す。
モジュール間データ受渡し: 構造図は部品の位置だけでなく、部品間で何を渡すかも示す。図の矢印ラベルは短い契約名にとどめ、直後に「送る部品」「受け取る部品」「渡すデータ・依頼」「受け取り側の用途と停止条件」を持つ表を置く。長い説明をノードに詰め込んだり、秘密を図や表に載せたりしてはならない。
テンプレートと具体例: AF-D16 実装詳細設計書HTMLテンプレートを正式な構成テンプレート、P2-D05 市場データ受渡し部 詳細設計書 v0.6を記述品質の具体例として扱う。ただし、P2-D05のPhase 2固有の技術判断を他の領域へ流用してはならない。
N/Aの扱い: 先頭六節のどれかが不要な場合でも省略しない。N/A、理由、確認者、代替成果物へのリンクをその節に記載する。特にテスト仕様は「テストなし」とせず、対象外の根拠と残る検証責任を示す。

6. 入出力契約の記法

属性名だけの羅列は禁止する。各公開APIには次の記法を用いる。

Module: raw_store.repository
Function: put_if_absent(request: RawWriteRequest) -> RawWriteResult
Input: raw_object_id: RawObjectId (required), payload: bytes (required), sha256: str (required)
Output: created: bool, object_uri: str, existing_sha256: str | null
Errors: ChecksumMismatch, StorageUnavailable, InvalidMetadata
Idempotency: same raw_object_id and same sha256 returns the existing result
Side effects: append-only object write and immutable audit record
Preconditions: metadata validation and secret-free request metadata
Tests: duplicate same payload, duplicate different payload, write failure, retry

実在するコードがある場合は対象言語の型・クラス名に合わせる。実装前で型名が未確定なら、仮名であること、確定ステップ、未決時の停止条件をUnknownとして記録する。

必須シナリオ記載内容

検証失敗どの検証で止まり、何を保存し、何を下流へ送らず、どのError/HealthEventを出すか。

8. 完了Gate

実装詳細設計完了: DD-01からDD-12が設計書セット上で充足、または理由付きN/Aとなり、A91の充足マトリクスでCritical/Highが0件、A90/Red Teamの安全指摘が採否・改訂・再レビューまで閉じていること。UnknownはPassにせず、実装着手を止める範囲または縮退範囲を明記する。
