実装詳細設計書構成標準

文書ID: AF-D14
作成日: 2026-08-04

対象: Phase横断の正式HTML詳細設計書

1. 目的

本標準は、詳細設計書を「方針・責務・属性名の説明」ではなく、独立した実装者が追加の設計判断をせずに実装、テスト、レビューへ進めるための契約として定義する。すべてを一文書に詰め込む必要はないが、設計書セット全体で必須構成要素を漏れなく満たす。

2. 設計文書の区別

種別答える問い十分ではない例
要件・基本設計なぜ必要か、何を扱うか、責務をどこで分けるか。「Adapterが変換する」「Rawを不変にする」だけで実装方法を示さない。
論理データ・アーキテクチャ設計どの概念、境界、論理データ、依存方向を持つか。項目名や概念図だけで、保存キー・型・変換順を示さない。
実装詳細設計どのモジュールに、どの型・関数・保存契約・処理順・失敗時挙動・テストを実装するか。Port名、API名、必須列の列挙だけで、シグネチャ・実装順・異常系・テストを省く。
判定基準: 「実装者が次に何のファイルを作り、どの値を検証し、失敗時に何を返し、どのテストを追加するか」を設計書だけから判断できなければ、実装詳細設計として未完了である。

5. 入出力契約の記法

属性名だけの羅列は禁止する。各公開APIには次の記法を用いる。

Module: raw_store.repository
Function: put_if_absent(request: RawWriteRequest) -> RawWriteResult
Input: raw_object_id: RawObjectId (required), payload: bytes (required), sha256: str (required)
Output: created: bool, object_uri: str, existing_sha256: str | null
Errors: ChecksumMismatch, StorageUnavailable, InvalidMetadata
Idempotency: same raw_object_id and same sha256 returns the existing result
Side effects: append-only object write and immutable audit record
Preconditions: metadata validation and secret-free request metadata
Tests: duplicate same payload, duplicate different payload, write failure, retry

実在するコードがある場合は対象言語の型・クラス名に合わせる。実装前で型名が未確定なら、仮名であること、確定ステップ、未決時の停止条件をUnknownとして記録する。

7. 完了Gate

実装詳細設計完了: DD-01からDD-12が設計書セット上で充足、または理由付きN/Aとなり、A91の充足マトリクスでCritical/Highが0件、A90/Red Teamの安全指摘が採否・改訂・再レビューまで閉じていること。UnknownはPassにせず、実装着手を止める範囲または縮退範囲を明記する。
