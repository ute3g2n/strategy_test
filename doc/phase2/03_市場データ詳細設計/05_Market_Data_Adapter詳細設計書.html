1. ドメインの概要: 市場データ受渡し部は何をするものか

市場データ受渡し部（Market Data Adapter）は、外部データ提供元から届く市場データを、システムが安全に保管し、後で同じ条件で読み直せる形に受け渡すための入口である。データ提供元ごとの呼び方、通信方式、銘柄記号の表記、認証方法を、この入口の内側だけに閉じ込める。

たとえば、外部から「ある銘柄の1分足をください」と受け取ったデータを、そのまま戦略へ渡すことはしない。まず元のデータを改変せず保管し、どの条件で取得したか、壊れていないか、必要な銘柄が全部そろったかを確認する。問題があれば、下流へ進めずに理由を残して止まる。これがこのドメインの役目である。

利用者このドメインに期待することこのドメインが返すもの
P2-05の取得処理指定期間・指定銘柄のデータを安全に取り込む。元データの保管結果、内容確認値、利用可否、失敗理由。
元データ・整形済みデータ保管庫（Raw / Normalized Store）元データと取得条件を改変せず受け取る。元データ本体、説明情報、依頼内容の識別値、受信時刻。
銘柄台帳（Instrument Catalog）外部銘柄記号を内部銘柄番号（InstrumentId）へ対応付ける材料を受け取る。銘柄対応の解決結果、銘柄仕様の観測、失敗理由。
再生処理・データ品質確認（Replay / Data Quality）問題のあるデータを混ぜず、再現できる版を使う。利用可否、品質上の理由、元データ参照、データ版の候補。
機能ID機能誰にでも分かる説明失敗時
MDA-F01取得依頼の確認期間、時刻、銘柄、利用モードに抜けや矛盾がないかを、外部へ問い合わせる前に確認する。問い合わせずにInvalidRequestを返す。
MDA-F02データ取得fixtureまたは将来の提供元Gatewayから、元データと取得に関する説明を受け取る。認証、権限、部分取得、rate limitを成功にしない。
MDA-F03Raw保存への受渡し元データの指紋を計算し、同じ内容を何度も上書きしない形でRaw Storeへ渡す。保存失敗時は「取得成功」と知らせない。
MDA-F04シンボルと契約情報の観測外部の名前を内部の銘柄台帳が判断できる材料へ変換する。ただし台帳を勝手に確定しない。一意に決まらなければPendingとして止める。
MDA-F05利用可否と監査今のデータが使えるか、どこで問題になったかを、秘密情報を出さずに記録する。DEGRADED、UNHEALTHY、UNKNOWNでは後続での利用を止める。

4.1 HistoricalRequestの入力パラメータ

パラメータ名型必須説明と検証
request_idstr必須呼出側が一意に付与する依頼ID。空文字不可。再試行時も同じ論理依頼なら保持する。
dataset_refstr必須datasetを指す公開可能な別名。API keyやURL queryを含めない。
schema_refstr必須要求するデータ形式の別名。未確認schemaを既定値で補完しない。
symbolstuple[str, ...]必須1件以上。外部表記はこの値の中だけに留め、Core IDとして扱わない。
start_utcdatetime必須timezone-aware UTC。end_utcより前であること。
end_utcdatetime必須timezone-aware UTC。未来時刻を勝手に丸めない。
source_mode"fixture" | "external"必須externalはH2-2承認済みだけ。未承認なら即時停止。

4.2 GatewayPayload、RawWriteRequest、IngestionResultのパラメータ

型.パラメータ型説明検証 / 取扱い
GatewayPayload.payloadbytes取得した元データ。SHA-256を計算し、改変せずRaw Storeへ渡す。

GatewayPayload.conditionliteral提供元が示す利用可能性。available以外は成功のRaw取り込みを行わない。
RawWriteRequest.request_fingerprintstr依頼内容を正規化して得る識別子。payload SHA-256と組み合わせてRaw object IDを決める。
RawWriteRequest.received_at_utcdatetimeAdapterがpayloadを受け取ったUTC時刻。timezone-aware UTC必須。
IngestionResult.raw_object_idstr不変Rawの識別子。Raw Store成功後だけ返す。

IngestionResult.health_event_idstr今回の取り込み状態を示すHealthEvent ID。Health記録失敗なら成功結果を返さない。

5.3 symbol / definition観測フロー

これは、外部の銘柄記号を銘柄台帳へ伝える流れである。この部品は観測した事実を渡すだけで、内部銘柄番号を自分で決めない。

flowchart LR
    依頼["銘柄記号・契約情報の照会依頼"] --> 取得["外部表記のまま照会する"]
    取得 --> 判定{"一つの候補に決まったか"}
    判定 -- "いいえ。候補不足・複数候補・未発見" --> 保留["保留と問題理由を記録する"]
    保留 --> 停止["銘柄台帳へ成功として渡さない"]
    判定 -- はい --> 観測["観測した事実をまとめる"]
    観測 --> 台帳["銘柄台帳へ観測記録を渡す"]
    台帳 --> 受領["受領結果を受け取る"]

内部銘柄番号（InstrumentId）を作るのはP2-D07の銘柄台帳だけである。

6. テスト仕様

本表はP2-D05が要求する全テストケースである。P2-05で機能を増やす場合は、対応するケースを追加してから実装する。テスト入力はすべてfixtureまたはmockであり、外部APIを呼ばない。

テストIDテスト概要テスト条件（入力値）操作期待結果合否判定基準
MDA-T01問題のない固定入力を、元データ保管庫へ安全に渡せることを確認する。協定世界時の開始・終了時刻、有効なdataset_refとschema_ref、銘柄記号1件、source_mode="fixture"、内容が正しい固定入力ファイルを用意する。取得受取口のingestを一度呼び出す。元データが保管され、利用可能状態（HEALTHY）と取込結果が返る。created=trueであり、保管済みの内容確認値が入力内容と一致し、状態記録がHEALTHYになっていること。
MDA-T02依頼を識別する番号が空の場合、外部へ問い合わせずに止めることを確認する。request_id=""とし、それ以外は一見正しい取得依頼を用意する。依頼確認処理のvalidate_requestを呼び出す。不正な依頼を示すInvalidRequestが返る。データ取得口、元データ保管庫、状態記録部のいずれも一度も呼ばれていないこと。
MDA-T03対象銘柄が一件も指定されない場合、あいまいな取得を開始しないことを確認する。symbols=()とし、空の銘柄一覧を持つ取得依頼を用意する。依頼確認処理のvalidate_requestを呼び出す。不正な依頼を示すInvalidRequestが返る。理由コードがSYMBOLS_REQUIREDであり、外部取得処理が始まらないこと。
MDA-T04世界共通時刻か判別できない時刻を、取得条件として受け入れないことを確認する。start_utc.tzinfo=Noneとし、時間帯情報を持たない開始時刻を用意する。依頼確認処理のvalidate_requestを呼び出す。不正な依頼を示すInvalidRequestが返る。理由コードがUTC_REQUIREDであり、時刻を勝手に補正して取得を続けないこと。
MDA-T05終了時刻が開始時刻以前の依頼を、取得前に止めることを確認する。start_utc >= end_utcとなる、時間の並びが逆または同じ取得依頼を用意する。依頼確認処理のvalidate_requestを呼び出す。不正な依頼を示すInvalidRequestが返る。データ取得口が一度も呼ばれず、誤った期間での取得が始まらないこと。
MDA-T06人間承認前の外部取得を、通信も保管も行わずに止めることを確認する。source_mode="external"かつh2_2_approved=falseの取得依頼を用意する。取得受取口のingestを呼び出す。外部状態が未承認であることを示すExternalStateErrorが返る。ネットワークへ接続する取得口と元データ保管庫が呼ばれず、成功結果が一切返らないこと。
MDA-T07固定入力を使う試験では、外部ネットワークへ接続しないことを確認する。内容が正しい固定入力を指定した、source_mode="fixture"の取得依頼を用意する。FixtureGateway.fetchを呼び出す。固定入力の内容が取得結果として返る。外部通信を行う部品が生成されず、模擬部品の呼出し履歴にも通信が残らないこと。
MDA-T08指定された固定入力ファイルが存在しないとき、成功扱いにしないことを確認する。存在しない固定入力ファイルの場所を設定した取得依頼を用意する。FixtureGateway.fetchを呼び出す。固定入力が見つからないことを示すFixtureNotFoundが返る。元データの保管、利用可能状態の記録、取込成功結果のいずれも作られないこと。
MDA-T09認証情報を含む説明情報を、保存も記録もせずに拒否することを確認する。metadata={"authorization":"x"}のように、認証情報らしい項目を含む取得結果を用意する。取得受取口のingestを呼び出す。説明情報が不正であることを示すInvalidMetadataが返る。元データと説明情報が保管されず、認証情報の値が例外、監査記録、画面表示のどこにも現れないこと。
MDA-T10提供元が品質低下と通知したデータを、通常利用へ渡さないことを確認する。condition="degraded"を持つ取得結果を用意する。取得受取口のingestを呼び出す。ExternalStateErrorが返り、状態はDEGRADEDとして記録される。元データ取込の成功結果、実行記録の候補、再生入力のいずれも作られないこと。
MDA-T11提供元が準備中と通知したデータを、不明状態として止めることを確認する。condition="pending"を持つ取得結果を用意する。取得受取口のingestを呼び出す。ExternalStateErrorが返り、状態はUNKNOWNとして記録される。停止理由を示すreason_codeがデータ利用判定部へ渡り、後続の利用が始まらないこと。
MDA-T12提供元が欠損と通知したデータを、取得成功として扱わないことを確認する。condition="missing"を持つ取得結果を用意する。取得受取口のingestを呼び出す。ExternalStateErrorが返り、状態はUNKNOWNとして記録される。受信成功を示すイベントも、通常利用へ渡すデータも作られないこと。
MDA-T13一部の銘柄だけが解決された場合、解決済み部分だけを通常利用へ流さないことを確認する。データ取得口が、部分的な銘柄解決を示すPartialSymbolResolutionを返すようにする。取得受取口のingestを呼び出す。分類済みの例外が返り、状態はDEGRADEDとして記録される。解決できた一部だけを元データ保管、再生処理、売買判断用の通常経路へ渡さないこと。
MDA-T14認証に失敗した場合、秘密の値を漏らさずに利用停止へ移すことを確認する。データ取得口がAuthenticationErrorを返すようにする。取得受取口のingestを呼び出す。分類済みの例外が返り、状態はUNHEALTHYとして記録される。秘密の値や認証用の項目値が、例外、監査記録、画面表示のどこにも含まれないこと。
MDA-T15利用権限や費用条件が不足する場合、人間承認へ戻して止めることを確認する。データ取得口がEntitlementDeniedを返すようにする。取得受取口のingestを呼び出す。分類済みの例外が返り、状態はUNKNOWNとして記録される。H2-2の再確認が必要な状態となり、元データが一件も保管されないこと。
MDA-T16提供元の回数制限が一時的な場合だけ、指示された待機時間を守って再試行することを確認する。最初の取得だけRateLimitedを返し、Retry-Afterを示す。二回目は正しい固定入力を返すようにする。取得受取口のingestを呼び出す。指定時間を一度待った後に、通常どおり保管と完了が行われる。再試行回数が上限内であり、Retry-Afterで示された時間より前に再試行しないこと。
MDA-T17回数制限が続く、または待機時間が示されない場合、無限に再試行しないことを確認する。データ取得口が常にRateLimitedを返す、またはRetry-Afterを返さないようにする。取得受取口のingestを呼び出す。状態はUNHEALTHYとなり、取得は停止する。再試行上限を超えた後に追加のfetchを行わず、成功結果を返さないこと。
MDA-T18初めて受け取った元データを、内容確認値とともに新規保管することを確認する。まだ保管されていない依頼内容の識別値と、内容が正しい元データを用意する。元データ保管口のput_if_absentを呼び出す。新しい元データの識別子が返り、作成済みを示すcreated=trueとなる。返された識別子、内容確認値、説明情報が、渡した元データと矛盾しないこと。
MDA-T19同じ依頼と同じ内容を再実行しても、元データを重複保存・改変しないことを確認する。同じ依頼内容の識別値と同じ元データを用意し、同じ取得を二回行う。取得受取口のingestを二回呼び出す。二回目は最初に保管した元データへの参照を返す。二回目のcreatedがfalseであり、元データ本体と監査履歴が書き換わらないこと。
MDA-T20同じ論理的な依頼でも内容が変わった場合、過去の元データを上書きしないことを確認する。同じ依頼内容に対して、一回目と内容確認値が異なる元データを用意する。取得受取口のingestを呼び出す。新しい元データとして隔離されるか、差分があるため停止する。以前の元データが書き換わらず、理由コードと差分比較の対象が記録されること。
MDA-T21元データ保管に失敗した場合、取得成功を後続へ知らせないことを確認する。元データ保管口がRawWriteErrorを返すようにする。取得受取口のingestを呼び出す。状態はUNHEALTHYとなり、取込成功結果は返らない。IngestionResultを返さず、受信成功を示すイベントも発行しないこと。
MDA-T22利用可否の記録に失敗した場合、元データが残っていても利用可能としないことを確認する。状態記録部が例外を返すようにし、それ以外は正常な固定入力を用意する。取得受取口のingestを呼び出す。状態はUNHEALTHYとして扱われ、取込成功結果は返らない。成功結果を返さず、元データが残る場合でも通常利用の対象にしないこと。
MDA-T23一つに決まった外部銘柄の観測を、根拠と有効期間付きで銘柄台帳へ渡せることを確認する。一件だけに解決された対応関係と、先物であることを示す分類、有効期間を持つ観測を用意する。銘柄台帳の受取口record_observationを呼び出す。受領結果ObservationReceiptが返る。根拠となる元データの識別子source_raw_object_idと、有効期間が受領結果または監査記録に含まれること。
MDA-T24複数候補がある外部銘柄を、内部銘柄として勝手に確定しないことを確認する。複数候補に解決される対応関係、または取引可能な銘柄を一つに決められない広がった候補を用意する。銘柄台帳の受取口record_observationを呼び出す。保留状態と状態記録が作られ、成功の受領結果にはならない。内部銘柄番号、内部市場イベント、取引可能状態への昇格を一切行わないこと。

11. エラー分類とFail-closed

この表は、どの失敗なら何を止めるかを決める。閉じた側へ倒す（Fail-closed）とは、使えると証明できないデータを、使えるものとして後続へ渡さないという意味である。

エラーの固定名起きた状況の例この部品が行う処理利用可否と停止判断
AUTHENTICATION_FAILED秘密情報がない、または認証に失敗した場合。秘密の値を記録せずに停止し、人間による確認を待つ。UNHEALTHYとし、データ利用判定を停止する。
ENTITLEMENT_DENIEDデータ集合を使う権限がない、または費用上限に達した場合。実際の取得を停止し、H2-2または再承認へ戻す。UNKNOWNとし、人間承認が終わるまで使わない。
RATE_LIMITED提供元が回数制限を返した場合。たとえば通信応答が429の場合。Retry-Afterがあるときだけ限定して再試行し、上限後は停止する。DEGRADEDからUNHEALTHYへ移し、通常利用を止める。
SYMBOL_PARTIAL銘柄の一部だけが解決された場合。たとえば通信応答が206の場合。解決済みの一部だけを通常経路へ流さず、対象を保留にする。データ利用判定を停止する。
SYMBOL_NOT_FOUND銘柄候補が見つからない場合。たとえば通信応答が404の場合。候補を除外または条件付きとして隔離し、別の銘柄へ自動で置き換えない。未確定事項台帳に記録し、人間または後続手順で決める。
DATASET_DEGRADEDdegraded、pending、missingのように、提供元が通常利用できないと示した場合。該当日と範囲へ品質上の注意を付け、採用できないデータとして扱う。対象範囲を停止または縮退利用にする。
CHECKSUM_MISMATCH再取得した元データが過去と違う、または内容が壊れている場合。新しい元データとして隔離し、既存の元データを置き換えない。内容の正しさを確認する停止判断を発動する。
DECODE_OR_SCHEMA_ERRORDBNまたはCSVを読み解けない、または指定された形式と一致しない場合。整形済みデータへ変換せず、元の内容とエラーの証跡を保存する。データ利用判定を停止する。
STORE_WRITE_FAILED元データまたは整形済みデータを保管できない場合。受信成功を後続へ知らせず、許された回数の再試行後に停止する。UNHEALTHYとし、通常利用を止める。
UNKNOWN_EXTERNAL_STATE銘柄対応、銘柄仕様、利用可否のどれかが判断できない場合。未確定事項として台帳化し、戦略や再生処理の入力へ渡さない。不明のまま成功にせず、閉じた側へ倒して停止する。

12. HealthEvent状態

この表は、今あるデータを使ってよいかを四段階で表す規則である。状態名は機械が判定するための固定値だが、利用者は右側の説明に従って判断する。

状態を表す固定値人にとっての意味後続での使い方
HEALTHY取得、保管、銘柄対応、品質確認がすべて終わり、問題がない状態。通常どおり利用できる。
DEGRADED注意すべき問題はあるが、影響する期間や銘柄を特定して隔離できる状態。人間が明示した縮退範囲だけ利用できる。
UNHEALTHY取得、保管、内容の整合性、認証のいずれかに重大な失敗がある状態。対象の市場データ利用を停止する。
UNKNOWN状態を判断できない、または判断に必要な観測が欠けている状態。合格として扱わず停止し、人間または後続手順で決める。

13. 実行モードとの接続

この表は、同じ市場データ受渡し部を、過去検証から将来の実運用まででどう使い分けるかを説明する。Phase 2では外部への実取得や注文を行わず、固定入力を中心に確認する。

実行方法受け取る入力市場データ受渡し部の動き許される変更
過去検証（Backtest）固定した元データ・整形済みデータ・銘柄台帳・データ版を受け取る。再生用の読み手として動き、外部APIを呼ばない。ローカルの保管庫を読むだけである。

実運用（Live）実運用の内部市場イベントを受け取る。本書の詳細設計の対象外であり、利用可否とデータ利用判定の約束だけを引き継ぐ。Phase 2では実行しない。

16. 型付き公開契約

ここでは、実装者が作るプログラム上のデータ型と関数の形を示す。下の英語はPythonのコードそのものであり、実装名・変数名は変更しない。コードの後の表で、人が読むための意味と副作用を説明する。

from dataclasses import dataclass
from datetime import UTC, datetime
from hashlib import sha256
from typing import Literal, Protocol

@dataclass(frozen=True)
class HistoricalRequest:
    request_id: str                 # required; caller-generated UUID text
    dataset_ref: str                # required; e.g. vendor/dataset alias, not a Secret
    schema_ref: str                 # required
    symbols: tuple[str, ...]        # required; non-empty; vendor syntax stays here
    start_utc: datetime             # required; timezone-aware UTC
    end_utc: datetime               # required; start_utc < end_utc
    source_mode: Literal["fixture", "external"]

@dataclass(frozen=True)
class GatewayPayload:
    payload: bytes
    metadata: dict[str, str]        # Secret/authorization header is prohibited
    condition: Literal["available", "degraded", "pending", "missing", "unknown"]

class VendorGateway(Protocol):
    def fetch(self, request: HistoricalRequest) -> GatewayPayload: ...

class HistoricalDataPort(Protocol):
    def ingest(self, request: HistoricalRequest) -> "IngestionResult": ...
@dataclass(frozen=True)
class IngestionResult:
    raw_object_id: str
    payload_sha256: str
    health_event_id: str
    created: bool

@dataclass(frozen=True)
class HealthEvent:
    event_id: str
    component_name: Literal["market_data_adapter"]
    state: Literal["HEALTHY", "DEGRADED", "UNHEALTHY", "UNKNOWN"]
    reason_code: str
    affected_range_start_utc: datetime | None
    affected_range_end_utc: datetime | None
    observed_at_utc: datetime

    @classmethod
    def degraded(cls, request_id: str, reason_code: str) -> "HealthEvent":
        return cls(request_id, "market_data_adapter", "DEGRADED", reason_code,
                   None, None, datetime.now(UTC))

次の表は、上のコードに現れる公開関数を、人が判断できる言葉で読み替えるための仕様である。

関数の固定名返すもの起こり得るエラー繰り返し実行した場合と変更の内容
ingest(request)元データの識別子、内容確認値、状態記録の識別子を含むIngestionResultを返す。InvalidRequest、ExternalStateError、RawWriteErrorを返すことがある。依頼の内容確認値と元データが同じなら既存の元データ参照を返す。内容が違う元データは新しい記録としてだけ保存する。
gateway.fetch(request)元データ本体、取得条件、利用可否を含むGatewayPayloadを返す。AuthenticationError、RateLimited、PartialSymbolResolutionを返すことがある。外部との通信による変更は取得口の内側だけに閉じ込め、中心部へ通信やSDK由来の例外を渡さない。
reporter.record(event)戻り値はない。状態の出来事を監査記録へ追加する。記録を永続化できないときは、呼出元をUNHEALTHYとして扱う。監査記録は追加だけを認め、過去の記録を書き換えない。

18. 誤実装しやすい規則のコード例

このコード例は、承認前の外部取得、時刻の曖昧さ、品質低下したデータを、誤って成功扱いにしないための最小限の実装順を示す。英語はPythonの予約語、型名、変数名、エラー固定名である。

def ingest(self, request: HistoricalRequest) -> IngestionResult:
    if request.source_mode == "external" and not self.h2_2_approved:
        raise ExternalStateError("EXTERNAL_FETCH_NOT_APPROVED")
    if request.start_utc.tzinfo is None or request.end_utc.tzinfo is None:
        raise InvalidRequest("UTC_REQUIRED")
    payload = self.gateway.fetch(request)
    if payload.condition != "available":
        self.reporter.record(HealthEvent.degraded(request.request_id, payload.condition))
        raise ExternalStateError(f"DATASET_{payload.condition.upper()}")
    digest = sha256(payload.payload).hexdigest()
    return self.raw_store.put_if_absent(request, payload, digest)

実装時はVendorGatewayを固定入力用の実装と将来の提供元用実装で差し替える。将来実装がDatabentoのSDKを使っても、SDKの型、APIキー、通信応答のオブジェクトは、この関数の引数・戻り値へ出さない。

20. H2-1承認対象

この承認は、元データ・整形済みデータ・銘柄台帳をどの方式で扱うか、主要候補と条件付き候補をどう分けるか、連続した価格系列と限月をどう扱うか、品質低下したデータを停止または縮退利用するか、Phase 3へ渡すデータ版の約束を、人間が決める場である。

承認前は、限月をつないだ系列を主要な入力へ昇格しない。不明事項（Unknown）を合格として扱わず、固定入力または対象範囲の縮退で設計・テストを続ける。
