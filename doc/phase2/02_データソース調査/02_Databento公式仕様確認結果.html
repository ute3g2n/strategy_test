1. 調査範囲と結論

Databento Historical API、公式Python client、GLBX.MDP3、ohlcv-1m、definition、statistics、DBN、symbology、Dataset Condition、HTTPエラー、費用の公式情報を確認した。今回固定するのは外部仕様の観測点とAdapter境界であり、Databentoの型・SDK・APIレスポンスをCoreの契約として採用することではない。

Phase 2の採用方針: 外部応答はRaw Storeへ原形と取得メタデータを保存し、Adapterで内部のUTC、InstrumentId、MarketEvent、quality_flags、data_versionへ変換する。未確認・部分解決・degraded・checksum不一致はPassにせず、Data Gateで停止または縮退させる。

2. 公式一次情報の確認台帳

確認ID公式URL確認内容Phase 2での扱い
OFF-P2-01Databento QuickstartPython clientの導入、Historical client、timeseries.get_range、dataset/schema/symbols/start/endの基本形を確認。SDK呼出しはAdapter実装の内部詳細。Coreには呼出し名を公開しない。
OFF-P2-02Venues and datasetsGLBX.MDP3はCME、CBOT、NYMEX、COMEXのMDP 3.0を対象とし、先物・先物オプションを提供する。データにはts_recvも収録される。対象候補のdataset候補。実際の利用可能期間・権利はアカウント条件と日付ごとに再確認する。
OFF-P2-03Schemas and data formatsohlcv-1mは1分間隔、ts_eventは区間開始時刻、取引がない区間はレコードが出ない。価格は固定精度、volumeは区間の出来高。statisticsは公式統計を表す。欠損バーをゼロ埋めして取引事実に見せない。日足や公式清算値は1分OHLCVと同一視しない。
OFF-P2-04Symbologysymbologyはraw_symbol、instrument_id、parent、continuous。GLBX.MDP3はparent/continuous入力に対応し、parentは[ROOT].FUTで関連契約を参照する。入力シンボル、解決後raw_symbol、instrument_id、解決期間をCatalogに記録する。continuousはRoll ruleの明示的な入力として隔離する。
OFF-P2-05Parent symbology exampleparent指定のdefinition取得で子契約とspreadが返り得る。instrument_classでfuture/spreadを識別し、expiration等で整理する。MCL.FUT等の候補確認ではdefinitionを先に取得し、spreadを除外して採用候補を確定する。
OFF-P2-06Databento Binary EncodingDBNはself-describing metadata headerを持つ正規化データ形式で、公式client/APIの標準的な内部・転送形式。メタデータはdataset/schema等を含む。Raw保存時にDBN原形または受信形式、metadata、request fingerprintを保存し、再現性を確保する。
OFF-P2-07DBN metadataDBN metadataには元のHistorical API requestを再構成するための情報が含まれる。Dataset、schemaなどがヘッダーに記録される。取得条件の監査証跡に利用する。値をCoreのMarketEventへ無差別に流さない。
OFF-P2-08Historical API authentication and errorsHTTP 206は部分的シンボル解決、403は権限不足、404はリソース/シンボル不在、429はrate limit超過。Historical APIには接続・リクエスト種別ごとの上限がある。206、403、404、429を成功扱いにしない。retryはRetry-Afterを尊重し、繰返し失敗はData Gate停止とする。
OFF-P2-09Dataset conditionDataset Conditionは日付単位のavailable、degraded、pending、missingを返す。degradedは欠損または正確性の問題があり得る状態。available以外は品質フラグとし、採用可否を日付単位で記録する。degradedをPassにしない。
OFF-P2-10Usage-based pricing / BillingHistorical dataは未圧縮DBNサイズ基準で課金され、月次上限超過時は追加Historical requestが停止され得る。確定見積りは具体的requestのcustomization後に確認する。実取得、費用、entitlementはH2-2承認前に行わない。見積りと承認記録を別管理する。

4. 候補5銘柄の取得可能性確認項目

候補の「取得可能性」は、公式サイトの一般仕様だけでは各アカウント・期間・シンボルの取得成功を保証しない。次の確認を候補ごとに行い、未実施はUnknownとする。

候補要求する確認合格条件未合格時の扱い
MCLMCL.FUTのdefinition、futureのみの子契約、期間、ohlcv-1m、condition、Raw checksum。必要期間の子契約が解決され、definitionと1分データの対応が追跡可能。Main候補から一時除外しfixture/dry-runへ縮退。
M6AM6A.FUTについてMCLと同じ確認。通貨先物固有のcontract size/tick等もCatalogで確認。必要期間、definition、1分データ、品質状態が追跡可能。Main候補から一時除外しfixture/dry-runへ縮退。
MZC / MZS / MZW各parentの子契約、短い履歴の有無、volume/空区間、condition、spread除外、proxy/fallbackの要否。条件付き候補として本線と分離したDatasetVersionを作成できる。Main Replay inputへ入れず、条件付き検証データとして隔離。

確認コマンドやAPI keyの値はこの成果物に記録しない。実行時のSecret参照名は DATABENTO_API_KEY のみとし、ログにはマスク済みの環境変数存在フラグだけを残す。

6. H2-2 Human Gate

承認対象: 外部APIへの実取得を行うか、対象dataset/schema/期間/候補を何にするか、Databento entitlement、費用上限、Secretを参照する実行環境、再取得差分の保存方針。

承認時の証跡: 承認者、承認日時、対象候補、期間、見積り、月次上限、Secret参照名、実行許可範囲を plan/phase2/ログ/ のHuman Gate記録へ保存する。API key値、Authorization header、account IDは記録しない。

未承認時: 外部API実取得、費用が発生するrequest、entitlement検証のための認証呼出しを停止する。P10で取得済みの研究用fixtureと公式公開仕様だけでAdapter設計を継続し、取得可否はUnknownのままにする。
