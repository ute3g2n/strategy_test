1. ドメインの概要: 実DBN変換は何をするものか

DBNはDatabentoが市場データを保存・受渡しするためのバイナリ形式である。P2-12は、P2-08で一回だけ取得したDBNのbytesを読み、提供元固有のrecordをCoreに出さず、内部共通形式のNormalizedBarとMarketEventへ変換する。

この部品は通信・認証・注文・戦略判断を行わない。デコード、時刻、銘柄対応、品質、保存、Manifestのどれかを確認できなければ、イベントを一件も返さずData Gateを停止する。

確認した公式一次情報確認日この設計で使う事実
Databento Binary Encoding2026-08-08DBNはmetadataとrecordからなり、recordには種別、publisher ID、外部instrument ID、イベント時刻がある。公式decoderで読む対象は保存済みbytesだけにする。
Databento OHLCV schema2026-08-08ohlcv-1mのts_eventは1分バー開始時刻で、価格は固定小数点の整数表現である。時刻や価格の意味を推測で変えない。
機能ID機能誰にでも分かる説明失敗時の動き
DBN-F01DBNの検証と読取りデータ箱の形式と中身が、記録した内容確認値どおりかを確かめてから読む。形式や内容確認値が違えば、読んだ結果を使わず停止する。
DBN-F02内部形式への正規化外部の数字・銘柄番号を、システム共通の時刻・価格・銘柄IDの形へ写す。銘柄や時刻を一つに決められなければ、勝手に選ばず停止する。
DBN-F03決定的Replay同じ箱・同じ規則なら、毎回同じイベント列が作られることを確かめる。少しでも入力や規則が変われば別の版として扱い、本線へ渡さない。

6. テスト仕様

この表はP2-12の範囲で必要な全試験を示す。P2-12-01では、記録済みSHA-256を入力識別子として固定するDBN-T01だけがGREENであり、Git管理外の実DBNは開かない。実装境界の試験は意図したREDである。REDをskipで隠さない。

テストIDテスト概要テスト条件（入力値）操作期待結果合否判定基準
DBN-T01P2-08のDBN入力の識別子を固定する。記録済みSHA-256だけ。実DBN本体は入力にしない。設計の定数とP2-08証跡のSHA-256を照合する。不一致なら設計を中断する。一致しても変換結果は作らない。H2-5前は実DBNを開かない。H2-5後に保護場所でhash/headerを再確認する。
DBN-T02内容確認値が違う入力を読む前に止める。正しい形式に見えるが期待SHA-256と異なるbytesを用意する。DatabentoDbnDecoder.decodeを呼ぶ。RAW_CHECKSUM_MISMATCHで停止する。DecodedRecord、NormalizedBar、Manifest、MarketEventが0件である。
DBN-T03形式、header、対応外schema、未知record、途中で切れたrecordを通常行にしない。magic不正、短いheader、許可外version、許可外rtype、切断bytesをそれぞれ用意する。Decoderを呼ぶ。DECODE_OR_SCHEMA_ERRORまたはDECODE_RECORD_INVALIDで停止する。SDK例外名やpayload本文を公開例外・証跡へ出さない。
DBN-T04受信UTC時刻が無い入力を、イベント時刻や現在時刻で補わない。raw_received_at_utcが無いRaw入力を用意する。Normalizerを呼ぶ。RAW_RECEIVED_AT_MISSINGで停止する。MarketEvent.received_at_utcを推測値で作らない。
DBN-T05外部銘柄を内部銘柄IDへ一意に結べないとき停止する。Catalog無し、候補複数、pending、audit失敗の入力を用意する。Normalizerを呼ぶ。CATALOG_MAPPING_UNRESOLVEDで停止する。任意のinstrument_idを選んだBarやEventがない。
DBN-T06UTC・一分足・価格・出来高・順序を固定して正規化する。UTCのts_event、固定精度価格、出来高、record順を持つ中間行を用意する。Normalizerを呼ぶ。bar開始はts_event、close時刻は規則版に従い一分後、価格は文字列のまま正規化される。naive/非UTC、未定義価格、価格関係不正、出来高不正、順序逆行は品質不合格になる。
DBN-T07品質不合格時にイベントを作らない。欠損、重複競合、異常価格、異常出来高、degraded、未知品質を含むBarを用意する。QualityChecker後にEvent Factoryを呼ぶ。QUALITY_REJECTEDで停止する。Manifest発行、Replay公開、Signal生成のいずれも行われない。
DBN-T08同じ入力から同じReplay系列を作り、入力や規則の変更を別版にする。同一のRaw hash、取得条件、Catalog、decoder版、規則版、code revisionを二回渡す。各入力を一つずつ変えた派生も用意する。二回の変換とReplayを比較する。同一入力は同一Bar、Manifest、Event ID列になる。変更入力は別data_versionになる。現在時刻や将来行を版番号へ混ぜない。
DBN-T09Vendor依存と秘密がCore契約へ漏れないことを確認する。公開契約のfield、Coreモジュールのimport、例外文字列を調べる。静的検査と契約試験を行う。SDK record、SDK例外、API key、Authorization、accountがCore型・証跡に無い。Decoder Adapter以外でdecoder依存をimportしていれば不合格である。
DBN-T10WSL隔離入力と依存wheelのすり替えを検出する。H2-5承認済みの保護パス、owner/mode、非リンク、wheel allowlist、入力hashを用意する。RUN-P2-DBN-001の事前検査を行う。読込前後のhashが一致し、保護条件と依存hashが一致する。/mnt、UNC、symbolic link、書込み可能入力、未許可wheel、Git index上のDBNを検出したら隔離試験を開始しない。

10. 永続化、Manifest、順序

この表は、既存Storeを使うときに何を別のdata_versionとして扱うかを定める。P2-12-01では実装せず、P2-12-02の必須契約とする。

項目固定する規則不一致時の扱い
Raw既存raw_object_idとpayload SHA-256を再利用し、DBN bytesを上書きしない。SHA-256不一致はRAW_CHECKSUM_MISMATCHで停止する。
data_version材料Raw SHA-256、取得条件hash、Catalog version/hash、normalization rule version、decoder version/artifact hash、品質hash、normalized content hash、code revision、source_mode="dbn_replay"を含める。一つでも変更すれば別版にし、既存版を上書きしない。
Manifestの型変更P2-12-02で既存DataVersionManifestへrequest_context_sha256、decoder_version、decoder_artifact_sha256を追加する。source_mode="dbn_replay"ではRaw SHA-256とこの3項目を必須、fixture_sha256は必ずNoneにする。source_mode="fixture_only"では従来どおりfixture_sha256を必須、DBN用3項目はNoneにする。いずれもその値をdata_version材料に含める。source modeに合わない値、または必須値の欠落はMANIFEST_INPUT_MISSINGとして停止する。
やさしい説明: 練習用のデータと本物のデータの身分証を混ぜません。どちらのデータかによって、必要な記録をはっきり分けます。

12. 設定、依存、監査、隔離入力

この表は、P2-12-02とP2-12-03で使用を許すものを狭く定める。H2-5が未承認の間、実DBN読取り・依存導入・WSL実行は行わない。

区分契約
decoder依存公式Databento Python clientのDBNStore.from_file等を候補とするが、P2-12-01では版を確定しない。H2-5後に依存名、版、配布元、wheelファイル名、SHA-256、Python ABIをGit管理の許可一覧で固定し、導入前に照合する。

固定受信時刻が無い場合、実DBN用のDbnReplayInputを作れず、通常値や現在時刻で代入してはならない。P2-12-01のテストで使う日時・Vendor・symbolはすべて合成fixtureであり、P2-08のprovenanceではない。

Catalogを一組で固定する規則: DbnCatalogBindingがresolver、catalog version、catalog SHA-256を一組で持つ。Normalizerは解決結果のcatalog_versionがBindingのversionと違えばCATALOG_MAPPING_UNRESOLVEDで停止する。DBN用Manifestは新しいManifestBuilder.build_dbn(..., catalog: DbnCatalogBinding, ...)だけで作り、catalog_versionやcatalog_sha256を別引数にするAPIを作らない。既存ManifestBuilder.buildはfixture専用として残す。

やさしい説明: データの版を作る場所が三つに分かれているため、一か所だけ直すと後で読み戻せません。三か所を同じ決まりで直します。

18. 誤実装しやすい規則のコード例

この規則は、時刻や銘柄を推測で補わないことと、Vendor依存をCoreから隔離することを示す。

from datetime import timedelta

def require_raw_received_at(value: datetime | None) -> datetime:
    if value is None or value.tzinfo is None or value.utcoffset() != timedelta(0):
        raise DbnNormalizationError("RAW_RECEIVED_AT_MISSING")
    return value

def resolve_or_stop(resolver: CatalogResolver, request: ResolveInstrumentRequest) -> str:
    result = resolver.resolve(request)
    if result.status != "resolved" or result.instrument_id is None:
        raise DbnNormalizationError("CATALOG_MAPPING_UNRESOLVED")
    return result.instrument_id

20. 人による承認の対象

H2-5: 既取得DBN一件をWSL隔離検証に使う入力配置と、固定版decoder依存の導入を承認する。追加取得、Secret投入、対象範囲拡大は含まない。

H2-2再承認が必要になる場合: RAW_RECEIVED_AT_MISSINGまたはCATALOG_MAPPING_UNRESOLVEDを既存証跡で解消できず、受信時刻・definition・symbologyを持つ新しい最小取得が必要になった場合。未承認なら既存DBNを通常利用せずData Gate UNKNOWNのまま停止する。
