最初に読む説明：このロードマップが決めること

最重要：これは実装開始・外部接続・実注文の許可ではありません

この文書は、Phase 4〜11をどの順番で分け、各Phaseで何を作るかを説明する候補ロードマップです。各Phaseを実際に始めるには、別途、そのPhase専用の複数Step実行計画書、詳細設計、REDテスト、機械品質Gate、レビュー、Human Gateが必要です。

Broker、Paper、Secret、実注文、実資金、Cloud、外部Data取得は、必要なPhaseの独立Human Gateが承認するまで行いません。

30秒で分かる結論

  1. Phase 4：既存のPython Coreを使い、利用者が画面や型付き入力から動かせるローカルBacktest製品の土台を作る。
  2. Phase 5：市場Dataの銘柄、期間、品質、Calendar、Cost、Gapなどを、実証できる形にする。
  3. Phase 6：実注文を出さずに、複数Unit、Portfolio、Risk、OMS、Kill、照合、復旧を作る。
  4. Phase 7：Risk・OMS・停止・照合ができた後で、Broker AdapterとPaper Tradingを検証する。
  5. Phase 8：長期Paper、20〜40 Unit、容量、Backup／Restore、端末・中継、障害復旧を実証する。
  6. Phase 9：まだ実資金を使わず、Live候補のEngine、契約、Risk値、費用、法務、Kill訓練を確認する。
  7. Phase 10：別Human Gateで明示承認された、少額・少数・限定期間だけを初めて実運用する。
  8. Phase 11：Small Liveの結果を基に、対象とRiskを段階的に拡大し、継続運用する。

計画上の完了と、実運用上の安全は同じではありません

Phase 1〜3の固定Coreや固定fixtureが合格していても、それだけで実市場の長期性能、利益性、Broker接続、Paper、Liveが合格したことにはなりません。未確認のものはUNKNOWN、後で決めるものはLATER_GATEとして残し、仮の値でPassにしません。

Phase 4Product／Application基盤とBacktest製品化

一言でいうと：既存Coreを、利用者が安全に操作・再現・確認できるローカルBacktest製品へつなぐPhaseです。

作る

製品の土台

型付き設定、Run／Job／Queue、Worker、API、UI、Persistenceをつなぎ、Backtestを「コードを直接呼ぶもの」から「利用者が操作する製品境界」へします。

できる

再現可能な検証操作

Data、Strategy、Config、Riskを指定し、Single／Sweep、Result、Chart、取引明細、Evidenceを確認できます。Cancel／Stop、履歴確認、checkpointからの再開も対象です。

まだしない

外部副作用

外部Dataの継続取得、Broker、Paper、Live、Secret、実資金、Cloud公開はこのPhaseの対象外です。

なぜこのPhaseが必要か

Phase 1〜3で固定したReplay、Fill、Cost、Roll、Gap、Calendar、Holdout、Turtle Strategy、Manifestなどを、利用者が同じ条件で実行し、結果とEvidenceを残せる境界にする必要があるためです。Coreの固定契約と、後続のData・Risk・Broker・UIの接続点を先に作ることで、後のPhaseが「何を受け取り、何を保存し、どこで止めるか」を判断できます。

上流計画での主な候補：FastAPI候補、型付き設定、SQLite WAL／Migration候補、ローカルJob Queue／Worker、React UI接続、単一Backtest、網羅検証、結果閲覧。候補技術の最終確定は、このロードマップではなくPhase 4の詳細設計・Gateで行います。

主な要求範囲：F01の基礎・起動／停止、F02のData／Strategy／Unit／Run、F03のBacktest／Sweep／Holdout、F05のAPI／UI／保存／Test要求。

このPhaseで作る成果物

  • Phase 4実行計画書複数Step、依存、Gate、停止条件、Evidence配置を定める。
  • 型付きRunモデル設定、Run、Job、Queue、状態、結果、履歴を扱う契約。
  • API／UI境界利用者の入力、検査、開始、停止、結果閲覧をつなぐ境界。
  • Persistence設計Run、Result、履歴、Evidenceを再現可能に保存する設計。
  • Backtest／Sweep実装Singleと複数条件の検証を固定条件で実行する仕組み。
  • Test／EvidenceGolden／Replay、API／File契約、UI主要状態、差分hashなどの証拠。
  • Runbook開始、停止、失敗、再開、証拠確認の運用手順。

前のPhaseから受け取るもの

  • RQV2-H3承認後の正式v2基準線。
  • RQV2-01の既存Core再利用範囲、Core Manifest、既存tests／fixture／Evidence。
  • F01〜F06のREQ、UC、Screen、State、Testへの追跡骨格。
  • Coreを無改変で使える範囲、または変更する場合の別設計・RED・影響レビューが必要であるという制約。

開始するための条件

確認すること開始可能な状態不足時の停止
承認RQV2-H3、Phase 4実行計画、Phase 4の開始Human Gateが確認できる。H3未承認のままP4実装へ進まない。
設計Run、API、UI、Persistence、停止・復旧、Evidenceの詳細設計とREDテストがある。入力範囲や保存契約が不明なら開始しない。
CoreCore差分が0、または変更内容・影響・承認が明示されている。無承認Core改変、固定fixtureの意味の拡張は停止。
外部境界外部Data、Broker、Secret、実資金、Cloudを呼ばない範囲が固定されている。外部I/Oが混入したら停止。

作業のまとまり

  1. 入力、Core再利用範囲、REQ／UC／UI／Test追跡を固定する。
  2. Run／Job／Queue、API、UI、Persistenceの詳細設計とデータ受渡しを確定する。
  3. Single／Sweep、Result、Chart、取引明細、Evidenceの操作契約を作る。
  4. 固定条件のREDテスト、実装、API／UI／保存の品質Gateを行う。
  5. 停止・失敗・再開・履歴・証拠のRunbookを作り、次のPhaseへData接続点を引き渡す。

正式なStep IDや実装順は、Phase 4専用の実行計画書で確定します。このロードマップは、作る成果物のまとまりを説明するものです。

品質Gate、Human Gate、完了条件

品質Gate

REQ／UC／Test追跡、Golden／Replay、API／File契約、UI主要状態、Critical／High 0、`git diff --check`、証跡hashを確認します。

Human Gate

Product基盤、Core無改変範囲、Backtest製品化範囲、P5へ渡すData境界を承認します。外部Dataや実注文は承認しません。

完了

Single／Sweepの入力、状態、結果、Evidenceを再現でき、UI・API・Worker・Persistenceの境界が機械検証されている状態です。

Unknownと次Phaseへの引渡し

UNK-P3-01（長期Data）、UNK-P3-05（Cost／Slippage／Gap）、UNK-P3-07（正式Calendar）、実市場のProviderや契約はP4の固定local検証だけでは解消しません。P4は、P5が実証できるようにData／Manifest／保存／Quality接続点を渡します。UI／Worker性能の測定設計はP4で行い、実測や20〜40 Unitの運用負荷はP8へ残します。

Phase 5市場Data運用化と実証

一言でいうと：Backtestへ渡す市場Dataが、本当に何を表し、どの期間・品質・費用・Calendar条件を持つかを証拠付きで確認するPhaseです。

作る

Dataの説明書と証拠

Catalog、Data contract、Raw／Normalized、Quality、Calendar、Provenance、Manifest、hash、Cost／Gap、長期・HoldoutのEvidenceを作ります。

できる

Dataを使ってよい範囲の判断

MCL、M6A、MZC、MZS、MZWの5候補について、対象、期間、欠損、時刻、Calendar、費用、仮定を確認し、Backtest入力として扱える範囲を判断できます。

まだしない

利益性・Live適合の断定

Data品質を確認しても、利益性、Broker、Paper、Live適合が自動的に証明されたことにはしません。

なぜこのPhaseが必要か

固定fixtureやsynthetic DataでReplayが動いても、実市場Dataの期間、銘柄、契約、Calendar、欠損、Cost、Slippage、Gapが正しいとは限りません。P5では、Dataを「取得した」だけで終わらせず、どこから来たか、何を含むか、どこが欠けているか、どの仮定を置いたかを再現可能に記録します。

主な要求範囲：F02 §13〜15、F03 §22、F05 §43／47／55、UNK-P3-01、UNK-P3-05、UNK-P3-07。

このPhaseで作る成果物

  • Data source／費用／Secret Gate記録Provider、entitlement、費用、外部I/O、Secret範囲を承認単位で記録する。
  • Instrument Catalog5候補の論理ID、実Symbol、取引所、限月、Roll、単位、対応関係を整理する。
  • Raw／Normalized／Quality report取得物、正規化、欠損、重複、時刻逆行、範囲外値を分けて検査する。
  • Provenance／Manifest／hashDataの出所、版、対象期間、生成条件、同一性を追跡する。
  • Calendar監視公式版、短縮日、臨時休場、更新監視を確認する。
  • Cost／Slippage／Gap report固定仮定と実測値を分け、感度と根拠を残す。
  • 期間分割Evidence長期、Holdout、Walk-forwardの範囲と境界を保存する。

対象範囲

対象確認すること未確認ならどうするか
初期5候補MCL、M6A、MZC、MZS、MZWの実Symbol、取引所、限月、Roll、単位、Provider／Broker対応。論理IDを実契約と混同せず、未確定としてP5のGateに戻す。
時間足D1、H4、H1、M30、M15の生成方法、元Data、provenance、M30の実M1連続性。不足する時間足を推測で補わず停止する。
品質欠損、重複、時刻逆行、範囲外、Calendar不一致、未来Data混入。Quality reportに記録し、Backtest入力へ渡さない。
費用・契約Provider、entitlement、費用上限、再配布、Secret、外部接続方式。別のData専用Human Gateが通るまで外部取得を開始しない。

前のPhaseから受け取るもの

  • P4で固定されたData／Manifest／保存／Qualityの接続点。
  • Dataを再現可能に登録・検査・停止できるRun／Evidence形式。
  • RQV2-01のCore契約と、`UNK-P3-01`、`UNK-P3-05`、`UNK-P3-07`の未解消状態。

開始するための条件

対象Symbol、期間、Data source、費用、Secret範囲、取得方法、停止条件、Evidence配置が、Data Provider専用Gateで承認されるまで、実Data取得や外部I/Oを開始しません。P4の固定fixtureから実Dataの値を推定しません。

作業のまとまり

  1. P4接続点、対象5候補、4資産種類、D1／H4／H1／M30／M15、REQ追跡を固定する。
  2. Catalog、Provider、Data contract、費用、Secret、保存・再配布条件を設計する。
  3. Raw／Normalized／Quality／Calendar／Provenance／Manifestの検査と再生成契約を作る。
  4. Cost／Slippage／Gap、長期、Holdout／Walk-forward、期間分割の判定条件を固定する。
  5. 承認範囲内で限定取得し、Quality、Calendar、Cost、Gap、HoldoutのEvidenceを残す。
  6. Unknownを解消または未解消のまま再分類し、P6へ渡す範囲を確定する。

品質Gate、Human Gate、完了条件

品質Gate

Data contract、再現、Look-ahead／Survivorship防止、固定値・実測値の分離、外部通信・Secret監査、未確認範囲の明示を確認します。

Human Gate

Data契約、費用、保存・再配布、対象範囲、外部接続方式を承認します。利益性やLive適合を承認するGateではありません。

完了

対象ごとにprovenance、hash、Quality、Calendar、Cost／Slippage／Gap、期間分割、欠落・停止・再生成の証拠があり、未確認範囲が明示されている状態です。

次Phaseへの引渡し

P5は、P6がRisk／OMSのSimulationへ入力できるData品質、Calendar、Cost、Gapの範囲を渡します。`UNK-P3-01`、`UNK-P3-05`、`UNK-P3-07`が完全に閉じない場合でも、Passへ変換せず、未解消の理由、次の確認時期、停止条件、Evidence先を統合台帳へ戻します。

Phase 6複数運用単位・Portfolio／Risk／OMS・Forward／Shadow

一言でいうと：Brokerへ注文を送る前に、複数Unitの資金・Risk・注文状態・停止・照合・復旧を、外部注文なしで完成させるPhaseです。

作る

実注文前の安全中枢

Portfolio／Account、資金配分、Risk、OMS、Order状態、Idempotency、競合、Kill、照合、Restart／Recoveryを作ります。

できる

仮想注文の安全確認

SignalからPositionまでの流れを固定Simulationで動かし、Risk拒否、Partial、Reject、Expire、差異、Incident、手動再開を確認できます。

まだしない

Brokerへの外部送信

Broker送信、Secret、Paper注文、実Account、実資金、Live、Cloudは行いません。

なぜPhase 7より前なのか

Brokerを先に接続すると、Risk bypass、重複注文、部分約定の扱い、照合不能、再接続後の誤再開などが、外部副作用を伴ったまま発生します。そのため、まずP6で「注文を送ってよいか」「送ったことになっているか」「Fillが不明なときに止まるか」「差異を直ちに解消できるか」を外部注文なしで固定Simulationします。

主な要求範囲：F02 §17〜18、F04 §23〜30、F05 §31〜34／44／48。

このPhaseで作る成果物

  • Portfolio／Risk／OMS詳細設計責務、入力、判定、状態、限度、停止、復旧を決める。

Gateと開始手順：Phase名だけでは始められない

Phaseの名前や目的が決まっても、実装・外部接続・実注文が自動的に許可されるわけではありません。各Phaseは、入力、設計、品質、承認、Evidenceを順番に確認します。

共通の7段階手順

  1. 統合台帳を確認する。Blocked、Unknown、Human Gate、期限、再開条件、Evidenceを確認する。
  2. 入力を固定する。前Phaseの成果物、Core範囲、対象Scope、Fixture、Manifest、hashを固定する。
  3. Phase専用計画を作る。plan/へ複数Step、担当、成果物、Gate、停止条件、Evidence配置を記録する。
  4. 詳細設計とREDを作る。実装者が判断なく進められる契約と、失敗を先に固定する。
  5. 機械Gateとレビューを行う。品質、Security、Red Team、独立レビューの指摘を閉じる。
  6. Human Gateの範囲を確認する。承認されたものだけを発火し、未承認の外部I/Oや実資金を行わない。
  7. 完了と引渡しを同期する。成果物、Evidence、Unknown、台帳、次Phase入力、doc/index.htmlを更新する。

Fail-closedの考え方

「確認できないが、とりあえず進める」は採用しません。Provider、Secret、費用、実Data、Order状態、照合、復旧、承認範囲が不明なら、止めてUnknownまたはBlockedとして記録します。

旧計画は削除・上書きせず、変更理由と過去の承認範囲を履歴として残します。新しい順序は、実注文より先に安全中枢、Paperより先に長期運用、Liveより先に候補審査を置くことが中心です。

旧計画の対象新Phase何が変わったか安全上の理由
旧Phase 2 Market Data新P5Product基盤をP4で先に作り、実Data、Calendar、Cost、QualityをP5で実証する。Dataを渡す先のRun／Manifest／Quality境界を先に固定できる。
旧Phase 3 Strategy／Backtest新P4既存Coreの固定契約を再利用し、UI／API／Worker／Persistenceへ製品化する。固定Coreの合格と、利用者が操作する製品境界を分けられる。
旧Phase 4 Broker／Paper新P7Broker／Paperより前にP6でRisk／OMS／Kill／Reconcileを完成させる。Risk bypass、重複注文、照合不能のまま外部副作用へ進むことを防ぐ。
旧Phase 5 Portfolio／Risk／Account新P6Broker注文前の責務境界、Risk、OMS、複数Unitを固定Simulationする。外部注文なしで失敗、停止、復旧を繰り返し検証できる。

変更理由を一言でいうと

  1. Broker／Paperを先行させず、Risk／OMS／Kill／照合を先に置いた。
  2. UI、API、Persistence、Job Queue、BacktestをP4にまとめ、利用者が操作できる境界を先に作った。
  3. 固定synthetic／PoCの合格と、実市場・長期・Cost・Calendar・Paper／Liveの実証を分けた。
  4. Paper直後にLiveへ進まず、P8で長期Paper、負荷、Backup／Restore、端末・中継を確認する。
  5. LiveをCandidate、Small、Normalの3段階に分け、それぞれ別のScope、Risk、実資金、Auto-approval Gateにした。

SLO遅延や復旧など、守りたいサービス水準の目標。P8で候補を測り、P11で継続監視と再承認に使う。
