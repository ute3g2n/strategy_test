6.1 単一Backtest

  1. 一つのRunId、一つのJobId、一つのimmutable condition hashを生成する。
  2. PreflightでData／Strategy／Risk参照、ExperimentPlan、Core baseline、fixture、Calendar、Manifestを検証する。
  3. Workerは同じBacktestRunRequestをCoreのBacktestRunner.runへ一度だけ渡す。
  4. CoreがCOMMITTEDなら既存ResultStoreのcommit markerとatomic publishを検証し、Application result refとEvidenceを保存する。
  5. CoreがSTOPPEDならpublishable resultを作らず、固定failure code、Checkpoint、Evidenceだけを保存する。

6.2 Sweep

Sweepは単一Backtestの設定を上書きする操作ではない。SweepSpecを検証した後、候補ごとに run_kind=SWEEP_CHILDの新しいRun、Job、Checkpoint、Result、Evidenceを作る。 Parent Sweepは候補の状態集約だけを持ち、候補結果を混ぜない。

  • 候補ID、設定payload、設定hashはソート・重複除去し、無効候補を理由付きで保存する。
  • 一つの候補の失敗を別候補の成功へ変換しない。個別失敗継続か全体停止かはSweepPolicyで固定する。
  • 全候補の結果を比較表示できるが、最良設定・Risk値・本番設定の自動採用は行わない。
  • 同じ候補を再実行する場合も新RunIdを作り、前回の条件・結果・Evidenceは上書きしない。

10.2 操作ポリシー

  • Cancel: Queue待機中はCore呼出し前にCANCELLED。RUNNINGではcancel intentを保存し、現在の処理境界とCheckpointで停止する。途中結果は参考用のSTOPPEDとして保存し、成功Resultに昇格しない。
  • Stop: Data不正、Manifest不一致、Look-ahead、Core停止、保存不整合など安全条件で即時または境界停止する。再試行可能な一時障害と同じ扱いにしない。
  • Retry: SQLiteの一時busy等、原因が一時的で副作用が確定しているローカル障害だけを10秒、30秒、60秒、最大3回とする。各attemptをAuditへ保存し、4回目はFAILED。
  • Resume: 直前のCheckpoint、Manifest、input sequence、commit marker、Core Snapshotを全照合する。照合できなければ新しいイベントを処理せずRECOVERY_REQUIRED。
  • Unknown side effect: Worker lease切断、commit marker不明、rename結果不明、Core結果受信不明は再試行せず、状態をRECOVERY_REQUIREDとして人の確認を待つ。
def execute_job(job):
    validate_lease(job.lease_token)
    if job.cancel_requested and job.status == "QUEUED":
        transition("CANCELLED"); return
    preflight_or_stop(job.run)
    for attempt, delay in enumerate((0, 10, 30, 60)):
        if attempt > 0:
            wait_local_only(delay)
        outcome = run_core_once_or_reconcile(job)
        if outcome.is_committed:
            publish_after_full_hash_check(outcome)
            transition("SUCCEEDED")
            return
        if outcome.is_typed_stopped:
            save_checkpoint_and_failure(outcome)
            transition("STOPPED")
            return
        if outcome.side_effect_unknown:
            transition("RECOVERY_REQUIRED")
            return
        if not outcome.retryable or attempt == 3:
            transition("FAILED")
            return
    transition("FAILED")

疑似コードのrun_core_once_or_reconcileはCoreを同じRunで二重実行してよいという意味ではない。 commit marker・idempotency・Checkpointを先に照合し、既にCOMMITTEDなら読み取りで完了させ、 不明ならRecoveryへ止める。

11.3 MigrationとWALの実装契約

  1. 起動時にDB fileの許可root、通常file、reparseなし、schema versionを検証する。
  2. 未適用migrationは番号順に、script hashを検証して一つのwrite transactionで適用する。
  3. migration中の失敗はtransaction rollback。未知のschema、hash差替え、途中migrationは起動を停止する。
  4. WALを使う場合も結果本文のcommitをSQLiteだけで完了扱いにせず、Core ResultStoreのmarkerと相互照合する。
  5. P4-06は固定されたmigration一覧以外を自動生成しない。既存DBを破壊、drop、初期化して復旧したことにしない。
