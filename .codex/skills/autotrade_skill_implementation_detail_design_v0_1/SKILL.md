# autotrade_skill_implementation_detail_design_v0_1

## 目的

論理設計や責務表を、実装に直接使える詳細設計へ変換する。設計書は「方針の説明」で終えず、実装対象、所有モジュール、型付き入出力、保存形式、正常系・異常系の順序、テストまでを一貫して定義する。

## 入力

- 要件、追跡マトリクス、Phase Runbook
- 前段のアーキテクチャ、ドメイン、Adapter、実行、品質設計
- 対象リポジトリの実装言語、既存ディレクトリ、既存テスト、依存ライブラリ
- 対象成果物、既存詳細設計書、レビュー指摘、Human Gate状態
- `detailed_design_scope`、`implementation_target`、`document_coverage_matrix`

## 出力

- 実装詳細設計書セット
- モジュール構成・依存方向・所有者の一覧
- 型付き入出力契約、永続化契約、シーケンス、アルゴリズム例、テスト対応表
- REQ / DEC / UNK / ART追跡表、レビュー採否表、改訂履歴

## 必須構成要素

各設計対象について、該当しない場合も `N/A` と理由を記録し、次を確認する。

1. 実装スコープ、前提、非対象、用語、対象リポジトリ・言語・配置先
2. モジュール構成、依存方向、公開境界、各モジュールの責務と非責務
3. クラス、関数、Repository、DTO、Command、Eventの責務と所有モジュール
4. 型付きの入力、出力、必須・nullable、既定値、エラー、副作用、冪等性
5. 正常系と主要失敗系のシーケンス、状態遷移、再試行、fail-closed、復旧
6. 永続化形式、キー、制約、索引、ファイル/テーブル配置、versioning、migration、保持方針
7. 非自明な変換・照合・重複排除・差分検出の擬似コードまたは対象言語のコード例
8. 設定、環境変数参照名、Secret境界、監査ログ、HealthEvent、観測指標
9. テスト対象、fixture、単体・結合・failure injection、受入条件、要件対応
10. Run Manifest、data_version、互換性、後続モジュールへの入力保証
11. Unknown、決定時期、担当、未決時の停止または縮退
12. 設計レビュー、レッドチーム、改訂、再レビューの採否と残課題

## 禁止事項

- モジュール構成、型、処理順、保存契約、テストを欠いた文書を「詳細設計」と扱うこと
- 入出力を属性名の羅列だけで済ませ、型・必須性・エラー・副作用を省くこと
- 外部SDKやvendor型をCore契約として流出させること
- 実在しないライブラリ、データベース、クラス、APIを確定事項として書くこと
- Unknown、Secret、API key、Account IDを隠すこと
- コード例を、対象リポジトリの言語・依存・設計契約と矛盾させること

## 品質チェック

- 独立した実装者が追加の設計判断なしに、対象モジュールとテスト雛形を作れる。
- 各公開APIは入力型、出力型、失敗、冪等性、副作用、呼出側が満たす条件を持つ。
- 永続化は保存単位、キー、上書き・差分・再実行の規則まで定義される。
- 正常系だけでなく、主要な異常系の停止・復旧・監査が図または手順で追える。
- コード例または擬似コードが、最も誤実装しやすい規則をカバーする。
- テスト対応表が各契約・異常系・要件を辿れる。
- A91の詳細設計完全性レビューで重大・高指摘が残っていない。
